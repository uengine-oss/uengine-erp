# 계획과 결정

원본 시나리오는 [scenario.md](scenario.md), 구조는 [architecture.md](architecture.md), 모듈 사이 계약은 [modules/events.md](modules/events.md) 다.

## 결정

| 번호 | 결정 | 이유 |
|---|---|---|
| 1 | 게시된 청구서는 되돌리지 않고 대변 메모로 정정한다 | 세금 신고된 문서를 시스템만 되돌리면 안 된다 |
| 2 | 연쇄 되돌리기는 범위를 보여 주고 동의를 받는다 | 뒤따른 작업이 같이 사라지는 것을 사람이 알아야 한다 |
| 3 | 회사 전체 되돌리기는 관리자 전용, 미리보기와 사유 필수 | 범위가 가장 넓다 |
| 프로젝트 1 | 시간은 작업 스트림에 쓰지 않고 자기 스트림에 둔다 | 스트림은 통째로 돌아가므로, 작업에 쓰면 시간 한 건을 되돌릴 때 그 뒤의 일이 모두 끌려온다 |
| 프로젝트 2 | 주문 취소는 시간이 기록된 프로젝트를 취소하지 않고 표시만 한다 | 일한 시간은 주문이 되돌리지 못한다. 사람이 정한다 |
| CRM 1 | 단계를 넷으로 고정하고 칸반은 공통 화면으로 한다 | 전환율은 단계가 같아야 뜻이 있다. 메타데이터로 충분했다 |
| CRM 2 | 수주의 `make_quote` 를 이벤트에 싣는다. 판매는 켠 뒤의 수주만 듣는다 | 견적이 필요 없는 수주가 있고, 초안이 견적 전환율의 분모에 들어가며, 판매를 늦게 켤 때 초안이 무더기로 생기면 안 된다 |
| 경비 1 | 영수증은 고객의 Supabase Storage 에 둔다. 파일 이름은 원장 밖, 원장에는 지문만 | 원장은 지울 수 없고, DB 는 500 MB 라 사진을 넣으면 쓰기가 멈춘다. Storage 는 이미 있고 서버를 늘리지 않는다 |
| 경비 2 | 금액과 적요는 모든 구성원이 읽는다. 영수증만 행 단위로 막는다 | 커널의 읽기 권한이 유형 단위다. 금액까지 가리려면 커널을 크게 고쳐야 한다. 사용자 판단이 필요하다 |
| 커널 1 | 역할 `member`, 모듈의 `requires`, `erp.peek_by` 를 더했다 | 직원 누구나 쓰는 문서와 다른 모듈 없이 못 켜는 모듈, 계정으로 직원을 찾는 일이 처음 생겼다 |
| 커널 2 | MCP 의 고치기와 지우기 도구에서 유형 목록을 뺐다 | 모듈이 늘수록 목록이 도구마다 커져 4,000 바이트 약속을 넘었다(4,477). 그 둘은 이미 가진 레코드를 말하므로 목록이 없어도 된다 |
| 인사 1 | 지워 달라고 할 수 있는 값은 원장 밖 표에 두고, 이벤트에는 칸 이름만 남긴다. 주민등록번호는 받지 않는다 | 원장은 지울 수 없다. 패턴은 `docs/modules/hr.md` 이고 급여가 따른다 |
| 인사 2 | 이름과 입퇴사일은 원장에 남기고 그 한계를 입력 화면과 스펙에 적는다 | 지난 문서가 이름을 보여 줘야 하고, 구독자에게 필요한 사실이다 |
| 인사 3 | 앞날의 퇴사는 기록하지 않고, 재입사는 새 레코드이며, 퇴사는 계정을 막지 않는다 | 예정은 사실이 아니다. 구독자가 특별히 처리할 것이 없어야 한다. 구성원은 되돌리기 대상이 아니라서 묶으면 퇴사를 되돌릴 수 없다 |
| 인사 4 | MCP 로는 개인정보를 읽지 못한다. 쓰기와 지우기는 된다 | 에이전트가 읽은 값은 대화 기록으로 나가 지울 수 없게 된다 |
| 제조 1 | 제조는 재고 표를 만지지 않는다. 완료 이벤트를 재고가 듣고 일반 전표로 움직인다 | 재고가 멈춰도 제조 기록이 남고, 예약, 원가, 전표, 되돌리기를 새로 만들지 않는다 |
| 제조 2 | 자재 부족으로 서버가 막지 않고 지시는 예약하지 않는다. 화면이 재고의 답을 나란히 보여 준다. 관찰(완료할 때 경고 창)은 화면에서만 따른다 | 제조는 재고 표를 읽을 수 없고, 구독자는 거부할 수 없다. 재고의 일상 운영도 음수를 허용한다 |
| 제조 3 | 다단계는 읽을 때만 펼치고 자식 지시를 만들지 않는다. 키트는 하지 않는다 | 규칙으로 반제품 초안이 생기므로 충분하다. 자동 자식 지시는 되돌릴 범위를 크게 만든다 |
| 제조 4 | 재고 계정은 `상품` 하나로 두고 재공품은 지시마다 0 으로 끝낸다. 표준 원가 차이는 제조원가차이로 보낸다 | 자재와 제품을 나누면 출고 분개가 함께 바뀌어 회계 변경이 커진다. 나중에 켠 회계의 동일성을 쉽게 지킨다 |
| 제조 5 | 재주문 규칙의 보충 방식은 제조 모듈이 카탈로그에 더하고, 재고는 값을 싣기만 한다. 관찰(규칙이 지시를 확정 상태로 만듦)과 달리 초안을 만든다 | 재고는 제조를 몰라야 한다. 사람이 보기 전에 자재를 잡지 않는다 |
| 제조 6 | 분해 문서를 두지 않고, 잘못 완료한 것은 되돌리기와 사가 상쇄로 처리한다 | 원장에 이미 되돌리기가 있다. 관찰(분해가 음수를 허용)을 따르지 않고 팔린 제품은 막는다 |
| 휴가 1 | 휴가 사유와 반려 사유는 원장 밖에 두고 본인, 상사, 인사 담당자만 읽는다. 표를 닫고 함수 하나로 답한다 | 건강·가족 일일 수 있고 원장은 지울 수 없다. 읽는 범위가 행마다 달라 역할로 말할 수 없다 |
| 휴가 2 | 신청과 부여는 유형을 `hr` 에게만 열고, 본인과 상사는 전용 함수로 자기 행을 읽는다. 팀 달력은 이름과 날짜만 내준다 | 커널의 읽기는 유형 단위이고 이벤트에 값이 실린다. 유형을 열면 동료의 병가가 원장으로 보인다 |
| 휴가 3 | 승인자는 상사, 없거나 퇴사했거나 계정이 없으면 인사 담당자다. 자기 신청은 결정할 수 없다 | 아무도 못 누르는 대기를 만들지 않는다 |
| 휴가 4 | 근태가 없어 출근율을 확인할 수 없으면 법이 정한 일수를 주고 "확인 못 함"으로 남긴다 | 법이 준 일수를 앱이 근거 없이 깎지 않는다. S11 |
| 휴가 4b | 승인된 쉼을 결근으로 치지 않는다. 유형마다 출근으로 봄, 소정근로일에서 뺌, 출근 아님을 고른다 | 고용노동부 해석(2021-08-04)이 업무 밖 질병 휴직 등을 소정근로일에서 빼라고 한다. 예시를 그대로 시험한다 |
| 휴가 5 | 부여 기준 전환, 소정근로일 비례, 미사용 수당, 공휴일 내장 목록은 만들지 않는다 | 확인한 규칙이 없거나 다른 모듈의 일이다. `docs/modules/timeoff.md` |
| 근태 1 | 주 52시간은 그 주 전체 근로시간으로 판단한다. 하루 8시간 초과의 합은 따로 보여 준다 | 대법원 2020도15393. 수당의 기준과 한도의 기준은 다르다고 판결이 말한다 |
| 근태 2 | 휴가 날짜는 신청마다 자기 스트림(`attendance_leave`)에 둔다 | 그날의 스트림에 쓰면 잘못된 승인을 되돌릴 때 그날 찍은 출근까지 끌려온다 |
| 공통 | 공휴일과 쉬는 요일, 법정 계산은 기초데이터 `sql/12_calendar.sql` 에 둔다. 모듈 문서의 `requires` 로 인사를 요구한다 | 휴가와 근태가 서로 몰라도 같은 달력을 쓴다. 분석도 같은 계산을 부른다 |
| 4 | 1차 범위는 모듈별 기본 기능과 성장 시나리오다. 빠진 고급·Enterprise 항목은 표에 ✗ 로 남긴다 | 처음 요구가 기초데이터부터 주문 처리까지다 |
| 5 | 앱·DB 버전을 양방향으로 확인하고, 모르는 필드는 거부한다 | 앱은 즉시 바뀌고 DB 는 고객이 올린다 |
| 6 | REST 는 카탈로그에서 자동 생성한다. 한 요청에 한 건, 재시도 키 지원 | 유형마다 손으로 만들지 않는다 |
| 7 | MCP 는 SQL 함수로 시작하고 장기 연동 키를 둔다 | 고객에게 서버를 하나 더 요구하지 않는다. 로그인 토큰은 1시간이면 만료된다 |
| 8 | **모듈 사이는 전부 구독이다.** 처음 제안(핵심 4개 모듈을 한 트랜잭션으로)을 사용자 지시로 철회했다 | 회사가 모듈을 하나씩 더하려면 판매가 재고를 몰라야 한다 |
| 9 | 예측과 what-if 를 1차 범위에 넣고, 근거가 모자라면 숫자를 내지 않는다 | 제품의 핵심 가치이며, 가상 회사 시험에서 경고 없이 크게 틀린 경우를 확인했다 |
| 10 | 구독자의 전달은 5초 cron + 앱의 즉시 재촉이다 | 1초 cron 은 로그가 하루 8만 행 쌓인다. 화면은 재촉으로 바로 보인다 |
| 12 | 결제 조건이 없는 문서의 기일은 청구일이다. 관찰(만든 날)을 따르지 않는다 | 소급 청구서의 미수금 연령이 틀어지고, 미래 청구서의 기일이 청구일보다 앞선다 |
| 13 | 구매 역할의 승인은 거부한다. 관찰(변화 없이 통과)을 따르지 않는다 | 화면이 "승인 완료" 라고 하는데 주문은 그대로면 승인된 줄 안다 |
| 14 | 잠금일 안의 문서는 게시·취소·삭제를 거부한다. 관찰(회계일을 저절로 옮김, 초안은 허용)을 따르지 않는다. 날짜를 뒤로 옮긴 정정은 받는다 | 말없이 바뀐 회계일은 사람이 고른 날짜와 어긋난다. 잠긴 청구서를 정정할 길은 있어야 한다 |
| 15 | 입금은 미결 계정 없이 예금으로 분개하고, 은행 대사는 원장 밖의 맞춤으로 둔다 | 전표 계약과 나중에 켠 회계의 동일성을 그대로 두는 가장 작은 설계다. 차이는 `erp_bank_reconciliation` 이 보여 준다 |
| 16 | 외화는 받지 않는다(`ERP_CURRENCY`) | 환산이 없으므로 받으면 100 USD 가 회사 통화 100 으로 잡힌다 |
| 11 | 일부러 관찰과 다르게 둔 동작: 음수 할부 없음, 연락처 병합은 이벤트로 이력을 남김, 가격 규칙 기간은 날짜 단위로 끝 포함, 빈 문서 번호 없음 | 앞의 셋은 결함에 가깝거나 이력을 잃는다. 마지막은 세무상 번호가 끊기면 안 된다 |
