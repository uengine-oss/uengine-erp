# 계획과 결정

원본 시나리오는 [scenario.md](scenario.md), 구조는 [architecture.md](architecture.md), 모듈 사이 계약은 [modules/events.md](modules/events.md) 다.

## 결정

| 번호 | 결정 | 이유 |
|---|---|---|
| 1 | 게시된 청구서는 되돌리지 않고 대변 메모로 정정한다 | 세금 신고된 문서를 시스템만 되돌리면 안 된다 |
| 2 | 연쇄 되돌리기는 범위를 보여 주고 동의를 받는다 | 뒤따른 작업이 같이 사라지는 것을 사람이 알아야 한다 |
| 3 | 회사 전체 되돌리기는 관리자 전용, 미리보기와 사유 필수 | 범위가 가장 넓다 |
| 4 | 1차 범위는 모듈별 기본 기능과 성장 시나리오다. 빠진 고급·Enterprise 항목은 표에 ✗ 로 남긴다 | 처음 요구가 기초데이터부터 주문 처리까지다 |
| 5 | 앱·DB 버전을 양방향으로 확인하고, 모르는 필드는 거부한다 | 앱은 즉시 바뀌고 DB 는 고객이 올린다 |
| 6 | REST 는 카탈로그에서 자동 생성한다. 한 요청에 한 건, 재시도 키 지원 | 유형마다 손으로 만들지 않는다 |
| 7 | MCP 는 SQL 함수로 시작하고 장기 연동 키를 둔다 | 고객에게 서버를 하나 더 요구하지 않는다. 로그인 토큰은 1시간이면 만료된다 |
| 8 | **모듈 사이는 전부 구독이다.** 처음 제안(핵심 4개 모듈을 한 트랜잭션으로)을 사용자 지시로 철회했다 | 회사가 모듈을 하나씩 더하려면 판매가 재고를 몰라야 한다 |
| 9 | 예측과 what-if 를 1차 범위에 넣고, 근거가 모자라면 숫자를 내지 않는다 | 제품의 핵심 가치이며, 가상 회사 시험에서 경고 없이 크게 틀린 경우를 확인했다 |
| 10 | 구독자의 전달은 5초 cron + 앱의 즉시 재촉이다 | 1초 cron 은 로그가 하루 8만 행 쌓인다. 화면은 재촉으로 바로 보인다 |
| 11 | 일부러 관찰과 다르게 둔 동작: 음수 할부 없음, 연락처 병합은 이벤트로 이력을 남김, 가격 규칙 기간은 날짜 단위로 끝 포함, 빈 문서 번호 없음 | 앞의 셋은 결함에 가깝거나 이력을 잃는다. 마지막은 세무상 번호가 끊기면 안 된다 |
