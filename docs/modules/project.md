# 프로젝트 (`sql/67f_project.sql`)

모듈 `project`(sort 72). 프로젝트, 작업, 단계, 담당자, 시간 기록을 다룬다. 다른 어떤 모듈도 필요 없다. 인사가 켜져 있으면 담당자는 직원이고, 판매가 켜져 있으면 서비스 주문의 이벤트로 프로젝트가 생길 수 있다. 근태는 이벤트가 있을 때만 분석에서 대조한다. 새 역할은 `project` 다.

**범위.** 다음은 하지 않는다.

| 안 하는 것 | 이유와 대신할 길 |
|---|---|
| 회사가 단계를 바꾸기, 프로젝트마다 다른 단계 | 할 일, 진행, 검토, 완료, 취소로 고정한다. 소요 실측과 칸반이 단순해진다 |
| 작업 의존 관계, 하위 작업, 마일스톤, 반복 작업 | 이번 시나리오에 쓰는 곳이 없다. 나중에 더해도 계약이 깨지지 않는다 |
| 작업을 다른 프로젝트로 옮기기 | 기록된 시간이 어긋난다. 새로 만든다 |
| 시간으로 청구하기, 원가 계산 | 판매와 청구에 닿는 일이다. 시간은 이벤트로 남으니 나중에 그 모듈이 들을 수 있다 |
| 타이머, 시간 승인 | 사람이 숫자로 적고 바로 반영된다 |
| 프로젝트 공개 범위, 고객 포털 | 모든 구성원이 읽는다 |
| 제품별 프로젝트 양식 | 주문 줄 하나가 작업 하나다 |

## 유형

`project`: `number`(`PJ00001`), `name, partner_id, manager_id, date_start, date_end(납기), note, origin_number, origin_cancelled, done_on, origin_type, origin_id, state(open, done, cancelled)`

`project_task`: `number`(`TK00001`), `name, project_id, project_name, employee_id, member_id, person_name, planned_hours, deadline, note, started_on, done_on, origin_line_id, user_id, department_name, state(todo, doing, review, done, cancelled)`

`time_entry`: `task_id, task_name, project_id, project_name, date, hours, employee_id, member_id, person_name, note, user_id, department_name`

**시간은 작업의 스트림에 쓰지 않는다.** 스트림은 통째로 돌아간다. 작업에 쓰면 시간 한 건을 되돌릴 때 그 뒤의 작업 변경이 모두 끌려온다. 그래서 작업에 기록 시간 칸이 없고 화면이 시간 기록을 모아 보여 준다.

## 담당자

| 상황 | 동작 |
|---|---|
| 인사 켜짐 | `employee_id` 칸이 보이고 `member_id` 칸은 화면에서 사라진다. 퇴사자에게 맡기지 못한다 |
| 인사 꺼짐 | `employee_id` 칸이 없고 `member_id` 로 고른다. 직원을 보내면 `ERP_MODULE_OFF` 다 |
| 인사 켜짐, `member_id` 로 보냄(MCP 등) | 그 계정의 재직 직원을 찾아 직원으로 적는다 |
| 인사 켜짐, 직원 기록이 없는 계정(외주 등) | 구성원으로 적는다 |

모듈이 인사를 묻는 코드는 없다. 칸의 `module` 표시와 `erp.peek`, `erp.peek_by` 로 된다(M1). 인사를 켜도 지난 작업의 담당자는 그대로이고 원장에 남는다.

## 명령과 권한

| 무엇 | 누가 |
|---|---|
| 프로젝트 만들기, 고치기, 완료, 취소, 다시 열기, 지우기 | `project` |
| 작업 만들기, 고치기, 지우기 | `project`, 그 프로젝트의 `manager_id` |
| 작업 단계 옮기기 | 위 + 그 작업의 담당자 |
| 내 시간 기록, 고치기, 지우기 | 구성원 누구나 |
| 다른 사람의 시간 | `project`, 그 프로젝트의 `manager_id` |

역할 `member` 는 구성원 누구나이고 처리기가 사람을 가린다(`docs/modules/expense.md`).

**규칙.**

- 납기는 시작일 이상이다. 계획 시간은 0 이상이다.
- 프로젝트는 끝나지 않은 작업이 있으면 완료되지 않고 그 이름을 말한다. 취소하면 끝나지 않은 작업이 함께 취소되고 완료된 작업은 그대로다.
- 끝난 프로젝트와 작업은 고칠 수 없고 다시 연다.
- **시간은 0 초과 24 이하, 소수 둘째 자리까지.** 한 사람의 하루 합계도 24시간까지다(여러 작업에 걸쳐, 동시 요청에도). 날짜는 오늘까지다. 입사일 전과 퇴사일 뒤는 안 된다. 완료된 작업과 끝난 프로젝트에 늦게 기록하는 일은 흔하므로 받고, 취소된 것에는 받지 않는다.
- 시간이 있는 작업은 지우지 못하고, 작업이 있는 프로젝트도 지우지 못한다. 주문에서 온 것도 지우지 못한다. 취소한다.

## 서비스 주문에서

제품의 `creates_project`(프로젝트가 켜져 있을 때만 보인다)를 켠 서비스 제품이 주문에 있으면 프로젝트가 생긴다. 판매 코드는 그대로이고, 프로젝트가 `project.orders` 로 구독한다(`erp.pj_on_order`).

| 이벤트 | 하는 일 |
|---|---|
| `SalesOrderConfirmed` | 프로젝트 하나와 해당 줄마다 작업 하나. 이름은 주문 번호와 고객, 납기는 `commitment_date`, 계획 시간은 단위가 시간 분류일 때만 수량을 시간으로 바꾼 값 |
| `SalesOrderLineAdded` | 작업을 더한다 |
| `SalesOrderLineQtyChanged` | 끝나지 않은 작업의 계획 시간을 고친다 |
| `SalesOrderCancelled` | 시간이 없으면 프로젝트와 작업을 취소한다. **시간이 있으면 두고 `origin_cancelled` 를 표시한다.** 일한 시간은 주문이 되돌리지 못하므로 사람이 정한다 |
| 다시 `SalesOrderConfirmed` | 취소된 프로젝트와 작업을 되살린다. 둘로 만들지 않는다 |

문서 ID 는 주문과 줄에서 나오므로 두 번 전달되어도 같다. 제품의 표시는 **주문을 확정한 때의 값**을 읽는다(`erp.fold(제품, 그 시각)`). 나중에 켜거나 표시를 바꿔도 지난 주문의 답은 그대로다.

M6: 처음 켤 때 `orders_since` 를 고르면 그 날짜 이후의 주문을 읽고, 비우면 켠 뒤부터다.

## 되돌리기와 사가

되돌릴 수 없는 상태가 없다. 외부에 나간 것이 없고 전표도 없다. 그래서 `compensate` 를 정의하지 않고 사가는 언제나 `rollback` 이다. 주문 확정을 되돌리면 같은 correlation 인 프로젝트와 작업이 함께 돌아가고, 그 뒤에 사람이 한 일은 연쇄로 보여 주고 동의를 받는다. 시간 한 건은 혼자 돌아간다.

## 나중에 켜기, 끄기

- **M6.** 켜기 전의 작업과 시간은 원장에 없다. 서비스 주문은 고른 날짜 이후만 읽는다.
- **M7.** 끄면 메뉴와 명령이 막히고 구독이 멈춘다. 다시 켤 때 밀린 주문을 처리할지 고른다. 분석은 원장으로 답한다.

## 모델

원장만 읽는다(M8). 함수는 `sql/70_analytics.sql` 에 있다. 모든 이벤트가 같은 사실을 실으므로 가장 새 이벤트 하나로 지금 상태를 안다.

| 모델 | 근거 | 답 |
|---|---|---|
| `project_effort` 작업 소요 실측 | 계획과 기록이 모두 있는 완료 작업 20건 | `erp_project_effort`: 기록 ÷ 계획의 중앙값과 10~90 백분위, 프로젝트별 합계, 시작부터 완료까지 일수 중앙값. 진행 중이거나 계획이나 기록이 없는 작업은 세지 않는다 |
| `project_risk` 납기 지연 위험 | 같은 20건 | `erp_project_risk`: 아래 판단 |

**납기 지연 판단.** 남은 일 = 끝나지 않은 작업의 (계획 × 비율 − 이미 기록한 시간, 0 이상)의 합. 속도 = 최근 28일 그 프로젝트의 시간 ÷ 28. 완료까지 일수 = 남은 일 ÷ 속도.

| 판단 | 조건 |
|---|---|
| 납기 없음 | 납기가 없다 |
| 납기 지남 | 납기가 어제 이전이다. 근거와 상관없는 사실이다 |
| 맞출 것 | 남은 작업이 없거나, 90 백분위로도 남은 날 안이다 |
| 모름 | 실측이 20건 미만, 최근 28일에 기록이 없음, 계획 없는 작업이 있음 |
| 늦을 수 있음 | 중앙값으로는 맞추고 90 백분위로는 넘는다 |
| 늦을 것 | 중앙값으로도 넘는다 |

**임계값 20건.** 10과 90 백분위를 말하려면 양쪽에 두어 건은 있어야 한다는 판단이다. 실측이 아니다. 속도는 지난 4주의 평균이라 인원이 바뀌면 틀린다. 달력 일로 세고 주말과 휴일을 빼지 않는다. 화면이 근거 수와 함께 보여 준다.

**근태 대조.** `erp_time_vs_attendance(p_from, p_to)`. 근태 이벤트(`AttendanceEntered`, `AttendanceCorrected`, `AttendanceCheckedOut`)가 **없거나 볼 권한이 없으면** `available: false` 만 답하고 아무것도 대조하지 않는다. 있으면 직원과 날짜별로 기록한 시간이 근무 시간을 넘는 날(`over`)과 근태 기록이 없는 날(`no_attendance`)을 보여 준다. 근태 스트림은 `hr`, `admin` 만 읽으므로 그들에게만 나온다. 구성원으로 적힌 시간은 대조하지 않는다. 모델이 아니라 사실 대조다.

## 화면

메타데이터 화면이다. 작업 칸반은 CRM 과 같은 공통 칸반이다(`views.moves`). 전용 부분: `TaskTimePanel`(작업의 시간과 빠른 기록), `ProjectPanel`(프로젝트의 작업과 합계), `AnalysisView`(실측, 지연, 근태). 간트 차트는 만들지 않았다.
