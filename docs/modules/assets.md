# 고정자산 (`sql/66_assets.sql`)

모듈 `assets`, 정렬 55. 자산을 등록하고 감가상각을 실행하고 처분한다. 회계 없이도 동작한다. 금액과 계정을 모두 여기서 정해 이벤트에 싣고, 회계는 그 이벤트를 받아 전표로 적을 뿐 상각을 계산하지 않는다([events.md](events.md)). 그래서 회계를 나중에 켜도 같은 전표가 나오고, 규칙을 고쳐도 지난 해는 움직이지 않는다.

**회계·세무 전문가의 검수 전이다.** 화면마다 그렇게 적혀 있다. 아래 근거는 2026-11-04 에 원문을 직접 읽고 대조했다.

## 어느 쪽 기준인가

자산마다 `basis` 를 고른다. **세법과 회계 기준이 갈리는 곳은 이 값으로 갈린다.**

| | `tax` 세법 상각범위액 (기본) | `book` 회사가 정한 잔존가치 |
|---|---|---|
| 근거 | 법인세법 시행령 제26조, 제28조 | 일반기업회계기준 제10장 10.32~10.40 |
| 상각률 | 시행규칙 별표 4. 내용연수로 정해지고 직접 못 적는다 | 정액법은 1÷내용연수, 정률법은 별표 4. 직접 적을 수 있다 |
| 정액법 금액 | 취득가액 × 상각률 | (취득가액 − 잔존가치) × 상각률 |
| 끝나는 때 | 한도를 넘지 않게 남은 금액이 다 찰 때. 0.333 처럼 끊긴 상각률이면 37번째 달까지 간다 | 내용연수의 마지막 달에 잔존가치까지 맞춘다 |
| 상각 뒤 남는 금액 | 취득가액의 5% 와 1,000원 중 적은 금액 | 적은 잔존가치 |
| 건물·구축물의 정률법 | 거부 | 허용 |

세법의 상각범위액은 **손금으로 인정받는 한도**다. 회사가 장부에 얼마를 비용으로 잡을지와는 다른 문제이고, 한도와 장부의 차이를 고치는 세무 조정(시부인, 감가상각비조정명세서)은 **이 앱이 하지 않는다**. 기본값을 세법으로 둔 것은 작은 회사가 대개 한도까지 잡는다는 판단이고, 이 판단은 확인하지 않았다.

| 건축물 외 유형자산은 정률 또는 정액. 신고하지 않으면 정률 | 제26조 제1항 제2호, 제4항 제2호 | 고를 수 있다. 신고 여부는 앱이 모른다 |

### 근거가 없어 우리가 정한 것

법령과 기준을 찾았지만 정한 곳을 찾지 못했다. **전문가 검수 때 먼저 볼 곳이다.**

- **처분 달은 상각하지 않는다.** 시행령 제26조 제9항은 취득만 말한다. 취득 달을 한 달로 쳤으니 처분 달까지 치면 하루도 안 쓴 달이 둘이 되어, 처분 달을 뺐다. 그 전 달까지 아직 상각하지 않은 금액은 처분과 함께 잡는다.
- **달 나누기.** 법령은 사업연도 단위다. 한 해의 금액은 정해 두고, 달은 `연 금액 × 경과 월수 ÷ 12` 를 반올림한 누계의 차이로 잡는다. 그해 마지막 달이 끝자리를 받는다. 정률법의 마지막 해는 금액을 그해 달수로 고르게 나눈다.
- **회사 기준의 월할.** 일반기업회계기준은 월할을 말하지 않는다. 세법과 같은 월 세기를 쓴다.
- **회사 기준 정률법의 끝.** 내용연수 마지막 달에 잔존가치까지 맞춘다.
- **사업연도는 달력 연도다.** 회사 정보에 사업연도 칸이 없다. 다른 사업연도의 회사는 정률법의 해 나눔이 어긋난다. 화면에 적었다.

### 확인하지 못한 것

| 무엇 | 왜 |
|---|---|
| 시행규칙 별표 6 업종별 내용연수 | 파일 위치는 찾았으나 읽지 않았다. 기계장치의 범위를 검사하지 않는다 |
| 중소기업회계기준(상법 시행령 제15조 제3호의 고시), K-IFRS | 보지 않았다. 유형자산 규칙이 일반기업회계기준과 다를 수 있다 |
| 국세청 안내 자료 | 보지 않았다. 법령 원문으로 대신했다 |
| 자산별 신고 여부 | 앱이 알 수 없다. 내용연수·상각 방법을 관할 세무서에 신고했는지는 회사가 챙긴다 |

### 다루지 않는 것

자본적 지출, 재평가, 손상, 즉시상각, 내용연수 변경, 상각 방법 변경, 업무용승용차, 중고자산 수정내용연수, 세무 조정과 조정명세서, 무형자산, 생산량비례법. 등록한 자산의 값은 고칠 수 없고 틀리면 등록을 되돌린다.

## `asset`

`number(FA/2026/00001), name, kind, acquisition_date, in_service_date, cost, life_years, method, basis, residual_value, rate, opening_accumulated, opening_through, asset_account_id, accumulated_account_id, expense_account_id, counter_account_id, memo, state, accumulated, book_value, end_value, rate_used, last_month, last_plan_month, plan, disposed_date, disposal_kind, proceeds, gain_loss`

| 상태 | 뜻 |
|---|---|
| `draft` 초안 | 고칠 수 있고 지울 수 있다 |
| `active` 상각 중 | 등록됐다. 이름과 메모만 고친다 |
| `fully` 상각 끝남 | 남는 금액까지 상각했다. 처분할 수 있다 |
| `disposed` 처분 | 매각 또는 폐기 |

| 명령 | 뜻 |
|---|---|
| `create{..., register}` | 초안. `register: true` 면 바로 등록 |
| `update` | 초안은 전부, 등록 뒤에는 `name, memo` 만. 그 밖은 `ERP_POSTED`. 화면은 등록 뒤 읽기 전용이다 |
| `register` | 규칙을 확인하고 계획을 정해 `AssetRegistered` |
| `delete` | 초안만 |
| `dispose{date, kind, proceeds, proceeds_account_id}` | `kind` 는 `sale`, `scrap`. 폐기에 대금이 있으면 `ERP_INVALID`. 처분일이 속한 달까지 이미 상각했으면 `ERP_STATE` |

계획 `plan` 은 해마다 한 줄 `{year, first, last, months, annual, amount}` 이고 등록 때 정해 이벤트에 실린다. 달까지 상각한 금액은 `erp.asset_cum_at(plan, 달)` 이다. 분석이 같은 계산을 `web/src/lib/forecast/assets.ts` 에 갖고 있고 시험이 둘을 맞춘다.

계정을 적지 않으면 자산 종류의 시드 계정이고 감가상각비는 판관비(818)다. 회계가 꺼져 있으면 계정 칸이 보이지 않고 받지 않지만, 정해진 시드 계정이 이벤트에 실려서 나중에 켠 회계가 같은 전표를 만든다.

취득 대금 계정 `counter_account_id` 를 적으면 등록할 때 차변 자산 / 대변 그 계정의 전표가 생긴다. 매입 청구서나 기초 잔액으로 이미 장부에 넣은 자산은 비운다. 이미 쓰던 자산(`opening_accumulated` 가 있는)에는 적을 수 없다.

## `depreciation_run`

`create{through}` 하나뿐이다. 그 달의 아무 날이나 받아 말일로 바꾼다. 상각 중인 자산마다 `누계 목표 − 지금 누계` 를 잡아 `DepreciationPosted` 를 내고, 자산마다 `AssetDepreciated` 로 누계를 올린다. 전표 날짜는 그 말일이다. 달을 빠뜨렸으면 다음 실행이 함께 잡고, 연말 한 번의 실행은 열두 번의 월 실행과 같은 데서 끝난다. 잡을 금액이 없으면 `ERP_NOTHING` 이다.

## 되돌리기와 잠금

- 되돌리기는 원장의 되돌리기(`erp_rollback_*`) 그대로다. 관리자만, 사유 필수. 실행을 되돌리면 자산 누계와 전표가 함께 돌아가고, 번호는 재사용하지 않는다. 앞선 실행을 되돌리면 그 뒤의 실행이 연쇄로 함께 간다(같은 자산 스트림을 건드리므로). 처분은 외부에 알려진 일이라 경고한다.
- 실행과 처분, 대금 전표가 있는 등록은 날짜가 잠금일 안이면 `ERP_LOCKED` 다. 잠금 안의 일은 되돌리기도 막힌다(`lock_fn`). 회계가 꺼져 있어도 같다.
- 잠금을 올린 뒤의 달로 실행하면 그 전 달 금액까지 열린 달에 잡힌다. 정정은 열린 기간으로 간다는 회계 모듈의 원칙과 같다.

## 부가세

자산 매각의 부가세는 처분이 다루지 않는다. 세금계산서를 내는 매각은 청구서를 만들어 줄 계정을 `미수금` 으로 적고, 처분의 대금 계정도 `미수금` 으로 고른다. 미수금이 서로 지워지고 부가세는 청구서로 신고 자료에 들어간다.

## 모델 `depreciation_outlook` (M8)

| 상태 | 언제 | 화면 |
|---|---|---|
| 잠김 | 고정자산을 켠 적이 없다 | 모듈 안내 |
| 근거 부족 | 첫 취득부터 지금까지 12개월이 안 된다 | 지금 있는 자산의 금액을 범위로만 |
| 사용 가능 | 12개월 이상 | 월별 금액과 80% 구간, 이 기간에 상각이 끝나는 자산 |

원장의 `AssetRegistered`, `AssetDisposed` 만 읽는다(`erp_asset_history`). 모듈을 꺼도 이력으로 답한다. 지금 있는 자산은 계획을 더한 값이라 불확실하지 않다. 불확실한 것은 앞으로 살 자산뿐이어서, 달마다 새로 산 자산이 더한 월 상각액을 무작위로 다시 뽑아 쌓는다. 이력 자체도 판마다 다시 뽑는다.

임계값 12개월은 정답을 아는 가상 회사로 쟀다. 회사 2000곳, 앞으로 12개월, 80% 구간에 실제 값이 들어간 비율은 이력 3개월 53.0%, 6개월 69.5%, 9개월 73.7%, **12개월 77.1%**, 18개월 78.0%, 24개월 79.0%, 36개월 79.7% 다. 분석 모델의 기준(구간 포함 70% 이상)으로는 9개월이지만 한 해의 사는 주기가 들어가도록 12개월로 잡았다. 처음에는 이력을 고정해 12개월이 60% 로 나왔고, 이력도 판마다 다시 뽑도록 고친 뒤 고칠 때 쓰지 않은 시드로 다시 쟀다. 가상 회사는 사는 빈도가 일정하고 자산이 모두 5년 정액이므로 **실제 회사에서는 더 나쁠 수 있다.** 처분과 정률 자산의 체감은 앞으로 살 자산에 넣지 않았다. 회귀 시험은 400곳으로 70~95% 안인지만 본다(`test/assets.test.mjs`).

교체 시점은 계산하지 않는다. 상각이 끝나는 자산을 보여 줄 뿐이고 상각이 끝났다고 바꿔야 하는 것은 아니다.
