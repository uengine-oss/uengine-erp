# 설비 보전 (`sql/67h_maintenance.sql`)

모듈 `maintenance`(sort 72). 설비를 등록하고, 고장 수리와 예방 점검을 요청부터 완료까지 적고, 예방 보전 계획이 예정일 며칠 전에 요청을 만든다. 다른 어떤 모듈도 필요 없고 아무 이벤트도 듣지 않는다. 제조가 켜져 있으면 설비를 작업장에 두고, 그 설비의 작업이 시작되면 제조가 `MaintenanceStarted` 를 듣고 작업장을 「보전 중」으로 적는다. **설비 보전은 제조를 모르고, 제조는 설비 보전이 없어도 동작한다.** 시나리오는 S25 다.

고장 간격(MTBF), 수리 시간(MTTR), 다음 고장 예상, 달마다 멈춘 시간은 어디에도 저장하지 않는다. 물을 때 원장의 요청 이벤트로 셈한다(`sql/70_analytics.sql`). 그래서 지난 어느 시점으로도 같은 답이 나오고, 모듈을 꺼도 답한다.

**범위.** 다음은 하지 않는다.

| 안 하는 것 | 이유와 대신할 길 |
|---|---|
| 보전 팀, 팀별 칸반 | 담당 기술자 한 사람과 분류의 기본 담당으로 충분하다. 목록을 기술자별로 묶어 본다 |
| 단계를 회사가 바꾸기 | 고장 간격과 수리 시간은 신규 → 진행 중 → 완료가 같은 뜻이어야 셀 수 있다 |
| 메일로 요청 받기, 활동 알림 | 서버가 필요하다. 요청은 화면, MCP, REST 로 만든다 |
| 예비 부품 출고, 외주 수리비 | 재고나 구매와 엮이는 일이다. 부품은 재고의 폐기나 출고 전표로, 비용은 구매나 경비로 적는다 |
| 사용량(가동 시간, 타수) 기준 예방 보전 | 계측값을 받는 길이 없다. 날짜 기준만 한다 |
| 고객 제품 수리(수리 주문) | 다른 업무다. 이 모듈은 회사 자신의 설비만 다룬다 |
| 제조 일정에 보전을 반영하기 | 제조에 작업장 일정 계획이 없다. 작업장의 「보전 중」 표시까지만 한다 |

## 유형

| 유형 | 칸 |
|---|---|
| `equipment_category` 설비 분류 | `name, technician_id, note`. 기초데이터처럼 다룬다(`catalog_master`) |
| `equipment` 설비 | `code(EQ00001), name, serial_no(유일), category_id, work_center_id(제조가 켜졌을 때), location, technician_id, vendor_id, model, warranty_end, cost, in_service_on, scrapped_on, note, state(active/scrapped)` |
| `maintenance_request` 보전 요청 | `number(MR00001), name, kind(corrective/preventive), equipment_id, equipment_name, category_id, work_center_id, priority(low/normal/high/urgent), technician_id, scheduled_date, failed_at, requested_on, plan_id, due_date, planned_hours, started_at, finished_at, duration_hours, downtime_hours, cancel_reason, note, state` |
| `maintenance_plan` 예방 보전 계획 | `code(PM00001), name, equipment_id, schedule(interval/dates), every_days, start_on, dates[], lead_days, technician_id, duration_hours, note, next_due, last_due, last_request_id` |

설비, 계획, 분류는 이름으로 부른다(`code` 는 번호 칸이 아니라 목록에 보이는 칸이다). 요청은 문서라 번호로 부른다.

단계: `new`(신규) → `in_progress`(진행 중) → `done`(완료). 고칠 수 없으면 `scrapped`(폐기로 끝남), 필요 없어지면 `cancelled`(취소).

## 명령

쓰기는 `maintenance` 역할과 관리자다. 읽기는 모든 구성원이다. 작업장은 제조의 것이라 `mrp` 역할이 만든다.

| 명령 | 뜻 |
|---|---|
| 설비 `create`, `update` | 담당을 비우면 분류의 기본 담당이다. 취득가는 0 이상. 사용 시작일은 비우면 오늘이고, 고장 간격을 이날부터 센다 |
| 설비 `scrap{scrapped_on}` | 폐기. 이 설비의 열린 요청은 취소되고(`cancel_reason: 설비 폐기`) 계획은 보관된다. 폐기한 설비는 메모만 고친다 |
| 설비 `delete` | 요청이나 계획이 있으면 `ERP_IN_USE`. 기록이 고장 간격 계산에 쓰이므로 보관한다 |
| 요청 `create` | 고장 수리는 고장 시각을 비우면 지금이고 지금보다 늦을 수 없다. 예방 점검에는 고장 시각이 없다. 예정일을 비우면 고장 수리는 고장 난 날, 예방 점검은 오늘이다 |
| 요청 `update` | 신규·진행 중일 때. 진행 중이면 설비와 유형은 못 바꾼다. 끝난 요청은 메모만 |
| `start{started_at}` | 신규 → 진행 중. 비우면 지금. 고장 시각보다 빠르거나 지금보다 늦을 수 없다. 이때의 작업장을 이벤트에 싣는다 |
| `done{finished_at, duration_hours, downtime_hours}` | 진행 중 → 완료. 작업 시간은 비우면 시작부터 끝까지, 정지 시간은 비우면 고장 수리는 고장부터, 예방 점검은 시작부터 끝까지다. 설비가 계속 돌았으면 0 을 적는다. 둘 다 0 이상 |
| `scrap{scrapped_on}` | 신규·진행 중 → 폐기로 끝남. 설비도 폐기한다(위와 같다) |
| `cancel{cancel_reason}` | 신규·진행 중 → 취소. 고장이 아니었으면 이것으로 끝낸다. 고장 수로 세지 않는다 |
| 요청 `delete` | 신규·취소만 |
| 계획 `create`, `update` | 이름과 설비는 필수. 며칠마다는 1~3660 의 정수, 며칠 전에는 0~365. 날짜 목록은 하나 이상이고 정렬해 중복을 지운다. 요청을 만든 계획은 설비를 바꿀 수 없다 |
| 계획 `run` | 지금 확인(아래). 화면의 「더 보기 → 지금 확인」 |
| 계획 `archive`, `unarchive`, `delete` | 요청을 만든 계획은 지울 수 없고 보관한다 |

## 예방 보전 계획

예정일은 「첫 예정일 + 며칠마다 × k」 이거나 적어 둔 날짜들이다. **창**은 오늘부터 「며칠 전에 만들지」 일 뒤까지다.

1. 마지막으로 만든 예정일보다 뒤이고 창 안에 드는 예정일 중 **가장 늦은 하나**의 요청을 만든다. 요청의 제목과 메모, 예상 작업 시간, 담당은 계획에서 온다.
2. 그 사이에 지나간 예정일은 만들지 않고 센다(`MaintenancePlanScheduled.skipped`). 몇 달 동안 아무도 확인하지 않았다고 밀린 점검이 한꺼번에 생기지 않는다. 처음 만든 계획의 첫 예정일이 과거이면 그 앞의 날짜는 세지 않는다.
3. **같은 예정일로 두 번 만들지 않는다.** 요청 ID 가 `계획 + 예정일` 에서 나오고, 원장에 그 스트림이 있으면 만들지 않는다. 사람이 지운 요청도, 되돌린 요청도 다시 만들지 않는다. 되돌리면 계획도 함께 돌아가므로 다음 예정일은 창에 들어올 때 만든다.
4. 다음 예정일(`next_due`)은 만들거나 고칠 때와 요청을 만들 때 다시 적는다. 날이 지나도 저절로 바뀌지 않는다.

**돌리는 곳은 넷이고 결과는 같다.** pg_cron 이 매일 01:20(`erp-maintenance-plans`), 앱의 재촉(`erp_bus_tick`)이 한 시간에 한 번(`erp.periodic_register`), 사람이 「설비 신뢰도」 화면의 「예방 보전 계획 지금 확인」(`erp_maintenance_run`, `maintenance` 역할), 계획의 「지금 확인」. 계획마다 따로 correlation 이고 하나가 실패해도 나머지는 돈다. 시험은 `erp.clock` 으로 날을 옮겨 `erp.mnt_plans_due()` 를 부른다. 설비가 폐기되거나 보관되면 그 계획은 쉰다. 모듈이 꺼져 있으면 아무것도 하지 않는다.

## 고장 간격과 수리 시간

원장의 요청 이벤트 중 가장 새 것으로 셈한다. 되돌린 일과 지운 요청은 빠진다. 함수는 `erp_maintenance_reliability(p_equipment_id, p_as_of)`.

| 값 | 셈 |
|---|---|
| 고장 | 고장 수리 요청 중 취소되지 않은 것(신규, 진행 중, 완료, 폐기로 끝남). 오보는 취소로 끝내면 세지 않는다 |
| 멈춘 시간 | 끝난 요청은 `끝난 시각 − 정지 시간` 부터 끝난 시각까지, 열린 고장은 고장 시각부터 지금까지. 예방 점검도 넣는다. **겹친 시간은 한 번만** 센다(`range_agg`). 사용 시작일 앞과 폐기일 뒤는 자른다 |
| 돈 시간 | 사용 시작일부터 지금(또는 폐기일)까지 − 멈춘 시간 |
| 고장 간격(MTBF) | 돈 시간 ÷ 고장 |
| 수리 시간(MTTR) | 완료한 고장 수리의 정지 시간 평균. 고장부터 다시 돌기까지다 |
| 작업 시간 | 완료한 고장 수리의 작업 시간 평균 |
| 가동률 | 돈 시간 ÷ (돈 시간 + 멈춘 시간) |
| 다음 고장 예상 | 마지막 고장을 고친 시각 + 고장 간격. **고장이 3번 이상이고** 지금 고치는 중이 아닐 때만 |
| 달마다 멈춘 시간 | 멈춘 구간을 회사 시간대의 달로 나눈다. 달을 넘긴 정지는 나뉜다 |

**3번은 판단이다.** 한 번의 고장으로는 간격이 하나도 없고, 두 번은 우연과 구별되지 않는다. 고장 간격이 지수 분포라고 보면 3번일 때도 구간이 넓지만, 작은 공장이 1년에 겪는 고장 수를 생각해 이만큼에서 말하기 시작한다. 실제 회사에서 다시 재야 한다. 모델 카드 `maintenance_reliability`(고장 간격·다음 고장)도 회사 전체의 완료한 고장 수리 3건에서 「사용 가능」이 된다.

참고 제품의 계산과 다르다. 그쪽은 첫 사용일부터 마지막 고장까지의 날 수를 고장 수로 나누고(멈춘 시간을 빼지 않고 날 단위로 자른다), 수리 시간도 날 단위다. 여기는 시간 단위이고 멈춘 시간을 뺀다. 고장이 하루 안에 고쳐지는 작은 공장에서 날 단위는 0 이 되기 때문이다.

## 제조와 만나는 곳

| 설비 보전이 내는 것 | 제조가 하는 일 |
|---|---|
| `MaintenanceStarted`(`work_center_id` 가 있을 때) | 그 작업장의 `maintenance_open` 에 요청을 더하고 `maintenance_state` 를 `maintenance`(보전 중), `maintenance_note` 를 「설비 이름 번호」로 적는다 |
| `MaintenanceDone`, `MaintenanceScrapped`, `MaintenanceCancelled` | 그 요청을 들고 있던 작업장에서 뺀다. 남은 것이 없으면 `available`(가동) |

- 구독은 `mrp.maintenance`(`erp.mrp_on_maintenance`), 이벤트는 `WorkCenterMaintenanceChanged` 다. 두 번 들어도 결과가 같다.
- 한 작업장에 설비가 여럿이면 모두 끝나야 가동으로 돌아온다. 고장 수리와 예방 점검을 가리지 않는다. 진행 중인 일이면 설비가 멈춘 것으로 본다.
- 작업장의 세 칸은 설비 보전이 켜져 있을 때만 보인다(`"module": "maintenance"`). 설비의 작업장 칸은 제조가 켜져 있을 때만 보이고 받는다.
- 제조 구독이 멈춰도 수리는 진행된다. 고치면 들은 순서대로 따라잡는다. 제조가 꺼져 있으면 아무도 듣지 않고 멈춘 것도 없다.
- 시작을 되돌리면 제조가 적은 것도 같은 correlation 이라 함께 돌아간다.

## 되돌리기와 사가

밖으로 나간 것이 없으므로 `compensate` 를 정의하지 않았고 사가는 언제나 `rollback` 이다. 모든 유형이 되돌릴 수 있다. 계획이 만든 요청을 되돌리면 계획의 마지막 예정일도 함께 돌아가고, 같은 날짜로 다시 만들지는 않는다(위 3).

## 나중에 켜기, 끄기

- **M6.** 켜기 전의 고장과 수리는 원장에 없다. 지난 고장을 적으려면 요청을 만들 때 고장 시각을, 시작과 완료에 그때의 시각을 적는다. 사용 시작일을 그 앞으로 적으면 고장 간격이 거기서부터 센다.
- **M7.** 끄면 메뉴와 명령이 막히고 계획이 돌지 않는다. 설비, 요청, 이력, 고장 간격은 남는다. 작업장의 「보전 중」은 그대로 남지만 칸이 보이지 않는다.

## 결정

- **작업장은 제조의 것이다.** 제조에 작업장이 없어 이번에 제조 모듈에 `work_center`(이름, 코드, 메모)를 더했다. 설비 보전이 작업장을 만들면 제조가 설비 보전을 알아야 하고, 작업장이 설비 보전에 있으면 제조를 끈 회사의 설비에 쓸모없는 칸이 생긴다. 판매가 재고의 납품 상태를 자기 주문에 적는 방식 그대로다.
- **설비의 상태는 사용 중과 폐기 둘이다.** 「보전 중」은 열린 요청에서 나오므로 설비 스트림에 따로 쓰지 않는다. 설비 목록은 진행 중인 요청이 있는 행에 「보전 중」 표시를 붙인다(`marks`).
- **설비, 계획, 기준은 `code`, 문서는 `number`.** 레코드의 표시 이름은 `number` 가 있으면 그것이다. 설비를 고를 때 「EQ00001」이 아니라 「프레스 1호기」로 보이게 하려고 번호 칸 이름을 `code` 로 했다.
- **예방 보전은 닫을 때가 아니라 날짜로 만든다.** 닫을 때 다음 것을 만드는 방식은 닫지 않으면 다음이 오지 않고, 다시 열고 닫으면 둘이 생긴다(참고 제품에서 관찰). 여기는 날짜가 오면 만들고 같은 날짜는 한 번이다.
- **정지 시간은 사람이 고칠 수 있다.** 기본값은 고장부터 끝까지지만, 고장 났어도 설비가 돌았거나 밤사이 멈춘 시간을 빼야 할 때 적는다. 원장에는 적은 값과 시각이 모두 남는다.

## 화면

메타데이터 화면을 쓴다. 보전 요청 목록은 예정일 달력(`views.date`), 단계별 칸반, 설비·기술자별 묶음을 가진다. 칸반 단추는 묻는 것이 없는 단계 이동만 하므로, 시작과 완료는 문서에서 한다. 전용 화면은 둘이다. `EquipmentPanel`: 설비 폼 아래에 이 설비의 고장, 고장 간격, 수리 시간, 멈춘 시간, 다음 고장 예상과 요청 목록, 「고장 신고」 단추. `ReliabilityView`(`/maintenance/reliability`, 「설비 신뢰도」): 설비별 표와 달마다 멈춘 시간, 「예방 보전 계획 지금 확인」.

## REST 와 MCP

카탈로그에서 자동으로 나온다. `erp_api_equipment`, `erp_api_maintenance_request`, `erp_api_maintenance_plan`, `erp_api_equipment_category` 가 생기고 MCP 도구의 `type` 에 넷이 더해진다. 단계 이동은 `erp_update` 의 `values.state`(`in_progress`, `done` 등)이고 완료 값은 같은 `values` 에 `downtime_hours` 처럼 싣는다.
