# uEngine ERP 아키텍처

서버 없이 이벤트 소싱 ERP 를 돌리는 구조다. 앱은 GitHub Pages 의 정적 파일이고, 데이터와 업무 규칙은 사용자 소유 Supabase 프로젝트의 Postgres 안에 있다. 회사는 판매 하나로 시작해 모듈을 하나씩 켠다. 흐름은 [scenario.md](scenario.md) 가 원본이다.

## 1. 전체 구조

```
 브라우저 (Vue 3, GitHub Pages)      외부 시스템 (REST)      에이전트 (MCP, Process GPT 등)
   화면과 예측 계산, 업무 규칙 없음     표준 CRUD               도구 4개 + 리소스
        │                                 │                        │
        │        HTTPS + 로그인 JWT 또는 연동 키                    │
        ▼                                 ▼                        ▼
 ┌─ Supabase (사용자 소유) ────────────────────────────────────────────────────┐
 │  GoTrue 로그인 · PostgREST · Realtime · pg_cron                              │
 │  ┌─ public (공개 API) ───────────────────────────────────────────────────┐   │
 │  │  erp_command     업무 쓰기의 입구                                     │   │
 │  │  erp_api_<유형>  카탈로그에서 생성한 REST 자원 → erp_command           │   │
 │  │  erp_mcp         MCP JSON-RPC → erp_command                           │   │
 │  │  erp_records · erp_events   읽기 전용 뷰 (RLS 적용)                   │   │
 │  │  erp_as_of · erp_records_at · erp_rollback_* · erp_models · 시계열     │   │
 │  └───────────────────────────────────────────────────────────────────────┘   │
 │  ┌─ erp (비공개, API 로 직접 접근 불가) ─────────────────────────────────┐   │
 │  │  events        추가만 가능한 원장 ← 유일한 진실                       │   │
 │  │  records       현재 상태 (버리고 다시 만들 수 있음)                   │   │
 │  │  catalog       유형 메타데이터 → 화면·REST·MCP 가 함께 사용           │   │
 │  │  modules       어떤 모듈이 켜져 있는가                                │   │
 │  │  subscriptions 구독자별 커서                                          │   │

 │  │  판매 ──┐                                    ┌── 재고 (quants)        │   │

 │  │  청구 ──┘   모듈끼리 함수를 부르지 않는다    └── 플러그인             │   │

 └──────────────────────────────────────────────────────────────────────────────┘
```

### 백엔드는 어디에 있는가

**Java 도, 별도 서버 프로세스도 없다.** 백엔드는 Postgres 안의 함수(PL/pgSQL)다. 브라우저의 HTTP 요청을 PostgREST 가 함수 호출로 바꾼다. Supabase 의 Edge Function 도 쓰지 않는다. 비즈니스 로직은 프런트엔드에 없으므로 앱을 배포해도 규칙은 바뀌지 않는다.

| Spring | 여기 |
|---|---|
| Controller + `@Transactional` | `public.erp_command` |
| Service·Aggregate | `erp.h_<유형>` |
| Security + 게이트웨이 | JWT + 역할 확인 + RLS |
| Kafka 토픽 | 원장 |
| 컨슈머 그룹 | `erp.subscriptions` 의 구독자별 커서 |
| `read_model` | `erp.records`, 파생 표 |

### 커맨드 한 번이 트랜잭션 하나다

1. 구성원·역할·모듈 켜짐을 확인한다(JWT 의 사용자 기준, 요청 본문의 값은 믿지 않음).
2. 재시도 키가 전에 쓰인 것이면 처음 결과를 돌려준다.
3. 애그리거트 행을 잠그고 버전을 확인한다.
4. 처리기가 상태를 읽고 규칙을 확인한 뒤 이벤트를 발행한다.
5. `records` 와 파생 합계(`effects`)를 갱신한다.
6. 어디서든 실패하면 위 전부가 사라진다.

판단(커맨드 → 이벤트)은 처리기가, 반영(이벤트 → 상태)은 규칙 없는 리듀서 `erp.apply` 하나가 한다. 이벤트에 판단 결과가 실리므로 규칙을 고쳐도 과거는 변하지 않는다. 대신 계산 버그를 나중에 고쳐도 과거 값은 저절로 재계산되지 않아 정정 이벤트를 써야 한다.

### 모듈 사이는 구독이다

주문 확정이라는 트랜잭션은 판매 문서만 바꾸고 끝난다. 재고 모듈은 그 이벤트를 **다른 트랜잭션에서** 읽어 출고 전표를 만든다. 판매는 재고가 있는지조차 모른다.

```
발행: erp_command → 원장에 이벤트 (커밋)
전달: 앱의 재촉(명령 직후) 또는 pg_cron(5초) → 구독자별 커서부터 읽기 → 처리기 실행 → 커서 전진
```

| 성질 | 어떻게 |
|---|---|
| 장애 격리 | 이벤트마다 부분 트랜잭션. 처리기가 실패하면 그 구독자만 그 이벤트에서 멈추고 관리자 화면에 보인다. 재시도하거나 사유를 남기고 건너뛴다 |
| 누락 없음 | 커서는 `(txid, seq)` 이고 가장 오래 열린 트랜잭션 앞까지만 읽는다. `seq` 만 쓰면 느린 거래를 놓치는 것을 실측했다 |
| 중복 처리 | 처리 결과와 커서가 한 트랜잭션이라 DB 안의 일은 한 번만 일어난다. 재설치·재시도에 대비해 처리기는 멱등으로 만든다 |
| 나중에 켜기 | 커서를 현재로 두거나, 고른 날짜나 처음으로 되돌려 과거를 읽는다 |
| 인과 | 구독자의 이벤트는 원본의 correlation 과 cause, 행위자를 이어받는다 |

**대가.** MES 처럼 모듈 사이는 최종 일관성이다. 주문 확정 직후 출고 전표가 생기기까지 짧은 지연이 있고, 재고 모듈이 멈추면 그동안 출고 전표가 없다. 트랜잭션은 한 모듈 안에서만 묶인다. 모듈 안의 연쇄는 `react` 훅으로 여전히 같은 트랜잭션이다.

MES 와의 차이: MES 는 서비스마다 DB 가 따로고 Kafka 로 잇는다. 여기는 DB 가 하나라 브로커가 필요 없고 장애는 격리되지만, 자원을 함께 쓰므로 모듈별로 따로 배포하거나 확장할 수 없다. 처리기는 같은 DB 권한으로 돌기 때문에 플러그인의 권한 격리는 코드 검토에 의존한다.

## 2. 이벤트 소싱이 주는 것

| 시나리오 | 동작 |
|---|---|
| 문서 시간 여행 | 슬라이더로 과거 시점의 문서를 읽기 전용으로 본다 |
| 회사 시간 여행 | 그 시점의 모든 목록, 재고, 미수금을 본다 |
| 실패 롤백 | 처리 중 오류 시 이벤트·상태·문서 번호 전부 취소 |
| 작업 되돌리기 | 잘못 확정한 주문을 출고 전표·재고 예약까지 모듈을 넘어 함께 되돌림 |
| 문서·회사 되돌리기 | 특정 버전이나 시점으로 되돌림(미리보기 후 적용) |
| 되돌리기 취소 | 되돌린 것을 다시 되돌림 |
| 재구축 | 파생 표를 지우고 원장에서 다시 만들어 동일함을 확인 |
| 나중에 켠 회계 | 청구 이벤트로 과거 전표를 다시 만든다 |
| 예측·what-if | 시점별 재고로 품절을 가려내 수요를 복원하고, 정책을 바꿔 재생한다 |

## 3. 되돌리기의 뜻

**이벤트를 지우지 않는다.** 되돌리기는 스트림마다 `Reverted` 이벤트를 하나 새로 쓴다. 원장에 "그때 정말 확정됐었다"와 "누가 왜 되돌렸다"가 모두 남고, 되돌리기 자체도 되돌릴 수 있다.

| 상황 | 동작 |
|---|---|
| 뒤에 다른 작업이 이어짐 | 미리보기에 연쇄 범위를 보여 주고, 동의 없이는 실행 안 함 |
| 구독자가 아직 처리하지 않음 | 되돌려진 이벤트는 전달하지 않고 건너뜀 |
| 합계가 깨짐 | 차단. 문서 간 인과가 없어도 재고가 음수면 막는다 |
| 게시된 청구서 | 차단. 대변 메모로 정정하도록 안내 |
| 고객에게 이미 보낸 견적 | 경고. 시스템만 되돌아가니 상대에게 따로 알려야 한다 |
| 미리보기 후 데이터 변경 | 충돌로 거부, 다시 미리보기 |
| 구성원·회사 설정·모듈 | 되돌리기 대상에서 제외 |
| 권한 | 관리자만, 사유 필수 |

문서 번호는 재사용하지 않는다. 되돌린 주문의 번호는 비어 있게 된다.

**두 시간축.** `occurred_at` 은 시스템이 알게 된 시각이고, 전표의 `invoice_date` 같은 업무 일자는 별도다.

## 4. 보안

공개 키는 노출되어도 되는 값이고, 경계는 JWT 와 RLS 다.

| 공격 | 방어 |
|---|---|
| 공개 키만으로 읽기·쓰기 | 뷰와 함수에 권한 없음. MCP 입구는 열려 있으나 키나 토큰 없이는 401 |
| 비구성원 로그인 | RLS 가 0건, 명령 거부 |
| 이벤트 위조 | 표·`emit`·처리기에 실행 권한 없음 |
| 행위자 위조 | 권한은 서명된 JWT 에서만 읽음 |
| 자가 가입 | `auth.users` 트리거로 차단 |
| 동시 요청으로 재고 초과 | 애그리거트 잠금 |
| 역할 밖 데이터 읽기 | 유형별 `read_roles`. 소유자 권한으로 도는 MCP 읽기도 직접 확인 |
| 넓은 필터로 대량 변경 | REST 자원은 한 요청에 한 건 |
| 재시도로 인한 중복 | 사람별 재시도 키 |
| 연동 키 유출 | 해시만 저장, 구성원 권한을 넘지 못함, 폐기 가능 |
| 앱·DB 버전 차이 | 모르는 필드 거부, 앱 최소 버전 확인 |

남는 위험: XSS 로 세션 탈취, 배포된 앱 코드의 공급망, 직원의 대량 조회(읽기 감사 없음), 호출 쏟아붓기(요청 제한 없음), 플러그인의 권한, 고객이 DB 소유자라 함수를 직접 고칠 수 있음, 클라우드 미검증.

## 5. 측정

이벤트 200,000건(문서 20,000개), 로컬 8코어 Postgres 기준. **무료 플랜은 이보다 느리다. 클라우드 측정은 아직 안 했다.**

| 작업 | 시간 |
|---|---|
| 문서 하나 시점 조회 | 3 ms |
| 문서 하나 전체 이력 | 2 ms |
| 회사 목록 시점 조회 50줄 | 51 ms (고치기 전 8,938 ms) |
| 회사 목록 시점 조회, 상태 필터 | 88 ms |
| 재고 합계 시점 조회 500품목 | 34 ms |
| 문서 되돌리기 미리보기 / 적용 | 5 ms / 6 ms |
| 최근 7일 회사 되돌리기 미리보기 | 71 ms |
| 구독자 하나의 처리량(이벤트 5,000건) | 초당 약 1,087건 |
| 실제 모듈의 커맨드 하나(이벤트 약 4만 건 시점) | 평균 2.6 ms |

저장량은 실제 다섯 모듈로 만든 데모 회사(3년, 주문 3,287건, 이벤트 43,432건)에서 DB 전체 170 MB 다. 이벤트 하나에 약 3.3 KB, 주문 하나에 이벤트 약 13건이다. 압축 방식을 바꿔도 크게 줄지 않았다(약 82 MB 로 같음). 이 크기면 무료 500 MB 에 이벤트 약 13만 건, 주문 약 1만 건이 들어간다. 처음에 합성 이벤트로 잰 1.3 KB 는 실제의 절반도 안 됐다.

## 6. 무료 플랜 제약과 대응

| 제약 | 대응 |
|---|---|
| API 문장 8초 제한 | 오래 걸리는 작업은 묶음 호출, 구독 전달은 시간 예산 안에서. 큰 회사 되돌리기는 제한에 걸릴 수 있어 미측정 |
| DB 500 MB | 사용량 표시, 80% 경고 |
| 자동 백업 없음 | 원장 내보내기 |
| 7일 비활성 시 일시 중지 | 안내 화면. cron 이 일시 중지를 막는지는 미확인 |
| 기본 SMTP 팀 멤버 전용 | 메일 없이 관리자가 계정 생성 |
| 고객 DB 업그레이드 불가 | 같은 SQL 재실행, 앱이 양방향으로 버전 차이 안내 |
| pg_cron 로그 누적 | 매시 정리. 5초 주기면 하루 약 17,000행이 쌓인다 |

## 7. 서버가 필요한 것

메일 발송, 결제, 전자세금계산서, 은행 연동은 DB 함수만으로 어렵다. 필요하면 사용자 프로젝트의 Edge Function 으로 붙인다. MCP 도 SQL 함수로 시작했지만, 스트리밍이나 OAuth 가 필요하면 Edge Function 으로 옮긴다. PostgREST 는 `/orders/{id}/confirm` 같은 경로를 지원하지 않으므로, 꼭 필요하면 이것도 Edge Function 라우터로 해결한다. Java 는 트래픽이 큰 고객이나 우리가 호스팅하는 유료판에서 다시 검토한다.

## 표 파일 가져오기 (`sql/85_import.sql`)

`erp_import(type, rows, mode, options)`: 행마다 화면과 같은 `erp_command` 를 부른다. 규칙을 따로 쓰지 않고 원장에도 똑같이 남으며 한 번의 호출이 한 correlation 이라 통째로 되돌릴 수 있다.

- `mode`: `dry_run` 은 다 돌려 보고 아무것도 남기지 않는다. `commit` 은 한 행이라도 실패하면 그 호출을 통째로 남기지 않는다. `options.keep_good: true` 면 성공한 행은 남긴다.
- 8초 제한: 호출은 1000행까지, 6초가 차면 멈추고 `next` 를 돌려준다. 거기까지는 쓰였다. 남은 행은 `options.start` 로 다시 보낸다.
- 열 이름은 필드 이름이나 화면 라벨이다. `options.columns` 로 화면이 잡은 대응을 넘긴다(`null` 이면 그 열을 뺀다). 참조 칸은 이름·코드·내부 참조로 찾고 없거나 여럿이면 그 행의 오류다. 빈 칸은 아무 말도 하지 않은 것이다.
- 키: 카탈로그 `import_key`(제품 `internal_ref`, 연락처 `ref`, 계정 `code` 등)가 채워져 있고 한 건과 맞으면 고치고, 없으면 만든다. 은행 거래는 건너뛴다(`import_existing: skip`).
- 결과: `{type, mode, written, correlation_id, total, processed, next, created, updated, skipped, failed, rows[{row, status, id?, code?, message?}]}`. `row` 는 0부터.
- `erp_import_template(type)`: `{type, label, key, columns[{field, label, type, required, ref, options, help}]}`. `vendor_price` 는 카탈로그 유형이 아니라 제품의 공급사 줄을 다룬다(`id` 가 외부 ID).
