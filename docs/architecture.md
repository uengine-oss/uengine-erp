# uEngine ERP 아키텍처

서버 없이 이벤트 소싱 ERP 를 돌리는 구조다. 앱은 GitHub Pages 의 정적 파일이고, 데이터와 업무 규칙은 사용자 소유 Supabase 프로젝트의 Postgres 안에 있다.

## 1. 전체 구조

```
 브라우저 (Vue 3, GitHub Pages)              외부 에이전트 (MCP 서버, 나중에 Process GPT)
   업무 규칙 없음. 화면만 그린다                 도구 4개 + 리소스, 같은 API 사용
        │  HTTPS + 사용자 JWT                          │
        ▼                                              ▼
 ┌─ Supabase (사용자 소유) ──────────────────────────────────────────┐
 │  GoTrue 로그인 · PostgREST · Realtime                              │
 │  ┌─ public (공개 API) ───────────────────────────────────────┐    │
 │  │  erp_command  : 쓰기는 이것 하나                           │    │
 │  │  erp_records · erp_events : 읽기 전용 뷰 (RLS 적용)        │    │
 │  │  erp_as_of · erp_records_at · erp_rollback_* · erp_rebuild │    │
 │  └───────────────────────────────────────────────────────────┘    │
 │  ┌─ erp (비공개, API 로 직접 접근 불가) ─────────────────────┐    │
 │  │  events    추가만 가능한 원장 ← 유일한 진실                │    │
 │  │  records   현재 상태 (버리고 다시 만들 수 있음)            │    │
 │  │  quants·gl 파생 합계 (버리고 다시 만들 수 있음)            │    │
 │  │  catalog   애그리거트 메타데이터 → 화면·MCP 가 함께 사용   │    │
 │  │  h_*       명령 처리기 (Java 서비스 계층에 해당)           │    │
 │  └───────────────────────────────────────────────────────────┘    │
 └────────────────────────────────────────────────────────────────────┘
```

### 쓰기 한 번이 한 트랜잭션이다

`erp_command` 호출 하나가 Postgres 트랜잭션 하나다. 그 안에서 순서대로 일어난다.

1. 구성원·역할 확인(JWT 의 사용자 기준, 요청 본문의 값은 믿지 않음)
2. 애그리거트 행 잠금 → 낙관적 버전 확인
3. 처리기가 상태를 읽고 규칙을 확인한 뒤 이벤트 발행
4. `records` 갱신 + 파생 합계(`effects`) 반영
5. 연쇄 반응: 주문 확정 → 출고 전표 생성 등이 **같은 트랜잭션** 안에서 이어짐
6. 어디서든 실패하면 위 전부가 사라진다

MES 와의 차이: MES 는 서비스마다 DB 트랜잭션이 따로고 Kafka 로 이어져 최종 일관성이다. 여기는 DB 하나라 주문·출고·재고가 한 번에 맞거나 한 번에 취소된다. 대신 서비스를 따로 배포·확장할 수 없다.

| MES (Java) | 여기 (Postgres) |
|---|---|
| `event_store` + 버전 유니크 | `erp.events` + `unique(stream_id, version)` |
| 애그리거트·서비스 | `erp.h_<type>` 처리기 |
| `@Transactional` + Outbox + Kafka | 한 트랜잭션 안의 react 훅 |
| Spring Security + 게이트웨이 | GoTrue JWT + RLS + `security definer` |
| `read_model` | `erp.records`, 파생 표 |
| `CompensationService`(서비스별, 충돌 시 사람에게 넘김) | `erp_rollback_*`(회사 전체 원자적, 연쇄 범위 미리보기) |

## 2. 이벤트 소싱이 주는 것

| 시나리오 | 동작 | 상태 |
|---|---|---|
| 문서 시간 여행 | 슬라이더로 과거 시점의 문서를 읽기 전용으로 본다 | 커널 시험 통과 |
| 회사 시간 여행 | 그 시점의 모든 목록, 재고, 미수금을 본다 | 커널 시험 통과(재고 합계 포함) |
| 실패 롤백 | 처리 중 오류 시 이벤트·상태·문서 번호 전부 취소 | 커널 시험 통과 |
| 작업 되돌리기 | 잘못 확정한 주문을 출고 전표·재고 예약까지 함께 되돌림 | 커널 시험 통과 |
| 문서 되돌리기 | 특정 버전으로 되돌림 | 커널 시험 통과 |
| 회사 되돌리기 | 특정 시점 이후를 전부 되돌림(미리보기 후 적용) | 커널 시험 통과 |
| 되돌리기 취소 | 되돌린 것을 다시 되돌림 | 커널 시험 통과 |
| 재구축 | 파생 표를 전부 지우고 원장에서 다시 만들어 동일함을 확인 | 커널 시험 통과 |
| 인과 추적 | 한 작업의 모든 이벤트와 원인 사슬 조회 | 커널 시험 통과 |
| 히스토리안 분석·예측 | 리드타임, 재고 이력, 시점 정확 백테스트 | 설계만, 미구현 |
| 백업·복원 | 원장 내보내기는 구현, 복원은 미구현 | 일부 |

"커널 시험"은 실제 Postgres 에서 커널과 시험용 소형 도메인(주문·출고·재고)으로 돌린 것이다. 실제 ERP 모듈로는 아직 돌리지 않았다.

## 3. 되돌리기의 뜻

**이벤트를 지우지 않는다.** 되돌리기는 스트림마다 `Reverted` 이벤트를 하나 새로 쓴다. 그래서 다음이 성립한다.

- 원장에 "그때 정말 확정됐었다"와 "누가 왜 되돌렸다"가 모두 남는다.
- 되돌리기 전 시점으로 시간 여행하면 그때의 사실이 그대로 보인다.
- 되돌리기 자체를 되돌릴 수 있다.

안전장치:

| 상황 | 동작 |
|---|---|
| 뒤에 다른 작업이 이어짐(출고 후 확정 되돌리기) | 미리보기에 연쇄 범위를 보여 주고, 동의 없이는 실행 안 함 |
| 합계가 깨짐(이미 출고된 재고의 입고 되돌리기) | 차단. 문서 간 인과가 없어도 재고가 음수면 막는다 |
| 게시된 청구서 | 차단. 대변 메모로 정정하도록 안내 |
| 고객에게 이미 보낸 견적 | 경고. 시스템만 되돌아가니 상대에게 따로 알려야 한다 |
| 미리보기 후 데이터 변경 | 충돌로 거부, 다시 미리보기 |
| 구성원·회사 설정 | 되돌리기 대상에서 제외 |
| 권한 | 관리자만, 사유 필수 |

문서 번호는 재사용하지 않는다. 되돌린 주문의 번호는 비어 있게 된다.

**두 시간축.** `occurred_at` 은 시스템이 알게 된 시각이고, 전표의 `invoice_date` 같은 업무 일자는 별도다. 시간 여행은 "그때 시스템이 알던 것"을 보여 준다. 소급 입력은 두 축이 달라지며, 그 차이도 분석할 수 있다.

## 4. 보안

공개 키는 노출되어도 되는 값이고, 경계는 JWT 와 RLS 다.

| 공격 | 방어 | 확인 |
|---|---|---|
| 공개 키만으로 읽기·쓰기 | 뷰와 함수에 권한 없음 | 실제 REST 401 |
| 비구성원 로그인 | RLS 가 0건, 명령 거부 | 시험 |
| 이벤트 위조 | 표·`emit`·처리기에 실행 권한 없음 | 실제 REST 403, 시험 |
| 행위자 위조 | 행위자는 서명된 JWT 에서만 읽음 | 시험 |
| 자가 가입 | `auth.users` 트리거로 차단 | 실제 GoTrue |
| 동시 요청으로 재고 초과 | 애그리거트 잠금 | 실제 REST 50건 |
| 역할 밖 데이터 읽기 | 유형별 `read_roles` | 시험 |
| 설치 직후 회사 가로채기 | 일회용 설치 코드 | 실제 REST |

남는 위험: XSS 로 세션 탈취, 배포된 앱 코드의 공급망, 직원의 대량 조회(읽기 감사 없음), 호출 쏟아붓기(요청 제한 없음), 클라우드 미검증.

## 5. 측정

이벤트 200,000건(문서 20,000개), 로컬 8코어 Postgres 기준. **무료 플랜은 이보다 느리다. 클라우드 측정은 아직 안 했다.**

| 작업 | 시간 |
|---|---|
| 문서 하나 시점 조회 | 3 ms |
| 문서 하나 전체 이력 | 2 ms |
| 회사 목록 시점 조회 50줄 | 51 ms (고치기 전 8,938 ms) |
| 회사 목록 시점 조회, 상태 필터 | 88 ms |
| 재고 합계 시점 조회 500품목 | 34 ms |
| 문서 되돌리기 미리보기 / 적용 | 5 ms / 6 ms |
| 최근 7일 회사 되돌리기 미리보기 | 71 ms |

저장량은 시험 이벤트 200,000건에 약 147 MB 다. 이 크기가 유지되면 무료 500 MB 에는 약 60만~70만 건이 들어간다. 실제 이벤트 크기는 모듈 구현 후 다시 잰다.

## 6. 무료 플랜 제약과 대응

| 제약 | 대응 |
|---|---|
| API 문장 8초 제한 | 오래 걸리는 작업은 묶음 호출. 원자적이어야 하는 큰 회사 되돌리기는 제한에 걸릴 수 있어 미측정 |
| DB 500 MB | 사용량 표시, 80% 경고 |
| 자동 백업 없음 | 원장 내보내기 |
| 7일 비활성 시 일시 중지 | 안내 화면 |
| 기본 SMTP 팀 멤버 전용 | 메일 없이 관리자가 계정 생성 |
| 고객 DB 업그레이드 불가 | 같은 SQL 재실행, 앱이 버전 차이 안내 |

## 7. 서버가 필요한 것

메일 발송, 결제, 전자세금계산서, 은행 연동은 DB 함수만으로 어렵다. 필요하면 사용자 프로젝트의 Edge Function 으로 붙인다. Java 는 트래픽이 큰 고객이나 우리가 호스팅하는 유료판에서 다시 검토한다.
