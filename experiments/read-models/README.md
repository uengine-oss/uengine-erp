# 읽기 모델 측정 (S21)

3년 치 데모 회사 가온가전을 임시 DB 에 실제 모듈로 만들고(`experiments/demo-check.mjs` 와 같은 방식), 같은 질문을 원장과 읽기 모델에 던져 잰다. 시간은 모두 같은 기계에서 5번 잰 중앙값이고, 모든 회차는 `results.json` 에 있다.

```bash
node scripts/build-sql.mjs && RUNS=5 node experiments/read-models/measure.mjs
# KEEP=1 은 DB 를 남기고, DB=<이름> 은 이미 만든 DB 를 다시 잰다(그 DB 에는 앞선 측정이 넣은 주문이 더 있다).
```

**기계.** Apple M4 Max(16코어, 128 GB), macOS(Darwin 25.0.0), Node v25.2.1. 데이터베이스는 colima VM(8 vCPU, 14 GiB, aarch64) 안의 Supabase 로컬 스택, PostgreSQL 17.6. 같은 기계에서 다른 VM 과 영상 인코딩이 돌고 있었고 측정 중 부하 평균은 63~141 이었다. 조용한 기계라면 모든 시간이 더 짧다. 무료 클라우드 플랜에서는 재지 않았다.

**회사.** `web/src/lib/demo/generate.ts` 의 씨앗 1. 이벤트 45,240건, 확정 주문 3,287건, 2023-10-31 부터 2026-10-31 까지. 만드는 데 250초. 아래의 표 크기와 명령 시간은 측정이 직접 넣은 주문까지 더한 뒤라 이벤트가 51,276건이다.

**두 가지 시간.** 「데이터베이스 안」 은 그 사용자의 권한(행 보안 포함)으로 데이터베이스 안에서 문장 하나가 걸린 시간이다. 네트워크와 이 기계의 다른 부하가 끼지 않는다. 「클라이언트까지」 는 결과를 받아 오는 데까지다. 브라우저라면 여기에 HTTP 가 더해진다.

## 같은 질문, 두 길

| 질문 | 원장에서 | 읽기 모델에서 | 배 |
|---|---|---|---|
| 현황판 전체(매출·재고·장부), 데이터베이스 안 | 1.4 s | 17.8 ms | 77× |
| 최근 12개월 월별 매출(관리자 화면의 비교), 데이터베이스 안 | 781 ms | 2.5 ms | 310× |
| 분석의 판매·재고·장부 이력: 원장은 92일씩 25번, 읽기 모델은 1번 (데이터베이스 안 합계) | 1.6 s | 228 ms | 7× |
| 같은 것, 클라이언트까지 | 3.2 s | 246 ms | 13× |
| 예측 화면이 처음 읽는 데이터 전체(앱의 로더 그대로) | 3.8 s | 1.5 s | 3× |

두 길의 답은 같았다. 현황판의 매출·재고·장부 숫자, 12개월 비교, 그리고 같은 데이터로 돌린 수요 예측, 품절 예상일, 발주 정책·단종·창고 재배치·납기 what-if, 발주 필요, 손익 전망 9개 모델의 결과가 하나도 다르지 않았다.

예측 화면이 3배에 그치는 것은 입고, 납기, 입금 이력은 아직 원장에서 나누어 읽기 때문이다. 읽기 모델이 맡은 것은 판매, 재고, 장부다.

## 원장이 커질 때

| 최근 12개월 월별 매출, 데이터베이스 안 | 그때까지 이벤트 | 원장에서 | 읽기 모델에서 |
|---|---|---|---|
| 2024-10-31 기준 | 2,347 | 591 ms | 4.4 ms |
| 2025-10-31 기준 | 14,525 | 1.8 s | 4.1 ms |
| 2026-10-31 기준 | 45,240 | 2.7 s | 5.6 ms |

같은 12개월을 묻는데 원장 쪽은 이력이 길어질수록 느려진다. 읽기 모델은 그 12개월의 행만 읽는다. 이 표는 날짜를 정해 그때의 원장을 묻는 형태(시간 여행과 같은 길)라, 원장 쪽 숫자가 위의 비교와 다르다.

## 최신으로 두는 비용

| 일 | 시간 |
|---|---|
| 새 이벤트 약 100건(108건) 반영, 세 모델 합계 | 8.3 ms |
| 새 이벤트 약 1,000건(1,092건) 반영, 세 모델 합계 | 43.9 ms |
| 주문 3건이 만든 이벤트 36건 반영 | 9.1 ms |
| PostgreSQL MATERIALIZED VIEW 로 만든 같은 일별 매출의 REFRESH(매번 전부 다시 계산) | 554 ms |
| 세 모델을 비우고 첫 이벤트부터 다시 만들기 | 1.8 s (일별 매출 1.2 s, 재고 138 ms, 장부 49 ms) |
| 데모를 다 만든 직후 처음 따라잡기(같은 일) | 2.6 s |

materialized view 는 REFRESH 할 때마다 3년 치를 처음부터 다시 계산하고, 그 사이에는 낡은 값을 준다. 주문 3건을 확정한 뒤 view 의 이번 달 매출은 REFRESH 전까지 0 이었고, 읽기 모델은 그 이벤트 36건을 9.1 ms 에 반영해 804,000 을 보여 주었다(REFRESH 뒤의 view 도 같은 값). 읽기 모델의 반영 비용은 이력 길이가 아니라 새 이벤트와 그것이 건드린 주문 수를 따른다. `REFRESH ... CONCURRENTLY` 는 재지 않았다.

## 크기

| 표 | 크기 | 행 |
|---|---|---|
| `erp.events` (원장) | 106.5 MB | 51,276 |
| `erp.records` | 54.7 MB | 14,556 |
| `erp.gl_lines` | 4.0 MB | 19,254 |
| `erp.rm_sales_line` | 4.0 MB | 16,930 |
| `erp.rm_sales_day` | 5.5 MB | 16,433 |
| `erp.rm_stock_day` | 2.3 MB | 10,136 |
| `erp.rm_gl_day` | 336 KB | 2,274 |

다시 만들기를 여러 번 한 뒤 `VACUUM FULL` 로 압축한 크기다. 다시 만들면 지운 행이 자동 vacuum 이 정리할 때까지 자리를 차지한다. 이 데모에서는 날짜·제품·지역·창고마다 주문이 대개 하나라 일별 표가 주문별 표보다 크게 작지 않다. 하루 주문이 많은 회사일수록 차이가 벌어진다.

## 명령은 느려지지 않는가

| 명령 하나(주문 만들기·확정), 클라이언트까지 | 중앙값 | 95% |
|---|---|---|
| 읽기 모델 반영 없이 | 14.3 ms | 64.4 ms |
| 옆에서 200 ms 마다 반영(24번) | 28.3 ms | 108 ms |
| 다시 반영 없이 | 15.4 ms | 107 ms |

명령의 트랜잭션 안에서는 읽기 모델을 하나도 쓰지 않는다(`test/read-models.test.mjs` 가 확인한다). 그러니 차이가 있다면 같은 CPU 를 나눠 쓰는 데서 온다. 이번 회차에서는 반영을 돌리는 동안 중앙값이 두 배였지만, 같은 날 앞선 세 회차에서는 (7.3, 7.1, 8.0), (54.0, 45.2, 47.1), (36.6, 33.3, 40.7) ms 로 반영을 돌릴 때가 오히려 빨랐다(`results.json` 의 `command_latency_other_runs`). 부하가 이만큼 흔들리는 기계에서는 일정한 효과를 말할 수 없다. 실제 운영에서 반영은 5초마다 한 번이고, 할 일이 없으면 아무것도 쓰지 않는다.

## 이미 빠른 것

장부 보고서는 동기 파생 표 `erp.gl_lines` 를 읽는다. 데이터베이스 안에서 시산표 21.6 ms, 합계시산표 2.9 ms, 손익계산서 7.6 ms, 재무상태표 14.1 ms, 결산 상태 17.4 ms 다. 읽기 모델로 바꾸면 몇 초 늦은 값을 보일 수 있는데 얻는 것이 작아 바꾸지 않았다. 원장을 처음부터 읽는 쪽은 분석 함수(`sql/70_analytics.sql`)이고, 읽기 모델은 그 자리를 대신한다.
