# 원장과 커맨드

## Purpose

가온가전의 모든 업무 쓰기는 명령 하나로 들어와 한 트랜잭션에서 추가만 되는 원장에 사실을 남긴다. 서버 프로세스가 없어도 동시 요청은 규칙을 넘지 못하고, 실패한 명령은 흔적을 남기지 않으며, 응답을 잃은 요청은 다시 보내도 한 번만 일어난다. 앱과 DB 의 버전이 어긋나면 데이터를 망가뜨리기 전에 쓰기를 멈춘다. 화면은 이 계약을 그대로 보여 준다. 메뉴·폼·목록은 카탈로그에서 그리고, 오류는 서버 문구로 말하며, 이력과 원장을 사람이 읽을 수 있게 한다.

## Requirements

### Requirement: 업무 쓰기는 명령으로 들어와 원장에 이벤트를 남긴다

시스템은 업무 쓰기를 공개 입구 `erp_command` 와 거기로 이어지는 REST·MCP 로만 받아야 한다(SHALL). 명령이 성공하면 이벤트가 원장에 더해지고 현재 상태가 바뀐다. 이벤트에는 바뀐 필드의 이전 값과 이후 값이 실린다. 바뀐 것이 없으면 이벤트를 남기지 않는다.

#### Scenario: 고치면 이전 값과 이후 값이 이벤트에 남는다

- **WHEN** 박영업이 수량 3 으로 만든 문서의 수량을 5 로 저장한다
- **THEN** 그 문서의 원장에는 만든 이벤트와 고친 이벤트가 차례로 남는다
- **AND** 고친 이벤트의 `changes` 에 수량의 `from` 3, `to` 5 가 실리고 현재 수량은 5 다

#### Scenario: 바뀐 것이 없으면 이벤트도 없다

- **WHEN** 박영업이 수량 1 인 문서를 수량 1 그대로 다시 저장한다
- **THEN** 그 문서의 이벤트는 처음 만든 1건뿐이다

### Requirement: 원장은 고칠 수 없고 명령 밖의 쓰기는 거부된다

시스템은 원장 이벤트를 추가만 할 수 있게 해야 하며 DB 소유자의 수정과 삭제도 거부해야 한다(SHALL). 구성원은 원장·현재 상태·구성원 표와 내부 처리기를 직접 쓰거나 부를 수 없다. 행위자는 서명된 로그인 토큰에서만 읽고 요청 본문의 값을 믿지 않는다.

#### Scenario: 소유자도 원장을 고치거나 지울 수 없다

- **WHEN** 회사의 DB 소유자가 SQL Editor 에서 원장 이벤트 한 건을 고치거나 지운다
- **THEN** 둘 다 `ERP_IMMUTABLE` 로 거부되고 이벤트는 그대로다

#### Scenario: 관리자의 브라우저도 이벤트를 위조할 수 없다

- **WHEN** 김대표가 자기 로그인 토큰으로 원장에 이벤트를 넣거나, 현재 상태와 구성원 표를 고치거나, 내부 처리기를 직접 부른다
- **THEN** 모두 권한 오류로 거부된다
- **AND** REST 로 `erp_events` 에 넣거나 `erp_records` 를 지우려 해도 401 또는 403 이다

#### Scenario: 요청 본문으로 다른 사람 행세를 할 수 없다

- **WHEN** 조회 역할 구성원이 본문에 `actor_id` 와 `roles: ["admin"]` 을 넣어 문서를 만든다
- **THEN** `ERP_FORBIDDEN` 으로 거부된다
- **AND** 박영업이 만든 문서의 이벤트에는 행위자로 박영업이 남는다

### Requirement: 명령 하나는 트랜잭션 하나다

시스템은 명령 하나의 판단·이벤트·현재 상태·파생 합계·문서 번호를 한 트랜잭션으로 묶어야 한다(SHALL). 어디서든 실패하면 전부 사라진다. 한 모듈 안의 연쇄 반응도 같은 트랜잭션이고, 연쇄로 생긴 이벤트는 같은 작업 번호(`correlation_id`)와 원인 이벤트를 가리킨다.

#### Scenario: 실패한 명령은 이벤트·상태·문서 번호를 남기지 않는다

- **WHEN** 이벤트를 쓰고 번호를 받은 뒤 규칙 오류가 나는 명령을 보낸다
- **THEN** 오류가 돌아오고 그 문서의 이벤트 수와 값은 명령 전과 같다
- **AND** 번호를 쓰지 않은 것으로 남아 다음 번호가 비지 않는다

#### Scenario: 연쇄 반응이 실패하면 원래 명령도 취소된다

- **WHEN** 문서를 만드는 명령의 연쇄 반응이 다른 문서를 쓴 뒤 실패한다
- **THEN** 오류가 돌아오고 회사 전체의 이벤트 수가 명령 전과 같다

#### Scenario: 연쇄로 생긴 이벤트는 같은 작업 번호와 원인을 가리킨다

- **WHEN** 문서를 만드는 명령이 연쇄 반응으로 다른 문서를 하나 더 만든다
- **THEN** 응답의 `events` 에 이벤트가 2건 실린다
- **AND** 두 이벤트의 `correlation_id` 가 같고, 둘째의 `causation_seq` 는 첫째를 가리키며 `source` 는 `reaction` 이다

### Requirement: 동시 요청도 규칙을 넘지 못한다

시스템은 같은 문서를 건드리는 명령을 차례로 처리해야 한다(SHALL). 규칙은 잠금을 잡은 뒤의 최신 상태로 판단하므로 동시에 들어온 요청이 수량을 초과하거나 쓰기를 잃지 않는다. 유일해야 하는 값은 동시에 만들어도 하나만 남는다.

#### Scenario: 수량 10 에서 동시에 50번 빼면 10번만 성공한다

- **WHEN** 수량 10 인 문서에서 1개씩 빼는 명령을 별도 연결로 동시에 50번 보낸다
- **THEN** 정확히 10건이 성공하고 나머지는 규칙 오류로 거부된다
- **AND** 남은 수량은 0 이다

#### Scenario: 동시에 40번 써도 잃어버리는 쓰기가 없다

- **WHEN** 수량 1,000 인 문서에서 1개씩 빼는 명령을 동시에 40번 보낸다
- **THEN** 40건 모두 성공하고 남은 수량은 960 이다
- **AND** 문서의 이벤트 버전은 1 부터 41 까지 끊기지 않는다

#### Scenario: 유일한 값은 동시에 만들어도 하나만 생긴다

- **WHEN** 같은 코드로 문서를 만드는 명령을 동시에 20번 보낸다
- **THEN** 1건만 성공하고 나머지는 `ERP_DUPLICATE` 로 거부된다

### Requirement: 앞선 버전으로 저장하면 충돌로 거부한다

시스템은 명령에 기대 버전(`p_expected_version`)이 있으면 현재 버전과 비교해 다르면 `ERP_CONFLICT`(HTTP 409)로 거부해야 한다(SHALL). 화면은 입력 중인 내용을 지키면서 충돌을 알리고 새로 고침을 제공한다. 입력 중이 아닌 화면에는 다른 사람의 변경을 바로 반영한다.

#### Scenario: 옛 버전을 보낸 저장은 거부된다

- **WHEN** 이미 버전 2 로 고쳐진 문서를 박영업이 버전 1 을 기대 버전으로 저장한다
- **THEN** `ERP_CONFLICT` 로 거부된다
- **AND** 공개 입구로 보내면 HTTP 409 다

#### Scenario: 같은 폼을 동시에 저장하면 한 사람만 이긴다

- **WHEN** 버전 1 을 기대 버전으로 하는 저장을 동시에 20번 보낸다
- **THEN** 1건만 성공하고 나머지는 `ERP_CONFLICT` 로 거부된다

#### Scenario: 입력 중에 다른 사람이 고치면 알리고 새로 고침을 제공한다

- **WHEN** 박영업이 메모를 입력하는 동안 다른 창에서 같은 문서가 고쳐진다
- **THEN** 입력한 값은 그대로 있고 「이 문서를 변경했습니다」 안내가 보인다
- **AND** 저장하면 「다른 사람이 먼저 변경했습니다」 가 보이고, 「새로 고침」 을 누르면 서버의 값으로 바뀌고 안내가 사라진다

#### Scenario: 입력 중이 아니면 다른 사람의 변경이 바로 반영된다

- **WHEN** 박영업이 문서를 열어만 두었을 때 김대표가 메모를 고친다
- **THEN** 새로 고치지 않아도 메모와 버전이 바뀌고 「김대표 님이 방금」 안내가 보인다

### Requirement: 재시도 키로 다시 보내도 한 번만 일어난다

시스템은 같은 사람이 같은 재시도 키로 명령을 다시 보내면 명령을 다시 실행하지 않고 처음 결과에 `replayed: true` 를 붙여 돌려주어야 한다(SHALL). 키는 사람별이므로 다른 사람의 같은 키는 다른 요청이다. 7일이 지난 키는 전달 작업이 돌 때 지워지며 그 뒤에는 새 요청으로 본다.

#### Scenario: 응답을 잃어 다시 보내도 문서는 하나다

- **WHEN** 박영업이 재시도 키 `key-1` 로 문서를 만들고 같은 키로 같은 요청을 다시 보낸다
- **THEN** 두 응답의 `id` 가 같고 둘째 응답에 `replayed: true` 가 있다
- **AND** 그 유형의 문서는 1건만 늘어난다

#### Scenario: 다른 사람의 같은 키는 다른 요청이다

- **WHEN** 영업 역할의 다른 구성원이 박영업과 같은 재시도 키 `key-1` 로 문서를 만든다
- **THEN** 새 문서가 만들어지고 `id` 가 박영업의 문서와 다르다

#### Scenario: 7일이 지난 재시도 키는 잊힌다

- **WHEN** 7일 전에 쓴 재시도 키로 전달 작업이 돈 뒤 같은 요청을 다시 보낸다
- **THEN** 처음 결과가 아니라 새 명령으로 처리된다

### Requirement: 업무 문서는 모르는 필드를 거부한다

시스템은 판매·재고·구매·청구·회계 문서와 전용 처리기가 없는 유형의 명령에 카탈로그에 없는 필드가 있으면 `ERP_UNKNOWN_FIELD` 로 거부해야 한다(SHALL). 조용히 버리면 DB 보다 새 앱이 저장됐다고 착각하기 때문이다. 기초데이터 유형의 처리는 `erp-master` 가 정한다.

#### Scenario: 모르는 필드를 넣은 명령은 거부된다

- **WHEN** 박영업이 카탈로그에 없는 필드 `nope` 를 넣어 문서를 만든다
- **THEN** `ERP_UNKNOWN_FIELD` 로 거부되고 문서는 생기지 않는다

### Requirement: 오류는 코드와 상태로 구분할 수 있다

시스템은 규칙 오류를 `ERP_코드: 한국어 문구` 형식으로 돌려주고 코드에 맞는 HTTP 상태를 내야 한다(SHALL). `ERP_AUTH` 는 401, `ERP_FORBIDDEN`·`ERP_MODULE_OFF` 는 403, `ERP_NOT_FOUND`·`ERP_UNKNOWN_TYPE` 은 404, `ERP_CONFLICT`·`ERP_DUPLICATE`·`ERP_IN_USE` 는 409, `ERP_REQUIRED`·`ERP_INVALID`·`ERP_INVALID_REF`·`ERP_UNKNOWN_FIELD` 는 422, 그 밖의 `ERP_` 코드는 400 이다. 화면은 코드를 빼고 문구만 보여 준다.

#### Scenario: 입력 오류는 코드로 구분된다

- **WHEN** 박영업이 필수값 없이, 목록에 없는 값으로, 숫자 칸에 글자로, 이미 있는 유일 값으로 문서를 만든다
- **THEN** 차례로 `ERP_REQUIRED`, `ERP_INVALID`, `ERP_INVALID`, `ERP_DUPLICATE` 로 거부된다

#### Scenario: 클라이언트는 상태 코드로 오류를 구분한다

- **WHEN** 외부 시스템이 공개 API 로 필수값을 빼고 만들고, 옛 버전으로 고치고, 조회 역할 토큰으로 쓴다
- **THEN** 차례로 422, 409, 403 을 받고 본문의 `message` 에 `ERP_REQUIRED`, `ERP_CONFLICT` 코드가 보인다

#### Scenario: 화면은 서버 문구만 보여 주고 칸을 표시한다

- **WHEN** 박영업이 필수 칸을 비우고 저장한다
- **THEN** 「고객 항목은 필수입니다」 처럼 서버 문구가 보이고 `ERP_` 글자는 보이지 않는다
- **AND** 그 칸이 잘못된 칸으로 표시된다

#### Scenario: 서버가 거절한 변경은 사유를 보여 주고 입력을 되돌릴 수 있다

- **WHEN** 취소된 문서를 고쳐 저장한다
- **THEN** 서버가 보낸 거절 사유가 폼 위에 보인다
- **AND** 입력을 되돌리면 저장된 값으로 돌아온다

#### Scenario: 다른 문서가 참조하는 레코드는 지울 수 없다

- **WHEN** 김대표가 다른 문서가 가리키는 레코드를 지운다
- **THEN** `ERP_IN_USE` 로 거부된다

### Requirement: 명령과 읽기는 역할을 따른다

시스템은 명령마다 카탈로그의 역할을 서명된 토큰의 사용자 기준으로 확인해야 한다(SHALL). `admin` 은 모든 쓰기가 가능하다. 카탈로그에 `read_roles` 가 있는 유형은 그 역할과 `admin` 만 읽으며, 목록·원장·이력·시점 조회·작업 묶음 조회에 똑같이 적용된다.

#### Scenario: 명령마다 역할을 확인한다

- **WHEN** 조회 역할 구성원이 문서를 만들고, 박영업이 같은 문서를 만들고, 박영업이 구성원을 추가한다
- **THEN** 조회 역할의 생성과 박영업의 구성원 추가는 `ERP_FORBIDDEN` 이고 박영업의 생성은 성공한다

#### Scenario: 읽기 제한 유형은 어디서도 보이지 않는다

- **WHEN** 회계 역할만 읽을 수 있는 문서를 박영업이 목록·원장·이력·시점 조회·작업 묶음 조회로 찾는다
- **THEN** 목록과 원장은 0건, 이력(`erp_stream`)과 시점 조회(`erp_as_of`)는 `ERP_FORBIDDEN`, 작업 묶음(`erp_correlation`)은 빈 목록이다
- **AND** 정회계는 같은 문서가 목록에 1건 보인다

#### Scenario: 조회 역할은 쓰기 버튼이 없고 읽기 제한 유형은 안내만 본다

- **WHEN** 조회 역할 구성원이 문서를 열고, 회계 역할만 읽는 유형의 목록과 문서를 주소로 연다
- **THEN** 저장·상태 변경·새로 만들기 버튼과 입력 칸이 없다
- **AND** 목록은 「회계 역할에게만 보입니다」, 문서는 「이 문서를 찾을 수 없습니다」 를 보여 준다

### Requirement: 원장과 이력을 화면에서 읽는다

시스템은 원장을 시간 역순 표로 보여 주고 유형·출처·이벤트·행위자로 거를 수 있어야 한다(SHALL). 이벤트를 고르면 원본 JSON 과 인과 사슬을 보여 준다. 문서의 이력은 누가, 어떤 출처로, 왜, 무엇을 바꿨는지 보여 준다.

#### Scenario: 원장을 유형·출처·이벤트·행위자로 거른다

- **WHEN** 김대표가 원장 화면에서 유형, 출처, 이벤트 이름, 행위자로 거른다
- **THEN** 건수가 조건에 맞게 줄어든다
- **AND** 맞는 이벤트가 없으면 「조건에 맞는 이벤트가 없습니다」 가 보이고 조건을 지우면 돌아온다

#### Scenario: 이벤트를 누르면 원본과 인과 사슬이 보인다

- **WHEN** 김대표가 연쇄로 생긴 이벤트의 행을 누른다
- **THEN** 원본 JSON 과, 원인 이벤트를 뿌리로 그 이벤트를 자식으로 둔 트리가 보인다
- **AND** 트리의 노드를 고르면 그 이벤트의 JSON 으로 바뀌고 문서로 갈 수 있다

#### Scenario: 이력은 사람과 에이전트, 사유를 구분해 보여 준다

- **WHEN** 에이전트가 사유를 붙여 고친 문서를 연다
- **THEN** 그 이력 항목에 「에이전트」 와 사유가 보인다
- **AND** 사람이 저장한 항목에는 이름과 「사람」 이 보인다

#### Scenario: 값을 바꾸면 이력에 라벨과 이전·이후가 남는다

- **WHEN** 박영업이 메모와 줄 수량을 고쳐 저장한다
- **THEN** 버전이 v2 가 되고 맨 위 이력 항목에 항목 라벨, 이전 값, 이후 값, 줄 변경, 합계가 보인다

### Requirement: 현재 상태는 언제나 원장을 재생한 값과 같다

시스템은 모든 문서의 현재 상태가 그 문서의 이벤트를 처음부터 재생한 값과 같음을 보장해야 한다(SHALL). 관리자는 무결성 검증으로 이를 묶음별로 확인할 수 있고, 어긋나면 건수로 알린다.

#### Scenario: 현재 상태는 원장 재생과 같다

- **WHEN** 명령들이 끝난 회사의 모든 문서를 원장에서 재생해 현재 상태와 비교한다
- **THEN** 다른 문서가 하나도 없다

#### Scenario: 무결성 검증이 몰래 고친 값을 찾아낸다

- **WHEN** 김대표가 원장 화면에서 무결성 검증을 누른다
- **THEN** 「불일치 0건」 이 보인다
- **AND** 원장을 거치지 않고 현재 상태를 고쳐 둔 뒤 다시 누르면 「1건이 이벤트와 다릅니다」 가 보인다

### Requirement: 화면은 카탈로그를 따라 메뉴와 폼을 그린다

시스템은 메뉴·폼의 칸·상태 표시·버튼을 카탈로그에서 그려야 한다(SHALL). 카탈로그에 없는 유형은 보이지 않고, 금액은 브라우저가 계산하지 않고 서버의 미리보기 값을 보여 주며, 상태 변경 버튼은 지금 상태에 맞는 것만 나온다. 위험한 동작은 확인을 거친다.

#### Scenario: 카탈로그에 있는 유형만 메뉴에 나타난다

- **WHEN** 판매와 회계만 켜진 회사의 박영업이 판매 메뉴를 연다
- **THEN** 견적·주문과 연락처가 보이고 출고 전표와 구매 메뉴는 없다

#### Scenario: 줄을 넣으면 서버가 계산한 값이 화면에 나타난다

- **WHEN** 박영업이 견적에 에어서큘레이터(정가 89,000)를 넣고 수량을 3 으로 고친다
- **THEN** 단가 89,000, 공급가 267,000, 합계 293,700 이 서버의 미리보기 값으로 나타난다

#### Scenario: 저장하면 번호가 붙고 주소가 바뀌며 이력이 시작된다

- **WHEN** 박영업이 새 견적을 저장한다
- **THEN** 주소에 문서 ID 가 들어가고 제목이 `S00001` 같은 번호가 된다
- **AND** 버전은 v1, 이력은 1건이고 다시 고칠 때까지 저장 버튼이 꺼진다

#### Scenario: 상태 변경 버튼은 지금 상태에 맞는 것만 나온다

- **WHEN** 박영업이 초안 문서의 발송 버튼을 누른다
- **THEN** 상태가 바뀌고 발송 버튼이 사라진다
- **AND** 인자가 필요한 변경은 대화상자로 묻고, 비워 보내면 서버 문구로 거부된다
- **AND** 취소처럼 위험한 변경은 위험 표시 버튼과 사유 칸을 거치며 사유가 이력에 남는다

#### Scenario: 참조 칸은 키보드만으로 고른다

- **WHEN** 박영업이 참조 칸에 글자를 치고 화살표와 Enter 로 고른다
- **THEN** 목록이 좁혀지고 고른 이름이 칸에 들어간다
- **AND** 카탈로그의 다른 검색 항목으로도 찾을 수 있고 Esc 는 고른 값을 지우지 않는다

#### Scenario: 줄 표는 Tab 으로 늘리고 구역·메모 줄을 넣는다

- **WHEN** 박영업이 줄의 마지막 칸에서 Tab 을 누르고 구역 줄과 메모 줄을 더한 뒤 줄 하나를 지운다
- **THEN** 새 줄의 첫 칸으로 커서가 가고, 구역·메모 줄이 줄 사이에 들어가며, 지운 줄이 사라진다

#### Scenario: 추가 명령과 위험 동작은 더 보기에 있다

- **WHEN** 박영업이 더 보기에서 추가 명령을 누르고 보관을 누른다
- **THEN** 추가 명령은 바로 실행되어 이력에 남는다
- **AND** 보관은 위험 표시 확인을 거친 뒤 문서에 「보관」 표시가 붙는다

#### Scenario: 저장 안 한 변경이 있으면 떠나기 전에 묻는다

- **WHEN** 박영업이 저장하지 않고 다른 메뉴를 누른다
- **THEN** 「저장되지 않았습니다」 대화상자가 나오고 「계속 입력」 을 고르면 입력이 그대로 있다

#### Scenario: 빈 목록은 할 일을 알려 준다

- **WHEN** 문서가 하나도 없는 유형의 목록을 연다
- **THEN** 「아직 등록된 …이 없습니다」 와 「새로 만들기」 링크가 보인다

#### Scenario: 없는 주소는 안내 화면을 보여 준다

- **WHEN** 잘못된 문서 ID, 설치되지 않은 유형, 없는 경로로 들어간다
- **THEN** 차례로 「찾을 수 없습니다」, 「설치되지 않은」, 「없는 화면」 안내가 보인다

### Requirement: 목록은 찾고 정렬하고 내려받고 인쇄할 수 있다

시스템은 목록의 검색·정렬·상태 필터·쪽 넘김을 주소에 남겨 뒤로 가기에도 유지해야 한다(SHALL). 정렬은 숫자를 숫자로 다룬다. CSV 는 코드가 아니라 이름으로 내려받고 수식 주입을 막는다. 인쇄는 메뉴와 버튼을 뺀 문서만 남긴다.

#### Scenario: 목록 조건이 주소에 남는다

- **WHEN** 김대표가 30건인 목록에서 쪽을 넘기고, 금액 열로 정렬하고, 검색한 뒤 한 줄을 열었다가 뒤로 간다
- **THEN** 쪽은 25건씩이고 정렬은 숫자 크기대로이며 주소에 `sort`, `dir`, `q` 가 남는다
- **AND** 뒤로 오면 같은 검색 결과가 보이고, 맞는 것이 없으면 「조건 지우기」 로 돌아온다

#### Scenario: 목록은 금액·상태·참조 이름을 읽기 좋게 보여 준다

- **WHEN** 보관 포함을 켜고 목록을 본다
- **THEN** 금액은 오른쪽 정렬, 상태는 알약, 참조는 이름으로 보이고 보관한 문서에 「보관」 이 붙는다

#### Scenario: CSV 는 이름으로 내려받고 수식 주입을 막는다

- **WHEN** 이름이 `=HYPERLINK("x")` 인 거래처가 있는 목록을 CSV 로 내려받는다
- **THEN** 파일 이름은 유형과 날짜이고 첫 글자는 BOM 이며 머리글은 칸 라벨이다
- **AND** 선택지는 라벨로 나오고 그 이름은 작은따옴표가 붙어 수식으로 해석되지 않는다

#### Scenario: 인쇄는 문서만 남긴다

- **WHEN** 문서 화면에서 인쇄를 누른다
- **THEN** 인쇄가 한 번 불리고 메뉴·이력·저장 버튼이 숨으며 회사 이름이 머리에 나온다

#### Scenario: 이력 패널을 접고 펼친다

- **WHEN** 문서 화면에서 이력 패널을 접었다 다시 펼친다
- **THEN** 패널이 사라졌다 다시 나타난다

### Requirement: 연결이 흔들려도 입력을 잃지 않는다

시스템은 실시간 연결이 있으면 다른 사람의 변경을 바로 보여 주고, 없어도 그대로 동작해야 한다(SHALL). 쓰는 중에 연결이 끊기면 입력을 지키고 재시도를 제공한다. 실패한 호출은 아무것도 바꾸지 않으므로 Supabase 디버거 확장이 내는 일시 오류(`XX000`, `pldbgapi2`)는 화면이 한 번 스스로 다시 보낸다.

#### Scenario: 다른 사람이 만든 문서가 목록과 원장에 바로 나타난다

- **WHEN** 김대표가 목록을 열어 두었을 때 다른 사람이 문서를 만든다
- **THEN** 새로 고치지 않아도 건수가 늘고 그 문서가 목록에 보인다
- **AND** 원장 화면에서도 맨 위에 바로 나타난다

#### Scenario: 실시간 연결이 막혀도 앱은 돌아간다

- **WHEN** 실시간 연결이 막힌 브라우저에서 문서를 만든다
- **THEN** 표시가 「실시간」 이 아닌 상태로 바뀌고 저장은 그대로 된다

#### Scenario: 쓰는 중에 연결이 끊겨도 입력은 남는다

- **WHEN** 박영업이 입력한 뒤 연결이 끊긴 상태에서 저장한다
- **THEN** 「연결할 수 없습니다」 와 연결 배너가 보이고 입력은 그대로다
- **AND** 연결이 돌아와 다시 시도하면 배너가 사라지고 저장된다

#### Scenario: 일시 오류는 한 번 스스로 다시 보낸다

- **WHEN** 저장의 첫 호출이 `XX000`, `pldbgapi2` 오류로 실패한다
- **THEN** 앱이 한 번 더 보내 저장되고 오류는 보이지 않는다

### Requirement: 앱과 DB 의 버전이 어긋나면 쓰기를 멈춘다

시스템은 앱이 명령마다 자기 버전을 싣고, DB 가 요구하는 최소 버전보다 낮으면 `ERP_APP_OUTDATED` 로 거부해야 한다(SHALL). 공개 상태 응답은 `version` 과 `min_app_version` 을 준다. 앱은 어느 쪽이 낮든 쓰기 버튼을 막고 무엇을 해야 하는지 안내한다.

#### Scenario: 오래된 앱의 명령은 거부된다

- **WHEN** 앱이 버전 `0.0.1` 을 실어 명령을 보낸다
- **THEN** `ERP_APP_OUTDATED` 로 거부된다
- **AND** 공개 키로 물은 `erp_status` 에 `min_app_version` 이 있다

#### Scenario: 화면의 모든 명령이 앱 버전을 싣는다

- **WHEN** 박영업이 화면에서 견적을 저장하고 확정한다
- **THEN** 나간 명령 2건 모두 `p_app_version` 에 세 자리 버전이 실린다

#### Scenario: DB 가 최소 버전을 높이면 열린 앱은 쓰기를 멈춘다

- **WHEN** 앱을 열어 둔 사이 DB 의 최소 앱 버전이 v9.9.9 가 되고 김대표가 저장한다
- **THEN** 「앱이 이 데이터베이스보다 오래되었습니다」 와 「최소 v9.9.9」 배너가 보이고 저장 버튼이 사라진다
- **AND** 저장 못 한 입력이 있으면 떠날 때 묻고, 목록의 새로 만들기·상태 변경·되돌리기와 모듈 켜고 끄기가 막힌다
- **AND** 같은 앱을 새로 고쳐도 계속 막히고, 최소 버전이 돌아오면 풀린다

#### Scenario: DB 가 앱보다 낮으면 업그레이드할 때까지 쓰기를 막는다

- **WHEN** DB 의 스키마 버전이 앱보다 낮은 회사에 김대표가 로그인한다
- **THEN** 「업그레이드할 때까지 저장할 수 없습니다」 배너가 보인다
- **AND** 읽기는 되지만 새로 만들기·저장·구성원 추가와 비활성화가 없고 모듈 끄기는 꺼져 있다

## 성능·비용 제약

이벤트 약 4만 건 시점에 실제 모듈의 커맨드 하나가 평균 2.6 ms 다(로컬 8코어 Postgres. 무료 플랜은 이보다 느리고 클라우드 측정은 아직 하지 않았다). 공개 API 문장은 Supabase 제한으로 8초 안에 끝나야 한다.
