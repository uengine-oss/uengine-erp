# 설치, 보안, 데모 회사

## Purpose

김대표는 서버 없이 앱과 자기 Supabase 프로젝트만으로 가온가전을 시작한다. 접속 정보를 넣고 화면이 주는 설치 SQL 을 실행해 회사를 만들면 관리자 계정이 생기고, 직원 계정은 메일 없이 관리자가 만든다. 공개 키는 노출되어도 되는 값이고 경계는 로그인 토큰과 행 권한이다. 비밀 키는 받지 않으며, 앱은 어느 정적 경로에 올려도 제3자에게 아무것도 보내지 않는다. 처음 둘러보려면 3년치 가상 회사를 실제 명령으로 만들 수 있다.

## Requirements

### Requirement: 앱은 접속 정보를 받되 비밀 키는 거부한다

시스템은 처음 접속하면 Supabase 프로젝트 연결 화면을 보여 주어야 한다(SHALL). 비밀 키(`sb_secret_` 형식과 `service_role` JWT)는 네트워크로 보내지도 저장하지도 않고 거부한다. 주소와 키의 형식이 틀리면 칸마다 알려 준다.

#### Scenario: 처음 접속하면 연결 화면이 나온다

- **WHEN** 김대표가 앱을 처음 연다
- **THEN** 「Supabase 프로젝트 연결」 화면과 「대시보드에서 새 프로젝트 만들기」 링크가 보인다

#### Scenario: 비밀 키는 보내지도 저장하지도 않는다

- **WHEN** 김대표가 공개 키 칸에 비밀 키나 `service_role` 토큰을 넣고 다음을 누른다
- **THEN** 「이 키는 공개하면 안 되는 키입니다. Publishable(공개) 키를 넣으세요」 가 보인다
- **AND** 그 값은 어떤 요청에도 실리지 않고 브라우저 저장소에도 없다

#### Scenario: 잘못된 주소와 키 형식을 알려 준다

- **WHEN** 김대표가 Supabase 가 아닌 주소와 아무 글자나 넣고 다음을 누른다
- **THEN** 주소 칸의 오류와 `sb_publishable_` 를 안내하는 키 칸의 오류가 보인다

### Requirement: 화면이 주는 SQL 로 설치하고 다시 실행해도 데이터는 그대로다

시스템은 공개 키로 표를 만들 수 없음을 설명하고 설치 SQL 을 복사하게 해야 한다(SHALL). SQL 끝에는 한 번 쓰는 설치 코드가 붙는다. 설치 코드는 브라우저에 회사가 생길 때까지만 있고, 회사가 생기면 DB 에서도 지워진다. 같은 SQL 을 다시 실행하면 데이터를 지우지 않고 업그레이드한다.

#### Scenario: 함수가 없으면 설치 단계로 가고 실행하면 다음으로 넘어간다

- **WHEN** 김대표가 빈 프로젝트의 주소와 공개 키를 넣는다
- **THEN** 「데이터베이스 설치」 화면에 「공개 키로는 표를 만들 수 없어서」 와 「우리에게 오지 않습니다」 가 보인다
- **AND** SQL 을 복사하면 끝에 설치 코드가 있고, SQL Editor 에서 실행하면 새로 고치지 않아도 「회사 만들기」 로 넘어간다

#### Scenario: 다른 브라우저에서 설치했으면 설치 코드를 다시 발급한다

- **WHEN** 이미 설치된 프로젝트에 설치 코드가 없는 브라우저로 접속해 회사를 만든다
- **THEN** 다시 발급할 SQL 한 줄이 보이고, 맞지 않으면 「설치 코드가 맞지 않습니다」 와 새 줄이 보인다
- **AND** 그 줄을 실행하고 다시 누르면 회사가 만들어진다

#### Scenario: 틀린 설치 코드로는 회사를 차지할 수 없다

- **WHEN** 공개 키로 틀린 설치 코드와 함께 `erp_bootstrap` 을 부른다
- **THEN** 400 이고 `message` 에 `ERP_SETUP_CODE` 가 있다

#### Scenario: 회사가 있으면 두 번째 회사를 만들 수 없다

- **WHEN** 회사가 있는 프로젝트에 공개 키로 `erp_bootstrap` 을 다시 부른다
- **THEN** `ERP_INITIALIZED` 로 거부된다

#### Scenario: 공개 키로는 설치 여부만 물을 수 있다

- **WHEN** 공개 키로 `erp_status` 를 부른다
- **THEN** 200 이고 `installed`, `initialized` 가 나오지만 `company_name` 은 비어 있다
- **AND** 구성원이 부르면 회사 이름이 나온다

#### Scenario: 같은 SQL 을 다시 돌리면 업그레이드되고 데이터는 그대로다

- **WHEN** DB 가 이전 버전일 때 김대표가 배너의 「SQL 복사」 로 받은 SQL 을 실행하고 「다시 확인」 을 누른다
- **THEN** 배너에 「이전 버전」 과 「데이터는 그대로 보존」 이 보인다
- **AND** 복사한 SQL 에는 설치 코드가 없고, 실행 뒤 배너가 사라지며 이벤트 수와 기존 문서가 그대로다

### Requirement: 회사를 만들면 관리자가 메일 없이 바로 로그인한다

시스템은 회사를 만들 때 관리자 계정을 메일 확인 없이 만들고 바로 로그인시켜야 한다(SHALL). 고른 통화에 맞춰 금액 자릿수가 정해진다. 설치 코드는 끝나면 브라우저에서 지운다.

#### Scenario: 통화로 자릿수가 정해지고 자동으로 로그인한다

- **WHEN** 김대표가 통화를 USD 로 고르고 KRW 로 바꾼 뒤 회사를 만든다
- **THEN** 「소수 2자리」, 「소수 0자리」 로 바뀌어 보이고 비밀번호 확인이 다르면 「일치하지 않습니다」 다
- **AND** 만들면 홈과 사용자 이름, 회사 이름이 보이고 설치 코드가 브라우저에서 사라진다

#### Scenario: 메일 없이 관리자 계정이 만들어진다

- **WHEN** 메일 확인이 켜진 프로젝트에서 올바른 설치 코드로 회사를 만든다
- **THEN** 메일을 받지 않고 그 계정으로 로그인되고 역할은 `admin` 이다

### Requirement: 구성원 계정은 관리자가 메일 없이 만든다

시스템은 관리자가 메일 없이 구성원을 만들고 역할을 줄 수 있게 해야 한다(SHALL). 비밀번호는 8자 이상이고 원장에 남지 않는다. 비활성화한 구성원은 로그인하지 못하고 읽거나 쓰지 못한다. 관리자는 자기 자신을 잠글 수 없다.

#### Scenario: 직원을 추가하면 메일 없이 바로 로그인한다

- **WHEN** 김대표가 설정의 구성원에서 박영업을 영업 역할로 추가한다
- **THEN** 비밀번호가 짧으면 「8자 이상」 이 보이고 고치면 표에 추가된다
- **AND** 박영업은 메일 없이 바로 로그인하고, 비밀번호가 틀리면 「이메일 또는 비밀번호가 맞지 않습니다」 다

#### Scenario: 직원에게는 관리자 동작이 보이지 않는다

- **WHEN** 박영업이 구성원, 백업, 원장 화면을 연다
- **THEN** 구성원 추가와 비활성화 버튼이 없고 백업 버튼이 꺼져 있으며 무결성 검증 버튼이 없다

#### Scenario: 비활성화한 직원은 더 로그인하지 못한다

- **WHEN** 김대표가 사유를 적어 박영업을 비활성화한다
- **THEN** 표에 「비활성」 이 보이고 박영업의 로그인은 「비활성화된 계정」 으로 막힌다
- **AND** 이미 받은 토큰으로 쓰면 `ERP_FORBIDDEN`, 읽으면 0건이다

#### Scenario: 관리자는 자기 자신을 잠글 수 없다

- **WHEN** 김대표가 자기 구성원 문서를 비활성화하거나 자기 관리자 역할을 뺀다
- **THEN** 둘 다 `ERP_SELF_LOCKOUT` 으로 거부된다

#### Scenario: 비밀번호는 원장에 남지 않는다

- **WHEN** 구성원을 만든 뒤 원장에서 비밀번호를 찾는다
- **THEN** 나오지 않는다

### Requirement: 공개 키만으로는 아무것도 읽거나 쓸 수 없다

시스템은 공개 키만 가진 호출자에게 `erp_status`, `erp_bootstrap`, `erp_mcp`, `erp_portal_*` 밖의 공개 함수와 모든 뷰를 닫아야 한다(SHALL). 내부 스키마는 API 로 닿지 않고 내부 함수는 공개 키에게 닫혀 있으며, 로그인한 구성원에게도 역할 확인 함수 넷만 열려 있다. 로그인했어도 구성원이 아니면 0건이고 명령은 거부된다. 회사가 생긴 뒤에는 자가 가입이 막힌다.

#### Scenario: 공개 키만으로는 읽거나 쓰지 못한다

- **WHEN** 공개 키만으로 `erp_records`, `erp_events`, `erp_members` 를 읽거나 `erp_command` 를 부른다
- **THEN** 읽기는 HTTP 401 또는 403, 명령은 권한 오류다

#### Scenario: 허용된 공개 함수 밖은 닫혀 있다

- **WHEN** 설치된 DB 의 함수 권한을 살핀다
- **THEN** 공개 키가 부를 수 있는 공개 함수는 `erp_status`, `erp_bootstrap`, `erp_mcp`, `erp_portal_*` 뿐이다
- **AND** 내부 함수는 공개 키에게 모두 닫혀 있고 구성원에게는 역할 확인 함수 넷만 열려 있다

#### Scenario: 내부 스키마는 REST 로 닿지 않는다

- **WHEN** 김대표의 로그인 토큰으로 `Accept-Profile: erp` 를 붙여 원장을 읽는다
- **THEN** 406 이다

#### Scenario: 로그인했어도 구성원이 아니면 읽을 수 없다

- **WHEN** 이 회사 구성원이 아닌 사용자가 로그인 토큰으로 문서·원장·카탈로그를 읽고 문서를 만든다
- **THEN** 문서와 원장은 0건, 카탈로그는 빈 목록, 명령은 `ERP_FORBIDDEN` 이다

#### Scenario: 회사가 생긴 뒤에는 자가 가입이 막힌다

- **WHEN** 회사가 있는 프로젝트에 공개 키로 가입하거나 계정을 직접 넣는다
- **THEN** 가입은 400 이상, 직접 넣기는 `ERP_SIGNUP_CLOSED` 로 막힌다
- **AND** 관리자는 구성원을 그대로 추가할 수 있다

### Requirement: 앱은 어느 정적 경로에서나 제3자 없이 동작한다

시스템은 빌드 결과를 어느 경로에 올려도 모든 자산을 그 아래에서 읽어야 한다(SHALL). 글꼴은 자체 제공이다. CSP 는 스크립트를 자기 출처로만, 연결을 자기 출처와 Supabase 로만 허용한다. 소스와 빌드에는 인라인 스크립트, `v-html`, `eval`, 하드코딩한 키, 분석 도구가 없다.

#### Scenario: 어느 경로에 올려도 동작한다

- **WHEN** 앱을 `/uengine-erp/app/` 아래에 올려 연다
- **THEN** 연결 화면이 나오고 모든 요청이 같은 호스트의 그 경로 아래에서 오며 콘솔 오류가 없다

#### Scenario: 글꼴은 자체 제공 Pretendard 로 그려진다

- **WHEN** 앱을 연다
- **THEN** 본문 글꼴이 Pretendard 이고 글꼴 파일이 자체 경로에서 200 으로 온다

#### Scenario: CSP 가 정해진 그대로이고 인라인 스크립트가 없다

- **WHEN** 빌드된 `index.html` 을 살핀다
- **THEN** `default-src`, `script-src` 는 `'self'`, `connect-src` 는 `'self'` 와 `https://*.supabase.co`, `wss://*.supabase.co`, 로컬 주소뿐이다
- **AND** 인라인 스크립트와 인라인 이벤트 속성, CDN 주소가 없다

#### Scenario: 소스와 빌드에 위험한 것이 없다

- **WHEN** 앱 소스와 빌드 결과를 살핀다
- **THEN** `v-html`, `innerHTML`, `eval`, 하드코딩한 키, 분석 도구, 금지된 제품 이름이 없다

### Requirement: 초대 링크로 접속 정보를 넘기고 접속을 해제할 수 있다

시스템은 초대 링크로 주소와 공개 키를 넘기되 사용자가 주소를 확인한 뒤에야 저장해야 한다(SHALL). 비밀 키가 든 링크는 거부하고 주소에서 지운다. 접속을 해제하면 이 브라우저에서 토큰과 접속 정보가 사라진다.

#### Scenario: 초대 링크는 주소를 확인시키고 접속 정보를 넘긴다

- **WHEN** 이재고가 초대 링크를 연다
- **THEN** 프로젝트 주소가 보이고 누르기 전에는 저장되지 않는다
- **AND** 누르면 로그인 화면이 나오고 회사 이름은 로그인 전까지 보이지 않는다. 예전 anon 키도 받는다

#### Scenario: 비밀 키가 든 초대 링크는 거부하고 주소에서 지운다

- **WHEN** 비밀 키가 든 초대 링크를 연다
- **THEN** 「이 키는 공개하면 안 되는 키입니다」 가 보이고 주소와 브라우저 저장소에 그 값이 없다

#### Scenario: 접속 해제하면 토큰과 접속 정보가 사라진다

- **WHEN** 김대표가 접속·보안 화면에서 초대 링크를 복사하고 접속 해제를 확인한다
- **THEN** 링크의 키는 화면에서 가려져 있고 복사하면 공개 키가 들어 있으며, 「우리 서버로 오지 않습니다」 안내가 보인다
- **AND** 해제하면 설치 화면으로 가고 이 브라우저의 접속 정보와 토큰이 없다. 계정은 그대로 쓸 수 있다

### Requirement: 프로젝트가 멈추면 안내하고 살아나면 돌아온다

시스템은 Supabase 프로젝트에 닿지 못하거나 일시 중지 응답(540)이 오면 재시도와 재개 방법을 안내해야 한다(SHALL). 살아나면 있던 화면으로 돌아간다.

#### Scenario: 프로젝트가 일시 중지되면 안내하고 살아나면 돌아온다

- **WHEN** 원장을 보던 중 API 에 닿지 못하게 되어 새로 고친다
- **THEN** 연결 안 됨 화면에 「7일 동안 활동이 없으면 일시 중지」 와 대시보드 링크, 재시도가 보인다
- **AND** 다시 닿으면 재시도로 원장 화면에 돌아온다

#### Scenario: 일시 중지 응답도 같은 안내로 처리한다

- **WHEN** API 가 540 으로 답한다
- **THEN** 같은 연결 안 됨 화면으로 간다

### Requirement: 무료 플랜의 한도를 보여 주고 원장을 내려받게 한다

시스템은 DB 사용량을 500 MB 대비로 보여 주고 80% 부터 경고해야 한다(SHALL). 자동 백업이 없는 플랜이므로 관리자는 원장을 묶음으로 받아 파일로 저장할 수 있다. 회사 정보는 관리자가 고치며 통화와 자릿수는 읽기 전용이다.

#### Scenario: 사용량은 500 MB 대비 막대와 안내를 보여 준다

- **WHEN** 김대표가 설정의 사용량을 연다
- **THEN** 「/ 500.0 MB」 와 막대, 「자동 백업이 없습니다」, 「7일 동안 활동이 없으면」 이 보인다

#### Scenario: 한도의 80% 를 넘으면 경고한다

- **WHEN** DB 사용량이 500 MB 의 80% 이상인 회사가 사용량을 연다
- **THEN** 「한도에 가까워지고 있습니다」 안내가 보인다

#### Scenario: 백업은 묶음으로 받아 NDJSON.gz 파일로 저장한다

- **WHEN** 김대표가 설정의 백업을 누른다
- **THEN** `uengine-erp_….ndjson.gz` 파일이 내려받아지고 「받았습니다」 가 보인다
- **AND** 파일의 첫 줄은 머리글, 마지막 줄은 문서 번호 상태이고 그 사이 이벤트 수는 원장과 같으며 `seq` 순서다

#### Scenario: 회사 정보를 고치면 표시줄에 바로 반영된다

- **WHEN** 김대표가 설정의 회사 정보에서 대표자와 회사명을 고쳐 저장한다
- **THEN** 통화는 입력 칸 없이 `KRW` 로 보이고 표시줄의 회사 이름이 바로 바뀐다

### Requirement: 가상 회사로 시작할 수 있다

시스템은 회사를 만들 때 가상 회사 가온가전의 3년을 사람이 쓰는 것과 같은 명령으로 넣는 선택을 제공해야 한다(SHALL). 고르지 않으면 데모 코드를 내려받지 않는다. 묶음으로 보내 진행을 보여 주고, 시간 제한에 걸리면 묶음을 나누며, 멈춰도 이어서 만들거나 거기까지로 끝낼 수 있다. 업무 데이터가 있는 회사에는 넣을 수 없고 관리자만 할 수 있다.

#### Scenario: 고르면 용량을 알리고 고르지 않으면 데모 코드를 받지 않는다

- **WHEN** 김대표가 회사 만들기 화면을 열고 가상 회사를 고른다
- **THEN** 처음에는 실제 회사가 선택되어 있고 용량 안내가 없다
- **AND** 고르면 「약 250 MB」 가 보이고 회사명 칸이 사라지며, 고르기만 해서는 스크립트를 더 받지 않는다

#### Scenario: 묶음으로 보내며 진행을 보여 주고 오류와 시간 제한을 스스로 넘긴다

- **WHEN** 김대표가 가상 회사를 만드는 동안 디버거 확장의 일시 오류와 시간 제한(`57014`)이 한 번씩 난다
- **THEN** 「… 까지 만들었습니다」 진행이 보이고 끝나면 홈으로 간다
- **AND** 묶음은 약 300개씩이고 일시 오류는 같은 묶음을 다시, 시간 제한은 반으로 나눠 보낸다

#### Scenario: 다 만들면 다섯 모듈이 켜진 가상 회사다

- **WHEN** 가상 회사가 다 만들어진다
- **THEN** 회사 이름 「가온가전(데모)」 과 「가상 회사입니다」 표시가 보이고 다섯 모듈이 모두 켜져 있다
- **AND** 주문 목록이 보이고 시산표는 「차변과 대변이 맞습니다.」, `stat_sales` 는 「사용 가능」 이며 전달이 다시 돈다
- **AND** 첫 이벤트의 날짜는 이야기의 첫날이다

#### Scenario: 가상 회사는 실제 명령으로 만들어져 숫자가 맞는다

- **WHEN** 짧은 이야기로 가상 회사를 끝까지 만든다
- **THEN** 멈춘 구독이 없고 현재 상태는 원장 재생과 같으며 차변과 대변이 같다
- **AND** 음수 재고가 없고 일은 이야기의 사람(박영업 등)의 이름으로, 출처 `demo` 로 남으며 첫 주문 확정의 날짜는 2023-11 이다

#### Scenario: 고칠 수 없는 오류는 다시 시도하고 탭을 닫아도 이어 간다

- **WHEN** 묶음이 고칠 수 없는 오류로 실패하고, 다시 시도한 묶음의 응답을 잃고, 김대표가 탭을 다시 연다
- **THEN** 「요청을 처리하지 못했습니다」 와 다시 시도가 보인다
- **AND** 진행은 이 브라우저에 남아 있어 보낸 곳 다음부터 이어 가고, 끝나면 음수 재고가 없으며 진행 기록이 지워진다

#### Scenario: 중간에 멈춘 회사는 관리자에게 알리고 거기까지로 끝낼 수 있다

- **WHEN** 가상 회사를 만들다 멈춘 채 김대표가 홈으로 간다
- **THEN** 「가상 회사를 만들다 멈췄습니다」 가 보이고 이미 켠 모듈이 메뉴에 나온다
- **AND** 이어 만들기를 다시 시도할 수 있고, 여기까지로 끝내면 알림이 사라지고 가상 회사 표시는 남으며 전달이 다시 돈다

#### Scenario: 실제 회사에는 가상 회사 표시도 데모 코드도 없다

- **WHEN** 김대표가 실제 회사로 시작하고 가상 회사 만들기 주소를 직접 친다
- **THEN** 홈으로 돌아가고 가상 회사 표시가 없으며 데모 코드를 받지 않는다

#### Scenario: 열기 전에는 단계를 넣을 수 없고 관리자만 연다

- **WHEN** 가상 회사를 열기 전에 단계를 보내고, 박영업이 열기를 부른다
- **THEN** 앞은 `ERP_INVALID`, 뒤는 `ERP_FORBIDDEN` 이다
- **AND** 김대표가 열면 다 만들 때까지 전달이 멈춘다

#### Scenario: 업무 데이터가 있는 회사는 가상 회사가 될 수 없다

- **WHEN** 주문이 있는 회사에서 가상 회사를 열거나, 닫힌 뒤 단계를 보낸다
- **THEN** 둘 다 `ERP_INVALID` 이고 전달은 멈추지 않는다

## 성능·비용 제약

무료 플랜은 DB 500 MB, API 문장 8초, 자동 백업 없음, 7일 비활성 시 일시 중지, 기본 SMTP 팀 멤버 전용이다. 다섯 모듈로 만든 가상 회사(3년, 주문 3,287건, 이벤트 43,432건)의 DB 전체는 170 MB, 이벤트 하나에 약 3.3 KB 이고, 이 크기면 500 MB 에 이벤트 약 13만 건, 주문 약 1만 건이 들어간다. 클라우드에서는 재지 않았다.
