# 기초데이터와 가격

## Purpose

회사가 설치 직후부터 단위·세금·결제 조건·창고 같은 기본 데이터로 일을 시작하고, 연락처·제품·변형·가격표를 역할에 맞게 관리할 수 있음을 보장한다. 가격과 세금과 할부는 저장된 규칙에서 언제나 같은 값으로 계산되고, 사람이 입력한 가격은 통화 자릿수로 잘리지 않는다. 판매 주문 줄에서 이 가격이 어떻게 쓰이는지는 판매 스펙(`erp-sales`)이 다룬다.

## Requirements

### Requirement: 새 회사는 바로 쓸 수 있는 기본 데이터로 시작한다

시스템은 회사를 만들 때 사용자의 명령과 같은 경로로 다음 기본 데이터를 만들어야 한다(SHALL).

- 단위: `개`, `다스`, `g`, `kg`, `톤`, `시간`, `일`, `cm`, `m`, `km`, `mL`, `L`
- 세금: `부가세 10% 매출`, `부가세 10% 매입`, `영세율 매출`, `영세율 매입`, `면세 매출`, `면세 매입`
- 결제 조건: `즉시`, `15일`, `30일`, `30%선금+잔금 60일`
- 계정과목: `현금`, `보통예금`, `외상매출금`, `선급금`, `부가세대급금`, `상품`, `비품`, `외상매입금`, `부가세예수금`, `선수금`, `자본금`, `이월이익잉여금`, `상품매출`, `잡이익`, `상품매출원가`, `대손상각비`, `재고자산감모손실`, `잡손실`
- 분류 `기본 분류`, 위치 `재고`, `공급사`, `고객`, `재고조정`, `폐기`, 코드 `WH` 창고, `기본 가격표`

#### Scenario: 새 회사에 세금·결제 조건·창고·가격표가 준비되어 있다

- **WHEN** 김대표가 새 회사를 만든다
- **THEN** 세금 여섯 개가 있고 `부가세 10% 매출` 의 세율은 10, 세금 계정은 `부가세예수금` 이며 `영세율 매입` 의 `scope` 는 `purchase` 다
- **AND** 결제 조건 네 개가 있고 `30%선금+잔금 60일` 의 줄은 `percent` 30 에 0일, `percent` 70 에 60일이다
- **AND** 위치 다섯 개가 있고 `폐기` 는 `scrap` 이 켜져 있으며 `고객` 의 `usage` 는 `customer` 다
- **AND** 코드 `WH` 창고의 재고 위치는 `재고` 다
- **AND** `기본 분류` 의 매출 계정은 `상품매출`, `외상매출금` 의 유형은 `asset_receivable`, `kg` 의 분류는 `weight` 다
- **AND** 회사의 `default_sale_tax_id` 는 `부가세 10% 매출`, `default_purchase_tax_id` 는 `부가세 10% 매입` 이다
- **AND** `기본 가격표` 의 통화는 회사 통화(`KRW`, 달러 회사면 `USD`)이고 규칙이 없다
- **AND** 기본 데이터 이벤트는 40건을 넘고 처음부터 끝까지 2초가 걸리지 않는다

#### Scenario: 기초데이터 메뉴에서 시드 세금과 계정과목을 본다

- **WHEN** 김대표가 로그인해 `기초데이터` 메뉴를 열고 `세금` 을 고른다
- **THEN** 메뉴에 `단위` 가 보이고 세금 목록에 `부가세` 가 들어간 행이 보인다
- **AND** `회계` 메뉴의 `계정과목` 목록에 행이 보인다
- **AND** `판매` 메뉴에는 `연락처` 가 보이고, 판매만 켠 회사에서도 `판매` 메뉴에 `연락처`, `제품`, `가격표` 가 보인다

### Requirement: 재설치와 재시드는 쌓인 데이터를 바꾸지 않는다

시스템은 설치 SQL 이나 기본 데이터 단계를 다시 실행해도 이벤트와 레코드를 늘리거나 사용자가 바꾼 값을 되돌리지 않아야 한다(SHALL). 기본 데이터는 한 번도 없던 것만 만든다. 기본 데이터 단계는 회사를 만들 때 돌며 화면에서 따로 부르는 동작은 없다.

#### Scenario: 기본 데이터를 다시 넣어도 바꾼 이름이 돌아오지 않는다

- **WHEN** 정회계가 시드 결제 조건 `15일` 의 이름을 `보름` 으로 바꾼 뒤 기본 데이터 단계가 다시 돈다
- **THEN** 원장의 이벤트 수가 늘지 않는다
- **AND** 그 결제 조건의 이름은 `보름` 그대로다
- **AND** `기본 가격표` 의 이벤트도 늘지 않는다
- **AND** 사용자가 지운 시드도 다시 생기지 않는다

#### Scenario: 설치 스크립트를 다시 실행해도 데이터가 그대로다

- **WHEN** 김대표가 쓰고 있는 회사에 설치 SQL 을 두 번 더 실행한다
- **THEN** 이벤트, 레코드, 변형, 등록된 기본 데이터 단계의 수가 실행 전과 같다
- **AND** 회사 정보에는 `default_sale_tax_id` 항목이 그대로 있다

### Requirement: 기초데이터 쓰기는 유형마다 정해진 역할만 할 수 있고 읽기는 구성원 모두 할 수 있다

시스템은 아래 역할과 `admin` 에게만 쓰기를 허용하고, 그 밖의 쓰기는 `ERP_FORBIDDEN` 으로 거부해야 한다(SHALL). 연락처 합치기(`merge`)의 역할은 연락처 쓰기 역할과 같다.

| 유형 | 쓸 수 있는 역할 |
|---|---|
| 연락처 `partner`, 태그 `tag` | `sales`, `purchase`, `accounting` |
| 제품 `product`, 제품 속성 `attribute`, 단위 `uom` | `sales`, `purchase`, `inventory` |
| 제품 분류 `product_category` | `sales`, `purchase`, `inventory`, `accounting` |
| 세금 `tax`, 세금 조정 `fiscal_position`, 결제 조건 `payment_term`, 계정과목 `account` | `accounting` |
| 창고 `warehouse`, 위치 `location` | `inventory` |
| 가격표 `pricelist` | `sales` |

#### Scenario: 역할에 없는 쓰기는 거부되고 역할에 맞는 쓰기는 통과한다

- **WHEN** 구성원이 기초데이터를 만들거나 합치는 명령을 보낸다
- **THEN** 박영업의 세금·계정과목·창고 생성은 `ERP_FORBIDDEN` 으로 거부된다
- **AND** 정회계의 위치 생성, 이재고의 연락처 생성, 최구매의 가격표 생성도 `ERP_FORBIDDEN` 으로 거부된다
- **AND** 조회(`viewer`) 역할 구성원의 연락처·제품 생성과 연락처 합치기도 `ERP_FORBIDDEN` 으로 거부된다
- **AND** 박영업의 연락처 생성·합치기와 가격표 생성, 정회계의 세금 생성, 이재고의 위치·제품 생성은 통과한다

#### Scenario: 구성원은 모두 읽고 회사 밖에서는 변형을 볼 수 없다

- **WHEN** 조회 역할 구성원이 제품·세금·계정과목·연락처 레코드와 `erp_variants` 를 읽는다
- **THEN** 행이 돌아온다
- **AND** 로그인하지 않은 요청의 `erp_variants` 읽기는 `permission denied` 로 거부된다
- **AND** 회사 구성원이 아닌 계정에게 `erp_variants` 는 0행이다
- **AND** 구성원도 변형 목록을 직접 지우거나 변형을 만드는 내부 동작을 직접 부르면 `permission denied` 로 거부된다

### Requirement: 저장할 때 값의 형식과 참조를 검사한다

시스템은 잘못된 값을 데이터베이스 오류가 아니라 업무 오류 코드로 거부해야 한다(SHALL). 카탈로그에 없는 항목과 줄 칸은 오류 없이 버리고 저장하지 않는다(MUST).

#### Scenario: 형식이 틀린 값은 업무 오류로 거부된다

- **WHEN** 박영업이 제품을 잘못된 값으로 저장한다
- **THEN** 제품 분류가 uuid 가 아니거나 없는 레코드이면 `ERP_INVALID_REF`, 매출 세금 목록에 없는 세금이 들어 있어도 `ERP_INVALID_REF` 로 거부된다
- **AND** 매출 세금이 목록이 아닌 글자이거나, 판매가가 `free` 이거나, 고객 납기 일수가 1.5 이거나, 제품명이 객체이면 `ERP_INVALID` 로 거부된다
- **AND** 제품명이 공백뿐이면 `ERP_REQUIRED` 로 거부된다
- **AND** 공급사 줄이 목록이 아니거나 줄이 객체가 아니면 `ERP_INVALID`, 공급사가 없는 줄은 `ERP_REQUIRED` 로 거부된다
- **AND** 공급사 줄의 날짜가 `2026-02-30` 이거나 줄 `id` 가 uuid 가 아니거나 같은 `id` 가 두 번 나오면 `ERP_INVALID` 로 거부된다
- **AND** 이미 있는 레코드의 id 로 새로 만들면 유형이 달라도 `ERP_DUPLICATE` 로 거부된다

#### Scenario: 카탈로그에 없는 항목과 줄 칸은 저장되지 않는다

- **WHEN** 정회계가 결제 조건을 만들며 `secret`, `active: false`, 줄의 `hacker` 를 함께 보낸다
- **THEN** 오류 없이 저장되고 `secret` 과 `hacker` 는 남지 않으며 `active` 는 `true` 다
- **AND** 줄의 칸은 `id`, `value`, `amount`, `days`, `delay_type`, `days_next_month` 뿐이다
- **AND** 제품을 만들며 보낸 모르는 항목과 공급사 줄의 모르는 칸도 남지 않는다

### Requirement: 단위는 같은 분류 안에서 배수로 환산한다

시스템은 `ratio` 로 수량을 환산하고 대상 단위의 `rounding` 에 맞춰 반은 올려 반올림해야 한다(SHALL). 다른 분류로는 환산하지 않는다(MUST). 환산은 공개 함수로 따로 부르지 않고 가격 조회와 문서 줄에서 쓰인다.

#### Scenario: 단위는 같은 분류 안에서 배수로 환산하고 대상 단위에 맞춰 반올림한다

- **WHEN** 시드 단위로 수량을 환산한다
- **THEN** 2 `다스` 는 24 `개`, 18 `개` 는 1.5 `다스`, 1500 `g` 은 1.5 `kg`, 1 `g` 은 0.001 `kg`, 1 `개` 는 0.08 `다스`, 5 `개` 는 5 `개` 다
- **AND** `kg` 에서 `시간` 으로 바꾸면 `ERP_UOM`, 없는 단위로 바꾸면 `ERP_NOT_FOUND` 로 거부된다
- **AND** `ratio` 가 0 이거나 `rounding` 이 -1 인 단위는 `ERP_INVALID` 로 저장되지 않는다
- **AND** `ratio` 24 인 새 단위 `상자` 1개는 2 `다스` 다
- **AND** 제품에 쓰인 `상자` 의 분류를 `weight` 로 바꾸면 `ERP_IN_USE` 로 거부되고 `ratio` 를 48 로 바꾸는 것은 통과한다

### Requirement: 분류·계정과목·창고·위치와 상위 관계는 어긋나지 않는다

시스템은 분류·위치·연락처의 상위를 따라가 자기 자신으로 돌아오는 변경, 겹치는 계정과목 코드와 창고 코드, 사내 위치가 아닌 창고 재고 위치를 거부해야 한다(SHALL). 위치의 `usage` 는 `view`, `internal`, `customer`, `supplier`, `inventory`, `transit` 중 하나다.

#### Scenario: 상위 순환과 코드 겹침과 잘못된 재고 위치는 거부된다

- **WHEN** 이재고가 제품 분류의 상위를 자기 자신이나 자기 하위 분류로 바꾼다
- **THEN** `ERP_INVALID` 로 거부된다
- **AND** 위치와 연락처의 상위를 자기 하위로 바꿔도 `ERP_INVALID` 로 거부된다
- **AND** 정회계가 시드 `외상매출금` 이 쓰는 코드 `108` 로 계정과목을 만들면 `ERP_DUPLICATE`, 유형이 `bogus` 이면 `ERP_INVALID`, 유형이 없으면 `ERP_REQUIRED` 로 거부된다
- **AND** 이재고가 재고 위치 없이 창고를 만들면 `ERP_REQUIRED`, 재고 위치가 `고객` 이면 `ERP_INVALID`, 코드가 `WH` 이면 `ERP_DUPLICATE` 로 거부된다

### Requirement: 세금은 포함 여부, 그룹, 계산 순서를 갖는다

시스템은 세금의 `amount_type`(`percent`, `fixed`, `division`, `group`)과 `price_include`, `include_base_amount`, `is_base_affected`, `sequence` 대로 계산해야 한다(SHALL). 세금은 줄에 고른 순서가 아니라 `sequence`, 그다음 먼저 만든 세금 순서로 적용한다. 그룹은 하위 세금으로 풀리고, 같은 세금이 두 번 닿아도 한 번만 계산한다. 음수 세율은 원천세로 허용한다.

#### Scenario: 새 세금은 회사 설정을 따르되 직접 밝히면 그 값을 쓴다

- **WHEN** 김대표가 회사 정보의 `새 세금은 가격에 포함`(`default_price_include`)을 켜고 정회계가 세금 두 개를 만든다
- **THEN** 포함 여부를 밝히지 않은 세금의 `price_include` 는 `true` 다
- **AND** `price_include: false` 로 만든 세금은 `false` 다

#### Scenario: 세금 그룹은 하위 세금으로 풀리고 줄에는 그룹이 남는다

- **WHEN** 정회계가 별도 10%, 별도 5% 세금을 묶은 그룹을 만들어 1000원 한 개에 매긴다
- **THEN** `subtotal` 1000, `tax` 150, `total` 1150 이다
- **AND** `tax_ids` 에는 그룹만 남고 `taxes` 에는 하위 세금의 100, 50 이 나온다
- **AND** 그룹과 그 안의 5% 세금을 함께 골라도 `tax` 는 150 이다
- **AND** 포함 10%, 포함 5% 를 묶은 그룹을 1150원에 매기면 `subtotal` 1000, `tax` 150, `total` 1150 이다
- **AND** 하위 세금이 없는 그룹의 `tax` 는 0 이다
- **AND** 그룹 안에 그룹을 넣거나, 그룹에 든 세금을 그룹으로 바꾸거나, 적용 범위가 다른 세금을 넣으면 `ERP_INVALID` 로 거부된다
- **AND** 별도 10% 와 별도 -3% 를 함께 1000원에 매기면 `tax` 는 70 이다

#### Scenario: 계산 순서와 기준 포함이 세액을 정한다

- **WHEN** 고정 100(`include_base_amount`)과 별도 10% 를 1000원 한 개에 매긴다
- **THEN** 고정 세금은 `base` 1000 에 100, 비율 세금은 `base` 1100 에 110 이고 `tax` 210, `total` 1210 이다
- **AND** 포함 10%(`include_base_amount`)와 별도 10% 를 1100원에 매기면 `subtotal` 1000, `tax` 210, `total` 1210 이다
- **AND** 앞 세금이 `include_base_amount` 여도 뒤 세금의 `is_base_affected` 가 꺼져 있으면 별도 10% 두 개의 `tax` 는 200 이다
- **AND** 먼저 만든 별도 10% 와 나중에 만든 별도 10%(`include_base_amount`)는 줄에 거꾸로 골라도 먼저 만든 쪽부터 계산해 `tax` 200 이다
- **AND** 나중 세금의 `sequence` 가 1, 앞 세금이 5 이면 `sequence` 가 먼저여서 `tax` 210 이다

### Requirement: 세금 금액은 줄 단위로 계산한다

시스템은 단가·수량·할인·세금 목록·세금 조정을 받아 `subtotal`, `tax`, `total`, `taxes`(`tax_id`, `name`, `base`, `amount`, `account_id`), `tax_ids`, `price_unit` 을 돌려주어야 한다(SHALL). 줄 합계(단가 × 수량 × (1 - 할인))를 회사 통화 자릿수로 먼저 반올림하고, 세금마다 반올림하며, `subtotal` 은 포함 세금을 뺀 나머지다. 이 계산은 구성원이 직접 부르는 공개 함수가 아니고 문서 줄의 금액을 만들 때 쓰인다.

#### Scenario: 별도 세금은 할인 뒤 줄 합계에 매기고 고정 금액 세금은 수량을 곱한다

- **WHEN** 19900원 3개에 `부가세 10% 매출` 을 매긴다
- **THEN** `subtotal` 59700, `tax` 5970, `total` 65670 이고 세금의 `account_id` 는 `부가세예수금` 이다
- **AND** `면세 매출` 이면 `subtotal` 59700, `tax` 0, `total` 59700 이다
- **AND** 1000원 2개, 할인 10%, 별도 10% 이면 `subtotal` 1800, `tax` 180, `total` 1980 이다
- **AND** 별도 10%, 별도 5% 를 1000원에 매기면 서로 곱하지 않아 `tax` 150, 둘 다 `base` 1000 이다
- **AND** 세금 없이 100원 2개이면 `subtotal` 200, `tax` 0, `total` 200, `taxes` 와 `tax_ids` 는 비어 있고 `price_unit` 은 100 이다
- **AND** 고정 50 을 1000원 3개에 매기면 `tax` 150, `total` 3150 이다
- **AND** 고정 100 을 1000원 2개, 할인 100% 에 매기면 `subtotal` 0, `tax` 200, `total` 200 이다

#### Scenario: 포함 세금은 줄 합계에서 빠지고 여럿이면 한 번에 나눈다

- **WHEN** 포함 10% 를 11000원 한 개에 매긴다
- **THEN** `subtotal` 10000, `tax` 1000, `total` 11000 이다
- **AND** 999원이면 `subtotal` 908, `tax` 91, `total` 999 로 합계는 단가 그대로다
- **AND** 포함 10%, 포함 5% 를 1150원에 매기면 `subtotal` 1000, `tax` 150, `total` 1150 이다
- **AND** 같은 세금을 110원에 매기면 세금은 각각 10, 5 이고 `subtotal` 95, `total` 110 이다
- **AND** 포함 10%, 별도 5% 를 110원에 매기면 `subtotal` 100, `tax` 15, `total` 115 이다
- **AND** 포함 고정 100, 포함 10% 를 1200원에 매기면 고정 금액을 먼저 빼서 `subtotal` 1000, `tax` 200, `total` 1200 이다
- **AND** 포함 고정 100 을 1100원 2개에 매기면 `subtotal` 2000, `tax` 200, `total` 2200 이다
- **AND** 포함 고정 100 을 50원에 매기면 `subtotal` -50, `tax` 100, `total` 50 이다

#### Scenario: 줄 합계를 먼저 반올림하고 반은 0 에서 멀어지는 쪽으로 간다

- **WHEN** 소수 둘째 자리까지 쓰는 달러 회사에서 33.33 3개에 별도 10% 를 매긴다
- **THEN** `subtotal` 99.99, `tax` 10, `total` 109.99 로 단가별이 아니라 줄 전체로 반올림된다
- **AND** 원화 회사에서 1005원에 별도 10% 를 매기면 `tax` 는 101, `total` 은 1106 이다
- **AND** 수량이 -1 이면 `subtotal` -1005, `tax` -101, `total` -1106 으로 대칭이다
- **AND** 원화 회사에서 1.5원 3개에 별도 10% 를 매기면 `subtotal` 5, `tax` 1, `total` 6 이다

#### Scenario: 나눗셈 세금은 세금 포함 금액에 대한 비율이다

- **WHEN** 별도 나눗셈 10% 를 900원 한 개에 매긴다
- **THEN** `subtotal` 900, `tax` 100, `total` 1000 이다
- **AND** 포함 나눗셈 10% 를 1000원에 매기면 `subtotal` 900, `tax` 100, `total` 1000 이다
- **AND** 별도 나눗셈 10%, 5% 를 800원에 매기면 나누는 수를 합쳐 세금은 각각 94, 47 이고 `total` 은 941 이다
- **AND** 별도 나눗셈 10% 와 별도 비율 10% 를 900원에 매기면 세금은 각각 100, 90 이고 `total` 은 1090 이다
- **AND** 세율이 100 인 나눗셈 세금은 `ERP_INVALID` 로 저장되지 않는다

### Requirement: 세금 조정은 세금을 바꾸고 전부 포함 세금일 때만 단가를 바꾼다

시스템은 세금 조정의 `tax_map` 으로 줄의 세금을 바꾸어야 한다(SHALL). 대상이 비면 세금을 빼고, 한 세금이 여럿으로 갈 수 있다. 원래 세금이 전부 포함 세금일 때 조정으로 세금이 바뀌면 원래 세금을 빼고 새 포함 세금을 더한 단가를 `price_unit` 으로 돌려준다. 그 밖에는 `price_unit` 은 들어온 값 그대로다.

#### Scenario: 세금 조정은 세금을 바꾸거나 빼거나 여럿으로 나눈다

- **WHEN** 정회계가 별도 10% 를 0% 세금으로 바꾸는 세금 조정을 만들어 1000원 한 개에 적용한다
- **THEN** `subtotal` 1000, `tax` 0, `total` 1000 이고 `tax_ids` 는 0% 세금이다
- **AND** 대상이 빈 줄이면 세금이 빠져 `taxes` 와 `tax_ids` 가 비고 `total` 은 1000 이다
- **AND** 별도 10% 를 1%, 2% 두 세금으로 나누고 대상이 아닌 3% 를 그대로 두면 `tax` 는 60 이고 `tax_ids` 는 세 세금이다
- **AND** 원래 세금이 없는 줄은 `ERP_REQUIRED`, 없는 세금을 가리키는 줄은 `ERP_INVALID_REF` 로 저장되지 않는다
- **AND** 대응 줄을 비워 저장하면 `FiscalPositionTaxMapRemoved` 가 남는다

#### Scenario: 전부 포함 세금이면 조정이 단가도 바꾼다

- **WHEN** 포함 10% 를 0% 세금으로 바꾸는 조정을 1100원 한 개에 적용한다
- **THEN** `subtotal` 1000, `tax` 0, `total` 1000 이고 결과 `price_unit` 은 1000 이다
- **AND** 대상이 빈 조정을 999원에 적용하면 `subtotal` 908, `total` 908, `price_unit` 908.1818181818 이다
- **AND** 포함 5% 로 바꾸는 조정을 1100원에 적용하면 `subtotal` 1000, `tax` 50, `total` 1050, `price_unit` 1050 이다
- **AND** 같은 조정을 999원에 적용하면 `subtotal` 909, `tax` 45, `total` 954, `price_unit` 953.5909090909 이다
- **AND** 결과 단가 1000 과 바뀐 0% 세금으로 다시 계산해도 `subtotal` 1000, `tax` 0, `total` 1000, `price_unit` 1000 이다

#### Scenario: 별도 세금이 끼면 조정해도 단가는 그대로다

- **WHEN** 포함 10% 와 별도 5% 가 함께 있는 1100원 줄에 포함 10% 를 0% 로 바꾸는 조정을 적용한다
- **THEN** `subtotal` 1100, `tax` 55, `total` 1155 이고 `price_unit` 은 1100 이다
- **AND** 별도 10% 를 포함 10% 로 바꾸는 조정을 1000원에 적용하면 `subtotal` 909, `tax` 91, `total` 1000 이고 `price_unit` 은 1000 이다

### Requirement: 결제 조건은 저장할 때 줄 규칙을 지킨다

시스템은 비율 줄의 합이 정확히 100 이 아닌 결제 조건을 거부해야 한다(SHALL). 줄이 하나도 없는 조건은 허용한다. 조기 할인은 100% 한 줄인 조건에만 쓴다(MUST).

#### Scenario: 비율 합계가 100 이 아닌 결제 조건은 저장되지 않는다

- **WHEN** 김대표가 `결제 조건` 화면에서 이름 `45일 조건` 에 비율 50 인 줄 하나를 넣고 `저장` 을 누른다
- **THEN** 화면에 서버의 오류 문구가 보이고 `ERP_` 코드는 보이지 않는다
- **AND** 같은 줄을 비율 100, 일수 45 로 고쳐 저장하면 제목이 `45일 조건` 이 되고 오류가 사라진다
- **AND** 비율 90 한 줄, 60 과 50, 고정 금액만 있는 줄, -10 과 110, 고정 -5 와 비율 100 은 `ERP_INVALID` 로 거부된다
- **AND** 방식 `balance`, `installment`, 다음 달 지정일 -5, 32, 기일 기준 `someday` 도 `ERP_INVALID` 로 거부된다
- **AND** 줄이 없는 조건, 일수가 -5 인 줄, 비율 100 과 고정 100 을 함께 둔 조건은 저장된다
- **AND** 저장된 줄은 `id` 를 받고 기일 기준을 밝히지 않으면 `days_after` 다

#### Scenario: 조기 할인은 100% 한 줄에만 쓰고 기한 안에 낼 금액을 계산한다

- **WHEN** 정회계가 100% 30일 한 줄에 조기 할인 2%, 7일을 넣어 저장하고 1100원을 2026-03-15 에 나눈다
- **THEN** 회차는 `due_date` 2026-04-14, `amount` 1100, `discount_date` 2026-03-22, `discount_amount` 1078 이다
- **AND** `discount_mode` 를 밝히지 않으면 `included` 다
- **AND** `excluded` 이고 `untaxed` 가 1000 이면 `discount_amount` 는 1080 이다
- **AND** 50 과 50 두 줄이나 고정과 100 두 줄에 조기 할인을 넣으면 `ERP_INVALID` 로 거부된다
- **AND** 할인율이 0 이거나 기한이 0 또는 -1 이면 `ERP_INVALID` 로 거부된다

### Requirement: 할부는 합이 정확히 맞고 음수 회차가 없다

시스템은 청구 금액과 청구일에서 회차별 `due_date`, `amount` 를 계산해야 한다(SHALL). 비율 줄은 합계의 비율이고 마지막 비율 줄이 나머지를 받는다. 고정 줄은 남은 금액까지만 받아 음수 회차가 생기지 않는다(MUST). 0원이 된 회차도 남는다. 공개 함수 `erp_preview` 로 저장 전에 미리 볼 수 있으며, 그 결과의 `schedule` 을 보여 주는 화면은 없다.

#### Scenario: 비율 할부의 끝수는 마지막 비율 줄이 받아 합이 정확히 맞다

- **WHEN** 30%(0일)와 70%(60일) 조건으로 100000원을 2026-01-10 에 청구한다
- **THEN** 2026-01-10 에 30000, 2026-03-11 에 70000 이다
- **AND** 33.33%, 33.33%, 33.34%(0, 30, 60일) 조건으로 10001원을 2026-01-01 에 청구하면 3333, 3333, 3335 이다
- **AND** 같은 조건으로 1001원을 2026-03-15 에 청구하면 334, 334, 333 이다
- **AND** 고정 100, 50%, 50% 조건으로 1000원을 청구하면 100, 500, 400 이다
- **AND** 100%(5일) 뒤에 고정 3000(15일)이 있는 조건으로 20000원을 2026-01-01 에 청구하면 2026-01-06 에 17000, 2026-01-16 에 3000 이다

#### Scenario: 고정 금액이 합계보다 커도 음수 할부는 없고 환불은 부호를 유지한다

- **WHEN** 고정 100 과 100%(30일) 조건으로 50원을 2026-03-15 에 청구한다
- **THEN** 2026-03-15 에 50, 2026-04-14 에 0 으로 음수 회차가 없다
- **AND** 99% 와 1%(30일) 조건으로 10원을 청구하면 10 과 0 이고 0원 회차도 남는다
- **AND** 30%, 고정 1000, 70% 조건으로 -100000원을 청구하면 -30000, -1000, -69000 이다

#### Scenario: 기일은 기준에 따라 월말과 지정일로 계산하고 조건이 없으면 청구일이다

- **WHEN** `days_after` 30일 줄로 2026-01-31 에 청구한다
- **THEN** 기일은 2026-03-02 다
- **AND** `days_after_end_of_month` 30일이면 2026-03-15 청구는 2026-04-30, 2026-01-31 청구는 2026-03-02 다
- **AND** `days_after_end_of_next_month` 30일이면 2026-03-15 청구는 2026-05-30, 2026-01-31 청구는 2026-03-30 이다
- **AND** `days_end_of_month_on_the` 30일에 지정일 10 이면 2026-03-15 청구는 2026-05-10, 2026-01-31 청구는 2026-04-10 이다
- **AND** 같은 기준으로 2026-03-15 청구는 지정일 0 이면 2026-04-30, 지정일 31 이면 2026-05-31 이다
- **AND** 결제 조건이 없거나 줄이 없는 조건이면 5000원을 2026-04-30 에 청구할 때 그날 한 줄이다

#### Scenario: 지정일이 그 달보다 크면 그 달 말일이다

- **WHEN** `days_end_of_month_on_the` 30일에 지정일 31 인 줄로 1000원을 2026-02-15 에 청구한다
- **THEN** 기일은 2026-04-30 이다

#### Scenario: 저장하기 전에 아무 금액과 날짜로 할부를 미리 본다

- **WHEN** 구성원이 공개 함수 `erp_preview` 에 유형 `payment_term`, 30%(0일)와 70%(60일) 줄, `amount` 1000, `date` 2026-01-10 을 보낸다
- **THEN** `schedule` 은 2026-01-10 에 300, 2026-03-11 에 700 이다

### Requirement: 제품 속성은 변형 방식과 쓰인 값을 지킨다

시스템은 `display_type` `multi` 속성에 `no_variant` 만 허용하고, 제품에 쓰인 뒤에는 `create_variant` 변경과 쓰인 값 삭제와 속성 삭제를 거부해야 한다(SHALL).

#### Scenario: 여러 값 속성은 변형을 만들 수 없고 제품에 쓰인 방식과 값은 바꿀 수 없다

- **WHEN** 박영업이 `display_type` `multi`, `create_variant` `always` 인 속성을 만든다
- **THEN** `ERP_INVALID` 로 거부된다
- **AND** `no_variant` 면 저장되고 나중에 `always` 로 바꾸면 `ERP_INVALID` 로 거부된다
- **AND** 값 이름이 겹치면 `ERP_DUPLICATE`, 이름이 없는 값은 `ERP_REQUIRED` 로 거부된다
- **AND** 제품에 쓰이기 전에는 `create_variant` 를 `dynamic`, `always` 로 바꿀 수 있다
- **AND** 제품에 쓰인 뒤에는 `create_variant` 를 바꾸면 `ERP_IN_USE` 로 거부된다
- **AND** 제품에 쓰인 값을 지우면 `ERP_IN_USE` 로 거부되고 쓰이지 않은 값은 지워진다
- **AND** 제품에 쓰인 속성을 지우면 `ERP_IN_USE` 로 거부된다

### Requirement: 연락처는 회사와 개인을 담고 합침 상태는 직접 쓸 수 없다

시스템은 연락처의 `company_type`, 주소, 태그, 담당 영업, 결제 조건, 가격표 등 카탈로그 항목을 저장해야 한다(SHALL). `merged_into` 와 `active` 는 합치기와 보관으로만 바뀐다(MUST).

#### Scenario: 화면에서 연락처를 만들고 태그·담당자·결제 조건을 고른다

- **WHEN** 김대표가 `태그` 화면에서 `우수 고객` 을 만들고, `연락처` 화면에서 구분 `회사`, 이름 `서울가전상사`, 전화, 이메일을 넣고 태그 `우수 고객`, 결제 조건 `30일`, 담당 영업 `김대표` 를 고른 뒤 `저장` 을 누른다
- **THEN** 제목이 `서울가전상사` 가 되고 태그 칸에 `우수 고객` 이 보이며 이력에 `사람` 이 한 일로 남는다
- **AND** `연락처` 목록에 이름과 구분 `회사` 가 보인다
- **AND** 명령으로 저장한 도시와 가격표 항목은 그대로 돌아온다
- **AND** 저장 요청에 `merged_into` 와 `active: false` 를 함께 보내도 `merged_into` 는 비어 있고 `active` 는 `true` 다
- **AND** `company_type` 이 `alien` 이면 `ERP_INVALID`, 없는 태그는 `ERP_INVALID_REF` 로 거부된다

### Requirement: 연락처는 합칠 수 있고 합칠 후보를 찾아 볼 수 있다

시스템은 `merge`(`into`) 명령으로 원본을 대상에 합치고 이벤트로 이력을 남겨야 한다(SHALL). 대상의 값이 우선이고 원본은 빈 칸만 채운다. 원본은 지우지 않고 `merged_into` 와 `active: false` 로 남는다. 발행된 문서의 `partner_id` 는 사실이므로 바꾸지 않는다. 합칠 후보는 공개 함수 `erp_partner_duplicates` 로 조회하고 화면은 없으며, 합치는 것은 사람이 한다.

#### Scenario: 연락처를 합치면 대상 값이 이기고 빈칸·태그·하위 연락처·공급사 줄이 옮겨진다

- **WHEN** 김대표가 `서울가전상사 (중복)` 연락처의 `더 보기` 에서 `연락처 합치기` 를 고르고 `합칠 대상` 으로 `서울가전상사` 를 골라 확인한다
- **THEN** 확인 버튼은 위험 동작으로 표시되고 이력의 첫 항목에 `연락처 합침` 이 남는다
- **AND** 원본의 `merged_into` 는 대상이고 `active` 는 `false` 다
- **AND** 대상의 이름과 이메일은 그대로이고, 비어 있던 전화와 사업자등록번호는 원본 값으로 채워지며, 태그는 대상 태그 뒤에 원본에만 있던 태그가 붙는다
- **AND** 원본의 하위 연락처는 대상 아래로 옮겨지고 제품 공급사 줄의 `partner_id` 는 대상으로 바뀐다
- **AND** 원본에는 `PartnerMerged`, 대상에는 `merged_from` 이 원본인 `PartnerMergeReceived` 가 남고, 명령 응답의 이벤트에 원본·대상·하위 연락처·제품이 모두 나온다

#### Scenario: 합쳐도 발행된 문서의 거래처는 그대로다

- **WHEN** 박영업이 확정한 주문의 거래처 `서울가전상사 (중복)` 을 `서울가전상사` 로 합친다
- **THEN** 그 주문의 `partner_id` 는 원본 그대로다

#### Scenario: 합쳐진 연락처는 고칠 수 없고 잘못된 합치기는 거부된다

- **WHEN** 박영업이 이미 합쳐진 연락처를 다시 합치거나 고치거나 보관을 푼다
- **THEN** `ERP_MERGED` 로 거부된다
- **AND** 이미 합쳐진 연락처를 대상으로 고르면 `ERP_INVALID` 로 거부된다
- **AND** 자기 자신이나 자기의 하위 연락처를 대상으로 고르면 `ERP_INVALID` 로 거부된다
- **AND** 대상을 주지 않으면 `ERP_REQUIRED`, 없는 id 나 연락처가 아닌 레코드를 주면 `ERP_NOT_FOUND` 로 거부된다
- **AND** 합친 뒤에도 대상은 계속 고칠 수 있다

#### Scenario: 고른 항목이 모두 같은 연락처를 묶어 보여 주고 빈 값은 맞지 않는다

- **WHEN** 구성원이 공개 함수 `erp_partner_duplicates` 에 `["email"]` 을 보낸다
- **THEN** 대소문자와 앞뒤 공백을 빼고 이메일이 같은 두 연락처가 먼저 만든 순서로 한 묶음의 `partners` 에 나온다
- **AND** `["email", "tax_id"]` 로 물으면 사업자등록번호가 빈 연락처는 맞지 않아 묶음이 없다
- **AND** `["note"]` 처럼 비교할 수 없는 항목은 `ERP_INVALID` 로 거부된다
- **AND** 둘을 합치고 나면 그 묶음은 더 나오지 않는다

### Requirement: 제품은 기본 변형과 회사 기본값을 갖고 규칙을 지킨다

시스템은 속성이 없는 제품에도 변형 한 줄을 만들고, 밝히지 않은 항목을 기본값으로 채워야 한다(SHALL). 단위와 구매 단위는 같은 분류여야 하고, 서비스는 추적할 수 없으며, 바코드는 겹칠 수 없다(MUST). 재고 추적(`is_storable`)은 재화만 켤 수 있다.

#### Scenario: 제품을 저장하면 기본 변형과 회사 기본값이 붙는다

- **WHEN** 김대표가 `제품` 화면에서 제품명 `제습기`, 제품 분류 `기본 분류`, 단위 `개`, 판매가 12000, 원가 8200 을 넣고 `저장` 을 누른다
- **THEN** `변형` 표에 한 줄이 생기고 그 표에는 `줄 추가` 버튼이 없으며 판매가는 `12,000` 으로 보인다
- **AND** 내부 참조 `P-1`, 판매가 2500, 원가 1500 으로 만든 제품의 변형은 SKU `P-1`, 정가 2500, 원가 1500 이고 사용 중이다
- **AND** 이벤트는 `ProductCreated`, `ProductVariantAdded` 순서로 남는다
- **AND** 밝히지 않으면 `type` 은 `goods`, 단위와 구매 단위는 `개`, 분류는 `기본 분류`, 매출 세금은 `부가세 10% 매출`, 매입 세금은 `부가세 10% 매입` 이다
- **AND** 밝히지 않으면 `sale_ok` 는 `true`, `invoice_policy` 는 `order`, `bill_policy` 는 `receipt`, `tracking` 은 `none` 이다
- **AND** `sale_tax_ids: []` 로 만들면 매출 세금은 비어 있다

#### Scenario: 제품 규칙 위반은 거부되고 재화만 재고를 추적한다

- **WHEN** 박영업이 단위 `kg`, 구매 단위 `개` 로 제품을 저장한다
- **THEN** `ERP_UOM` 으로 거부된다
- **AND** 서비스에 추적 `lot` 을 넣으면 `ERP_INVALID`, 이미 쓰인 바코드를 넣으면 `ERP_DUPLICATE` 로 거부된다
- **AND** 재화의 `is_storable` 은 기본 `true` 이고 `false` 로 끌 수 있다
- **AND** `true` 를 보내며 서비스로 만들어도, 재화를 서비스로 바꿔도 `is_storable` 은 `false` 다
- **AND** 구매 모듈이 꺼진 회사에서 `purchase_ok` 를 보내면 `ERP_MODULE_OFF` 로 거부되고, 보내지 않으면 `purchase_uom_id` 없이 저장된다

### Requirement: 콤보 제품과 공급사 줄은 제품에 함께 저장된다

시스템은 `combo` 제품에 선택 항목을 하나 이상 요구하고, 각 항목에 겹치지 않는 제품을 하나 이상 요구하며, 콤보 제품을 항목에 넣는 것을 거부해야 한다(SHALL). 공급사 줄의 변경은 `ProductVendorAdded`, `ProductVendorChanged`, `ProductVendorRemoved` 로 남는다. 콤보가 주문에서 어떻게 값이 매겨지는지는 판매 스펙이 다룬다.

#### Scenario: 콤보는 선택 항목이 있어야 하고 제품이 겹치거나 콤보가 들어갈 수 없다

- **WHEN** 박영업이 유형 `combo` 제품을 선택 항목 없이 저장한다
- **THEN** `ERP_INVALID` 로 거부된다
- **AND** 항목에 제품이 없으면 `ERP_INVALID`, 같은 변형이 두 번 나오면 `ERP_DUPLICATE`, 없는 변형이면 `ERP_INVALID_REF` 로 거부된다
- **AND** 콤보 제품의 변형을 항목에 넣으면 `ERP_INVALID` 로 거부된다
- **AND** 변형 둘(둘째 `extra_price` 50)을 넣은 항목은 저장되고 `is_storable` 은 `false` 이며 줄마다 `id` 가 붙는다

#### Scenario: 공급사 줄은 입력한 대로 보관되고 변경은 자기 이벤트로 남는다

- **WHEN** 최구매가 `제습기` 에 공급사 `바람부품`, 단가 100, 최소 수량 10, 납기 3일, 공급사 제품 코드 `V1`, 할인 5 인 줄을 넣어 저장한다
- **THEN** 그 값이 그대로 돌아온다
- **AND** 단가를 90 으로 바꾸면 `ProductVendorChanged` 가 남는다
- **AND** 줄을 비우면 `ProductVendorRemoved` 가 남는다
- **AND** 종료일이 시작일보다 빠르거나 최소 수량이 -1 이면 `ERP_INVALID` 로 거부되고 시작일과 종료일이 같은 줄은 저장된다

### Requirement: 즉시(`always`) 속성은 조합 전체를 변형으로 만든다

시스템은 `always` 속성만 있는 제품에 값 조합 전체를 변형으로 만들어야 한다(SHALL). 최대 1000개이고 넘으면 `ERP_VARIANT_LIMIT` 로 거부한다. 변형의 정가는 제품 판매가에 그 조합의 값별 추가 금액 합을 더한 값이다. 값이 빠져도 변형 줄은 지워지지 않고 `active: false` 로 남으며 값이 돌아오면 같은 id 로 되살아난다(MUST).

#### Scenario: 즉시 방식은 모든 조합을 만들고 정가에 값의 추가 금액을 더한다

- **WHEN** 박영업이 판매가 10000 인 `에어서큘레이터` 에 색상 `빨강`, `파랑`(추가 500)과 크기 `S`, `M`, `L`(`L` 추가 1000)을 넣어 저장한다
- **THEN** 변형 6개가 서로 다른 id 로 생긴다
- **AND** 파랑·L 변형의 이름은 `에어서큘레이터 (파랑, L)`, `price_extra` 는 1500, 정가는 11500 이다
- **AND** 빨강·S 변형의 `price_extra` 는 0, 정가는 10000 이다
- **AND** 판매가를 20000 으로 바꾸면 파랑·L 변형의 정가는 21500 이다
- **AND** 값의 순서를 바꿔 같은 조합을 찾아도 같은 변형이고 변형은 6개 그대로다

#### Scenario: 값을 빼면 변형이 보관되고 돌아오면 같은 id 로 되살아난다

- **WHEN** 박영업이 색상 2개와 크기 2개로 변형 4개를 가진 제품에서 `파랑` 을 뺀다
- **THEN** 변형 줄은 4개 그대로이고 사용 중인 것은 `빨강` 변형 2개다
- **AND** `ProductAttributeChanged` 와 `ProductVariantArchived` 가 남고 보관된 변형은 옛 문서를 위해 `active: false` 로 읽힌다
- **AND** 값을 되돌리면 4개가 같은 id 로 사용 중이 되고 `ProductVariantReactivated` 가 남는다
- **AND** 값을 더하면 새 조합만 생기고 기존 변형의 id 는 그대로다
- **AND** 속성이 없던 제품에 값 둘인 속성을 더하면 기본 변형은 보관되고 새 변형 둘이 사용 중이 된다
- **AND** 판매가 1000 인 제품에 값 하나(추가 300)인 속성을 더하면 기본 변형이 같은 id 와 이름으로 이어지고 정가는 1300 이 된다

#### Scenario: 조합이 1000개를 넘으면 거부된다

- **WHEN** 박영업이 값 10개인 속성 3개를 넣어 제품을 저장한다
- **THEN** 변형 1000개가 4초 안에 만들어지고 `erp_variants` 에도 1000행이 있다
- **AND** 그 제품의 판매가 변경과 속성값 이름 변경도 각각 4초 안에 끝난다
- **AND** 여기에 값 2개인 속성을 더하면 `ERP_VARIANT_LIMIT` 로 거부된다

#### Scenario: 화면에서 속성 값과 변형을 목록으로 고른다

- **WHEN** 김대표가 `제품 속성` 화면에서 `색상` 에 값 `빨강`, `파랑` 을 넣어 저장하고 `제품` 화면의 `속성` 표에서 `줄 추가` 를 누른다
- **THEN** 속성을 고르기 전에는 값 칸에 `앞 칸을 먼저 고르세요` 가 보이고 `색상` 을 고르면 `빨강`, `파랑` 이 선택지로 나타난다
- **AND** 둘을 골라 저장하면 `변형` 표에 두 줄이 보인다
- **AND** `가격표` 화면의 규칙 줄에서 대상을 `변형` 으로 고르고 변형 칸을 누르면 변형 목록이 나타난다

### Requirement: 주문할 때(`dynamic`)와 만들지 않음(`no_variant`) 속성은 미리 변형을 만들지 않는다

시스템은 `dynamic` 속성이 하나라도 있는 제품에 변형을 미리 만들지 않고, 변형을 요청받았을 때 그 조합을 만들어야 한다(SHALL). 변형 요청은 주문 줄이 보내며 구성원이 직접 부르는 공개 함수는 없다. 변형을 만드는 속성마다 값이 정확히 하나 필요하다. `no_variant` 값은 변형을 늘리지 않고 요청에 섞여 있어도 무시한다(MUST).

#### Scenario: 주문할 때 방식은 처음 쓸 때 변형을 하나만 만든다

- **WHEN** 박영업이 판매가 1000 인 `공기청정기 프로` 에 `dynamic` 속성 `금`(추가 5000), `은` 과 `always` 속성 `S`, `M` 을 넣어 저장한다
- **THEN** 변형은 하나도 없다
- **AND** `금`, `S` 로 처음 요청하면 `ProductVariantAdded` 로 변형 하나가 생기고 정가는 6000 이다
- **AND** 값 순서를 바꿔 다시 요청해도 같은 변형이다
- **AND** 열 곳에서 동시에 처음 요청해도 변형은 하나다
- **AND** 견적 줄에 제품과 값을 넣으면 그때 변형이 생기고 같은 값의 다음 견적 줄은 같은 변형을 쓴다

#### Scenario: 변형을 정할 수 없는 값 조합은 거부되고 보관된 변형은 되살아난다

- **WHEN** `금`, `은` 과 `S`, `M` 속성을 가진 제품에 `금` 만, 값 없이, `금`·`은`·`S` 를 함께, 또는 제품에 없는 값으로 변형을 요청한다
- **THEN** `ERP_INVALID` 로 거부된다
- **AND** 없는 제품이면 `ERP_NOT_FOUND` 로 거부된다
- **AND** 제품에서 `금` 을 빼면 그 변형은 사용 중이 아니고 `금` 으로 요청하면 `ERP_INVALID` 로 거부된다
- **AND** `금` 을 되돌리면 같은 변형이 사용 중으로 돌아온다
- **AND** 손으로 보관한 변형도 다시 요청하면 같은 id 로 되살아난다

#### Scenario: 만들지 않음 방식은 변형을 늘리지 않고 변형 가격에도 넣지 않는다

- **WHEN** 박영업이 `공기청정기 보급형` 에 `no_variant` 속성 `포장`(추가 700), `각인` 을 넣어 저장한다
- **THEN** 변형은 1개이고 `values` 는 비어 있으며 `price_extra` 는 0 이다
- **AND** `포장` 을 골라 요청하든 값 없이 요청하든 같은 변형이다
- **AND** 즉시 속성 `S`, `M` 과 섞으면 변형은 2개이고 `M`, `각인`, `포장` 으로 요청하면 `M` 변형이다

### Requirement: 변형 줄은 정해진 칸만 고칠 수 있고 바코드는 겹치지 않는다

시스템은 변형 줄에서 `sku`, `barcode`, `standard_price`, `active` 만 고치게 해야 한다(SHALL). 줄을 손으로 더할 수 없다. 바코드는 동시에 저장해도 한 변형에만 붙는다(MUST). 변형 이름은 제품 이름과 속성값 이름에서 나온다.

#### Scenario: 변형 줄에서는 SKU·바코드·원가·사용 여부만 고칠 수 있다

- **WHEN** 박영업이 원가 700 인 제품의 변형 줄 하나에 SKU `SKU-A`, 바코드, 원가 900 과 함께 이름 `해킹`, `price_extra` 999, 빈 `values` 를 보낸다
- **THEN** SKU, 바코드, 원가만 바뀌고 이름, `price_extra`, `values` 는 그대로다
- **AND** `ProductVariantChanged` 가 남고 `erp_variants` 에 새 SKU 와 바코드가 보인다
- **AND** 그 변형의 원가는 900 이고 고치지 않은 변형의 원가는 제품 원가 700 이다

#### Scenario: 없는 변형, 겹치는 바코드, 틀린 속성 줄은 거부된다

- **WHEN** 박영업이 `id` 없는 변형 줄을 넣어 저장한다
- **THEN** `ERP_INVALID` 로 거부된다
- **AND** 이미 쓰인 바코드를 같은 제품의 다른 변형, 다른 제품의 변형, 다른 제품 자체에 넣으면 `ERP_DUPLICATE` 로 거부된다
- **AND** 제품 8개에 같은 바코드를 동시에 저장하면 하나만 통과하고 나머지는 `ERP_DUPLICATE` 로 거부된다
- **AND** 속성 줄의 값이 비었거나, 속성에 없는 값이거나, 같은 속성이 두 번 나오거나, 추가 금액이 글자이면 `ERP_INVALID` 로 거부된다
- **AND** `S` 만 고르고 추가 금액을 `S` 5, `M` 9 로 보내면 `S` 5 만 남는다

#### Scenario: 제품과 값 이름을 바꾸면 변형 이름이 따라간다

- **WHEN** 박영업이 색상 `빨강`, `파랑` 변형을 가진 `가습기` 의 이름을 `초음파 가습기` 로 바꾼다
- **THEN** 변형 이름은 `초음파 가습기 (빨강)`, `초음파 가습기 (파랑)` 이다
- **AND** 속성값 `빨강` 을 `자주` 로 바꾸면 변형 이름은 `초음파 가습기 (자주)`, `초음파 가습기 (파랑)` 이고 `erp_variants` 에도 같다
- **AND** 그때 제품에 남는 `ProductVariantChanged` 의 `source` 는 `reaction` 이고 `correlation_id` 는 속성 명령과 같다

### Requirement: 보관과 삭제는 변형에 닿고 쓰이는 레코드는 지울 수 없다

시스템은 제품의 보관·보관 해제·삭제를 그 변형에 반영하고, 다른 레코드가 가리키는 제품과 세금의 삭제를 `ERP_IN_USE` 로 거부해야 한다(SHALL). 되돌리기로 제품에서 빠진 변형은 옛 id 만 남고 더 쓸 수 없다.

#### Scenario: 보관·삭제는 변형에 닿고 쓰이는 제품과 세금은 지울 수 없다

- **WHEN** 박영업이 제품을 보관한다
- **THEN** 그 변형은 `erp_variants` 에서 `active` 가 `false` 이고 변형으로는 여전히 읽힌다
- **AND** 보관을 풀면 `active` 는 `true` 로 돌아온다
- **AND** 제품을 지우면 `active` 는 `false` 이고 그 변형과 제품으로 하는 요청은 `ERP_NOT_FOUND` 로 거부된다
- **AND** 가격표 규칙이 제품이나 그 변형만 가리켜도 제품 삭제는 `ERP_IN_USE` 로 거부된다
- **AND** 시드 세금 `부가세 10% 매출` 의 삭제는 `ERP_IN_USE` 로 거부된다

#### Scenario: 되돌리기로 제품에서 빠진 변형은 찾을 수 없고 바코드를 놓는다

- **WHEN** 되돌리기로 제품의 변형 목록이 변형을 더하기 전으로 돌아간다
- **THEN** 빠진 변형은 `erp_variants` 에서 `active` 가 `false` 이고 바코드가 비어 있다
- **AND** 그 변형을 찾으면 `ERP_NOT_FOUND` 로 거부된다
- **AND** 그 바코드를 다른 제품이 쓸 수 있다

### Requirement: 줄 전체를 보내도 원장에는 바뀐 줄만 남는다

시스템은 화면이 줄 전체를 보내도 차이를 계산해 종류별로 이벤트 하나씩 남겨야 한다(SHALL). 대상은 `PaymentTermLine*`, `FiscalPositionTaxMap*`, `AttributeValue*`, `ProductAttribute*`, `ProductVendor*`, `PricelistRule*` 이다. 변화가 없으면 이벤트도 없다(MUST). 알려진 `id` 의 줄은 이전 줄 위에 덮어 쓰므로 고친 칸만 보내도 된다.

#### Scenario: 줄 전체를 보내도 바뀐 줄만 이벤트로 남는다

- **WHEN** 정회계가 세 줄짜리 결제 조건을 같은 줄 그대로 다시 저장한다
- **THEN** 이벤트는 `PaymentTermCreated` 하나뿐이다
- **AND** 두 줄의 비율을 바꾸면 `PaymentTermLineChanged` 하나에 바뀐 두 줄과 이전 값이 실린다
- **AND** 줄의 `id` 와 `days` 만 보내면 나머지 칸은 이전 값을 유지한다
- **AND** 한 줄을 빼면서 다른 줄을 바꾸면 `PaymentTermLineRemoved`, `PaymentTermLineChanged` 순서로 남는다
- **AND** 줄을 고치고 가운데에 줄을 더하면 `PaymentTermLineChanged`, `PaymentTermLineAdded`, `PaymentTermLineReordered` 순서로 남고 줄 순서는 보낸 대로다
- **AND** 이름만 바꾸면 `PaymentTermUpdated` 가 남는다
- **AND** 박영업이 가격표 규칙을 고치고 더하고 빼면 `PricelistRuleChanged`, `PricelistRuleAdded`, `PricelistRuleRemoved` 가 남고 같은 규칙을 다시 보내면 이벤트가 없다

### Requirement: 가격 규칙은 저장할 때 검사한다

시스템은 대상·날짜·수량·할인·마진이 어긋난 규칙과 자기 자신으로 돌아오는 기준 가격표를 거부해야 한다(SHALL). 가격표는 판매 역할과 `admin` 만 쓴다.

#### Scenario: 잘못된 가격 규칙과 자기 자신으로 돌아오는 기준은 저장되지 않는다

- **WHEN** 박영업이 대상이 `category`, `product`, `variant` 인 규칙을 그 대상 없이, `fixed` 규칙을 가격 없이, 기준이 `pricelist` 인 규칙을 기준 가격표 없이 저장한다
- **THEN** `ERP_REQUIRED` 로 거부된다
- **AND** 대상 `bogus`, 종료일이 시작일보다 빠른 규칙, 시작일 `someday`, 기준 수량 -1, 할인 101, 계산식 할인 101, 반올림 단위 -1 은 `ERP_INVALID` 로 거부된다
- **AND** 없는 변형이나 uuid 가 아닌 제품을 가리키면 `ERP_INVALID_REF` 로 거부된다
- **AND** 최소 마진 10 에 최대 마진이 5 이거나 없으면 `ERP_INVALID` 로 거부되고 최대 마진 5 만 넣은 규칙은 저장된다
- **AND** 시작일과 종료일이 같은 규칙은 저장되고 모르는 칸 `hacker` 는 남지 않는다
- **AND** 가격표가 자기 자신이나 자기를 기준으로 삼은 가격표를 거쳐 돌아오는 기준을 고르면 `ERP_INVALID` 로 거부된다

### Requirement: 가격은 가격표 규칙에서 한 가지로 정해진다

시스템은 가격표·변형·수량·날짜·단위로 `price_unit`, `list_price`, `discount`, `rule_id` 를 돌려주어야 한다(SHALL). 규칙은 구체적인 대상(변형, 제품, 분류, 전체 순), 큰 기준 수량, 가까운 분류, 나중에 넣은 규칙 순서로 하나만 고른다. 기간은 날짜 단위이고 시작일과 종료일을 포함한다. 맞는 규칙이 없거나 가격표가 없으면 정가다. `discount` 유형은 할인율을 `discount` 로 보여 주고 `formula`, `fixed` 는 단가에 녹인다.

#### Scenario: 구체적인 대상이 먼저이고 그다음 기준 수량, 가까운 분류, 나중에 넣은 규칙 순이다

- **WHEN** 박영업이 판매가 10000 인 변형의 가격을 묻고 가격표에 변형 7000, 제품 8000, 분류 8500, 전체 9000 고정 가격 규칙이 이 순서로 있다
- **THEN** `price_unit` 은 7000 이고 `rule_id` 는 변형 규칙이다
- **AND** 그 변형 규칙은 다른 변형에 쓰이지 않아 다른 변형은 제품 규칙의 8000 이다
- **AND** 수량 20 에서 분류 규칙(할인 5)은 기준 수량 10 인 전체 규칙(할인 40)을 이겨 `discount` 는 5 다
- **AND** 같은 전체 규칙의 기준 수량이 1, 10, 100 이면 수량 150 은 기준 수량 100 규칙(할인 20)을 쓴다
- **AND** 기준 수량이 같은 말단, 중간, 최상위 분류 규칙(할인 5, 20, 30)이 있으면 가까운 말단 분류의 5 다
- **AND** 상위 분류의 기준 수량 10 규칙(고정 210)은 수량 10 에서 하위 분류의 기준 수량 1 규칙(고정 300)을 이기고, 수량 9 면 300 이다
- **AND** 조건이 모두 같은 할인 5, 할인 6 규칙이면 나중에 넣은 6 이다
- **AND** 규칙이 비었거나 가격표가 없으면 `price_unit` 과 `list_price` 는 10000, `discount` 는 0, `rule_id` 는 `null` 이다

#### Scenario: 규칙 기간은 날짜 단위로 시작일과 종료일을 포함한다

- **WHEN** 시작일이 2026-06-15 인 할인 10 규칙으로 2026-06-15 의 가격을 묻는다
- **THEN** `discount` 는 10 이다
- **AND** 2026-06-14 에 물으면 규칙이 맞지 않아 `discount` 는 0 이다
- **AND** 종료일이 2026-06-30 이면 2026-06-30 에는 맞고 2026-07-01 에는 맞지 않는다
- **AND** 종료일이 2026-01-31 인 제품 규칙(고정 5000)은 2026-02-01 에 전체 규칙(할인 3)으로 넘어간다

#### Scenario: 할인은 단가를 두고 할인율을 보여 주고 고정 가격은 단가에 녹는다

- **WHEN** 판매가 10000 에 전체 규칙 할인 10 이 있다
- **THEN** `price_unit` 10000, `list_price` 10000, `discount` 10 이다
- **AND** 할인 100 이면 `discount` 는 100 이다
- **AND** 값 추가 금액 500 으로 정가가 10500 인 변형에 고정 8000 규칙이 있으면 `price_unit` 8000, `list_price` 10500, `discount` 0 으로 추가 금액을 더하지 않는다

#### Scenario: 계산식은 할인 → 반올림 → 추가금 → 마진 한도 순서다

- **WHEN** 판매가 12345 에 계산식 할인 10, 반올림 단위 100, 추가금 -10 규칙이 있다
- **THEN** `price_unit` 11090, `list_price` 12345, `discount` 0 이다
- **AND** 판매가 1000, 할인 15, 반올림 단위 100, 추가금 5 이면 반은 올려 `price_unit` 은 905 다
- **AND** 판매가 999, 할인 10 이면 `price_unit` 은 899.1 이다
- **AND** 판매가 2000, 원가 600, 기준 `standard_price`, 계산식 할인 -50, 최소 마진 400, 최대 마진 100000 이면 `price_unit` 은 1000 이다
- **AND** 같은 기준에 최대 마진 200 만 있으면 `price_unit` 은 800 이다
- **AND** 판매가 1000, 할인 50, 최소 마진 100, 최대 마진 100000 이면 마진의 기준은 할인 전 가격이라 `price_unit` 은 1100 이다
- **AND** 달러 회사에서 판매가 100, 할인 7, 반올림 단위 1, 추가금 -0.01 이면 `price_unit` 은 92.99 다

#### Scenario: 다른 가격표를 기준으로 삼으면 그 가격표의 할인까지 뺀 값에서 시작한다

- **WHEN** 판매가 10000 이고 기준 가격표에 할인 10 규칙이 있으며 이 가격표는 기준 `pricelist`, 계산식 할인 50 규칙을 쓴다
- **THEN** `price_unit` 은 4500 이다
- **AND** 기준 가격표가 고정 8000 이고 이 가격표가 할인 25 규칙이면 `price_unit` 8000, `list_price` 10000, `discount` 25 다
- **AND** 기준 가격표에 맞는 규칙이 없으면 정가에서 시작해 계산식 할인 10 의 `price_unit` 은 9000 이다

#### Scenario: 요청 단위로 바꿔 계산하고 기준 수량은 제품 단위로 잰다

- **WHEN** 판매가 1000 인 `개` 단위 제품을 1 `다스` 로 묻고 기준 수량 12, 할인 10 규칙이 있다
- **THEN** 규칙이 맞아 `price_unit` 12000, `list_price` 12000, `discount` 10 이다
- **AND** 기준 수량이 13 이면 규칙이 맞지 않아 `discount` 는 0, `rule_id` 는 `null` 이다
- **AND** 기준 수량 1, 10 규칙에서 수량 10 은 10 규칙을, 수량 9.99 는 1 규칙을 쓴다
- **AND** 판매가 1200, 고정 1000 규칙을 1 `다스` 로 물으면 `price_unit` 12000, `list_price` 14400 이다
- **AND** 판매가 1000, 계산식 할인 10, 반올림 단위 1000, 추가금 10 을 1 `다스` 로 물으면 `price_unit` 11120, `list_price` 12000 이다
- **AND** `kg` 당 판매가 5500 을 `g` 으로 물으면 `price_unit` 은 5.5 이고 계산식 할인 10 이면 4.95 다

### Requirement: 입력한 가격은 그대로 저장하고 금액만 통화 자릿수로 반올림한다

시스템은 판매가, 원가, 값별 추가 금액, 공급사 단가, 변형 원가, 콤보 추가 금액, 가격 규칙의 고정 가격·추가금·마진을 입력한 값 그대로 저장해야 한다(MUST). 단가는 통화 자릿수로 자르지 않고 환산과 계산식에서 생긴 끝수만 소수 10자리에서 정리한다. 통화 자릿수로 반올림되는 것은 줄 금액부터다(SHALL). 고정 금액 세금의 금액은 돈이므로 저장할 때 반올림하고, 세율은 그대로 둔다.

#### Scenario: 입력한 가격은 통화 자릿수로 잘리지 않고 줄 금액만 반올림한다

- **WHEN** 소수 자리가 없는 원화 회사에서 박영업이 판매가 1000.5, 원가 99.4, 공급사 단가 12.5, 값 추가 금액 10.5 로 제품을 저장한다
- **THEN** 네 값이 그대로 저장되고 변형의 `price_extra` 는 10.5, 정가는 1011 이다
- **AND** 판매가 1234.56789 는 가격 조회에서 `price_unit` 1234.56789 로, 변형 규칙의 고정 가격 777.12345 는 777.12345 로 돌아온다
- **AND** 규칙에 넣은 고정 가격 10.4 는 10.4 로 저장된다
- **AND** 단가 1234.56789, 수량 10000 의 줄은 `subtotal` 12345679 이고 돌아오는 `price_unit` 은 1234.56789 다
- **AND** 판매가 19.99 에 계산식 할인 12.5 이면 `price_unit` 은 17.49125 이고, 달러 회사에서 계산식 할인 15 이면 16.9915 다
- **AND** 정회계가 금액 99.5 로 만든 고정 금액 세금의 `amount` 는 100 이고 세율 12.5 로 만든 비율 세금의 `amount` 는 12.5 다

### Requirement: 가격 조회는 쓰기를 하지 않고 구성원에게만 열린다

시스템은 공개 함수 `erp_price`(`p_pricelist_id`, `p_variant_id`, `p_qty`, `p_date`, `p_uom_id`)로 구성원에게 가격을 알려 주어야 한다(SHALL). 조회는 원장에 아무것도 쓰지 않는다(MUST). 날짜를 주지 않으면 업무 일자를 쓴다. 이 함수를 부르는 화면은 없다.

#### Scenario: 가격 조회는 아무것도 쓰지 않고 날짜를 안 주면 업무 일자를 쓴다

- **WHEN** 구성원이 2031-03-01 하루만 유효한 할인 7 규칙의 가격을 날짜 없이 묻는다
- **THEN** 업무 일자가 그날이 아니면 `discount` 는 0 이다
- **AND** 업무 일자가 2031-03-01 이면 `discount` 는 7 이고 `즉시` 결제 조건의 `due_date` 도 2031-03-01 이다
- **AND** 조회 뒤 원장의 이벤트 수는 그대로다

#### Scenario: 가격 조회는 구성원만 할 수 있고 없는 대상은 업무 오류다

- **WHEN** 조회 역할 구성원이 `erp_price` 로 `기본 가격표` 에서 판매가 4000 인 변형의 가격을 묻는다
- **THEN** `price_unit` 4000, `list_price` 4000, `discount` 0, `rule_id` `null` 이다
- **AND** 로그인하지 않은 요청은 `permission denied`, 회사 구성원이 아닌 계정은 `ERP_FORBIDDEN` 으로 거부된다
- **AND** 구성원도 내부 가격·세금 계산을 직접 부르면 `permission denied` 로 거부된다
- **AND** 없는 변형, 가격표, 세금, 세금 조정, 결제 조건이나 uuid 가 아닌 세금은 `ERP_NOT_FOUND` 로 거부된다
- **AND** `개` 단위 제품의 가격을 `kg` 으로 물으면 `ERP_UOM` 으로 거부된다
