# 통계, 예측, what-if

## Purpose

가온가전은 쌓인 이벤트만으로 지역·제품·시즌 통계와 수요·품절·납기·입금·손익 예측을 보고, 바꾸기 전에 what-if 로 시험해 본다. 모든 모델은 잠김·근거 부족·사용 가능 중 하나로 보이며, 근거가 모자라면 숫자 대신 무엇이 더 필요한지와 범위만 말한다. 결과 구간이 0 을 포함하면 효과를 구분할 수 없다고 먼저 말한다. 분석은 원장만 읽고 원장을 바꾸지 않으며, 읽을 권한이 없는 문서의 숫자는 주지 않는다. 정확도 수치는 정답을 아는 가상 회사로 잰 것이고 실제 회사의 성능이 아니다.

## Requirements

### Requirement: 모든 모델은 세 상태 중 하나로 보인다

시스템은 아래 14개 모델을 `locked`(잠김), `insufficient`(근거 부족), `ready`(사용 가능) 중 하나로 알려야 한다(SHALL). 공개 함수 `erp_models` 는 모델마다 `id`, `kind`, `label`, `state`, `missing_modules`, `evidence` 를 돌려준다. 모듈이 한 번도 켜진 적 없으면 잠김이고, 근거는 아래 표를 따른다.

| 모델 | 이름 | 필요한 모듈 | 필요한 근거 | 모듈을 끈 뒤 |
|---|---|---|---|---|
| `stat_sales` | 지역·제품·시즌 통계 | 판매 | 없음 | 이력으로 계산 |
| `quote_conversion` | 견적 전환율 | 판매 | 견적 40건 | 이력으로 계산 |
| `stat_headcount` | 인원 추이·입퇴사 | 인사 | 가장 이른 입사일부터 3개월 | 이력으로 계산 |
| `mrp_lead_time` | 실측 제조 기간 | 제조 | 제조 완료 10건 | 이력으로 계산 |
| `mrp_materials` | 자재 소요 전망 | 제조, 재고 | 제조 완료 10건 | 잠김 |
| `whatif_production` | 생산량 변경 | 제조, 재고 | 제조 완료 10건 | 잠김 |
| `demand_sales` | 판매 기준 수요 예측 | 판매 | 판매가 있었던 달 15개월 | 이력으로 계산 |
| `demand_true` | 품절 보정 수요 예측 | 판매, 재고 | 재고 이력 30일, 판매 12개월 | 이력으로 계산 |
| `stockout_risk` | 품절 예상일 | 판매, 재고 | 재고 이력 30일 | 잠김 |
| `whatif_policy` | 발주 정책 변경 | 판매, 재고 | 재고 이력 270일(입고 10건이 있으면 180일), 판매 9개월 | 잠김 |
| `whatif_realloc` | 창고 재배치 | 판매, 재고 | 창고 2곳, 재고 이력 180일, 판매 9개월 | 잠김 |
| `whatif_drop` | 단종 | 판매 | 대체 상품 품절 사례 5건, 판매 9개월 | 이력으로 계산 |
| `lead_time` | 실측 납기 | 구매, 재고 | 입고 10건 | 이력으로 계산 |
| `whatif_lead` | 납기·공급사 변경 | 판매, 재고, 구매 | 입고 10건, 판매 9개월 | 잠김 |
| `reorder_plan` | 발주 필요 예측 | 판매, 재고, 구매 | 입고 30건 | 잠김 |
| `cash_in` | 입금 예측 | 청구 | 입금 완료 청구서 100건 | 잠김 |
| `whatif_terms` | 결제 조건 변경 | 청구 | 입금 완료 청구서 100건, 조건이 바뀐 거래처 3곳 | 잠김 |
| `pnl_outlook` | 손익 전망 | 판매, 회계 | 전표가 있는 달 3개월 | 이력으로 계산 |

#### Scenario: 첫 화면은 18개 모델을 세 상태로 보여 준다

- **WHEN** 김대표가 예측·what-if 메뉴를 연다
- **THEN** 모델 카드 18장이 보이고, 근거가 넉넉한 회사의 `stat_sales`, `demand_sales`, `demand_true`, `stockout_risk`, `lead_time`, `whatif_policy`, `whatif_lead` 는 「사용 가능」 에 「열기」 다

#### Scenario: 어떤 모듈도 켜기 전에는 모두 잠겨 있다

- **WHEN** 모듈을 하나도 켜지 않은 회사의 모델 목록을 읽는다
- **THEN** 14개 모두 `locked` 이고 `missing_modules` 가 비어 있지 않다
- **AND** `demand_true` 의 안내에 「재고 모듈을 켜면」 이 있다

#### Scenario: 판매만 켠 회사는 통계만 열리고 수요 예측은 근거를 기다린다

- **WHEN** 판매만 켠 가온가전이 주문을 몇 건 확정하고 예측 화면을 본다
- **THEN** `stat_sales` 는 「사용 가능」, `demand_sales` 는 「근거 부족」 에 「판매 15개월 필요」 다
- **AND** `demand_true` 는 「잠김」 에 「재고 모듈을 켜면 열립니다」, `cash_in` 은 잠김이며, 박영업에게는 「관리자에게」 요청하라는 안내가 보인다
- **AND** 판매가 있었던 달이 15개월이 되면 `demand_sales` 가 `ready` 다. 주문 하나 뒤에 오래 기다린 것은 이력으로 치지 않는다

#### Scenario: 어떤 모듈 조합에서도 세 상태 중 하나로 답한다

- **WHEN** 판매·재고·구매·청구·회계의 어떤 조합으로 켠 회사의 모델 목록을 읽는다
- **THEN** 모두 세 상태 중 하나다

### Requirement: 잠긴 모델은 계산하지 않고 어떤 모듈을 켤지 안내한다

시스템은 잠긴 모델의 화면에서 원장을 읽지 않고 필요한 모듈과 모듈 화면으로 가는 길을 보여 주어야 한다(SHALL).

#### Scenario: 잠긴 모델은 원장을 읽지 않고 안내만 한다

- **WHEN** 김대표가 재고 모듈을 켜기 전 시점에서 `demand_true` 를 연다
- **THEN** 「잠김」 과 「재고 모듈을 켜면 열립니다」, 「모듈 화면으로」 링크가 보인다
- **AND** 결과 칸이 없고 판매 시계열 호출이 한 번도 나가지 않는다

### Requirement: 근거가 모자라면 숫자 대신 필요한 것과 범위를 말한다

시스템은 근거가 모자란 모델에 대해 무엇이 얼마나 더 필요한지와 말할 수 있는 범위만 내고 점 하나의 숫자를 내지 않아야 한다(SHALL). `erp_models` 는 회사 전체의 근거를, 모델 계산은 그 제품·공급사의 근거를 본다. 화면은 모델 계산의 상태를 따른다.

#### Scenario: 무엇이 얼마나 더 필요한지와 범위만 보여 준다

- **WHEN** 판매 이력이 모자란 시점에 김대표가 `demand_sales` 를 연다
- **THEN** 「판매 15개월 필요」 와 「계절을 한 번도 다 보지 못해 폭이 넓습니다」 범위, 경고가 보이고 합계 표는 없다

#### Scenario: 대체 사례가 없는 단종은 0~100% 범위로만 말한다

- **WHEN** 재고 이력이 없는 시점에 김대표가 공기청정기 보급형의 단종을 돌린다
- **THEN** 결과 표 없이 「대체 상품 품절 사례 5건 필요」, 「대체율을 몰라」, 「대체율 0%일 때와 100%일 때의 범위입니다」 가 보인다
- **AND** 재고가 넉넉해 품절 사례가 모자란 가상 회사에서도 `insufficient` 이고, 실제 변화는 그 범위 안에 있다

#### Scenario: 근거 수에 닿으면 열리고 발주 계획은 더 많이 요구한다

- **WHEN** 모든 모듈을 켠 회사에 견적 40건, 입고 10건, 입금 완료 100건, 전표 3개월이 쌓인다
- **THEN** `quote_conversion`, `lead_time`, `whatif_lead`, `cash_in`, `pnl_outlook` 이 `ready` 가 된다
- **AND** `reorder_plan` 은 입고 30건을 기다리며 `insufficient` 이다

#### Scenario: 재고 이력이 길어도 판매 한 시즌을 보기 전에는 수요 예측이 열리지 않는다

- **WHEN** 판매와 재고를 함께 켠 지 다섯 달 된 회사의 모델 목록을 읽는다
- **THEN** `stockout_risk` 는 `ready` 이고 `demand_true` 는 `insufficient` 에 「판매 12개월 필요」 다

#### Scenario: 재고 이력이 모자라면 날수를 함께 말한다

- **WHEN** 재고 모듈을 켠 지 18일 된 시점의 모델 목록을 읽는다
- **THEN** `demand_true` 는 `insufficient` 에 「재고 이력 … 필요 (지금 18일)」 이다

#### Scenario: 발주 정책은 입고 기록이 있으면 필요한 이력이 줄어든다

- **WHEN** 입고 기록 없이 재고 이력만 쌓인 회사와, 입고 기록이 쌓인 회사의 `whatif_policy` 를 읽는다
- **THEN** 앞 회사는 재고 이력 270일, 뒤 회사는 180일을 요구한다

#### Scenario: 결제 조건은 조건이 바뀐 거래처가 있어야 답한다

- **WHEN** 입금 완료 청구서가 넉넉하지만 결제 조건이 바뀐 거래처가 없는 회사의 `whatif_terms` 를 돌린다
- **THEN** `insufficient` 에 「거래처 …곳 필요」 이고 결과 없이 0 에서 시작하는 범위만 준다
- **AND** 실제 변화는 그 범위 안에 있다

#### Scenario: 회사 전체는 되어도 그 제품의 근거가 모자라면 그 답을 따른다

- **WHEN** 카드에서 `whatif_drop` 이 사용 가능인데, 품절 사례가 없는 제품과 대체 후보를 골라 돌린다
- **THEN** 페이지 상태는 「사용 가능」 인 채 그 결과만 근거 부족으로 「대체 상품 품절 사례 5건 필요」 를 말한다
- **AND** `whatif_lead` 의 공급사 선택에는 구매 기록이 있는 공급사만 나온다

### Requirement: 사용 가능한 모델은 결과와 80% 구간, 근거, 경고를 함께 보여 준다

시스템은 예측 결과를 80% 구간, 근거(기간, 사례 수), 경고와 함께 보여 주어야 한다(SHALL). 숫자 하나만 내지 않는다.

#### Scenario: 수요 예측은 제품별 결과와 80% 구간, 근거를 보여 준다

- **WHEN** 김대표가 `demand_true` 를 연다
- **THEN** 제품별 표와 「80% 구간」, 근거에 「재고 이력」 과 「기록된 품절일」 이 보인다
- **AND** 기간을 30일로 고르면 「앞으로 30일」 로 바뀌고, `demand_sales` 의 경고에는 「판매가 오래 끊긴 구간」 이 있다

#### Scenario: 품절 확률은 말한 만큼 맞는다

- **WHEN** 가상 회사 8곳의 30일 품절 확률을 실제와 비교한다
- **THEN** 80% 이상이라 말한 칸의 실제 품절 비율은 80% 를 넘고, 20% 미만이라 말한 칸은 20% 아래다
- **AND** 화면의 `stockout_risk` 에 제품·창고별 표가 나온다

#### Scenario: 실측 납기는 미입고를 세고 공급사별로 나온다

- **WHEN** 최구매가 `lead_time` 을 연다
- **THEN** 전체와 공급사별 납기가 80% 구간과 함께 나오고 아직 안 온 주문도 센다
- **AND** 입고 근거가 모자라면 `insufficient` 에 범위만 준다

#### Scenario: 발주 필요 예측은 날짜와 수량을 말한다

- **WHEN** 입고가 넉넉한 회사의 `reorder_plan` 을 돌린다
- **THEN** 제품·창고마다 발주 기한과 0 이상의 제안 수량이 나오고 지금 발주해야 하는 줄(`need_now`)이 있다
- **AND** 재고 단계의 회사는 `insufficient` 에 「입고 …건 필요」 다

#### Scenario: 입금 예측은 미입금 청구서를 세고 주별로 말한다

- **WHEN** 정회계가 `cash_in` 을 연다
- **THEN** 합계와 주별 차트가 나오고 막대에 올리면 그 주가 보인다
- **AND** 입금 완료가 모자란 회사는 `insufficient` 다

#### Scenario: 손익 전망은 전표를 읽고 앞으로 석 달을 말한다

- **WHEN** 김대표가 `pnl_outlook` 을 연다
- **THEN** 앞으로 3개월의 달별 표가 나온다

#### Scenario: 새 제품을 몇 년치 0 으로 읽지 않는다

- **WHEN** 400일 전에 출시한 제품의 수요를 같은 제품의 전체 이력과 비교한다
- **THEN** 두 예측의 비율이 0.8 ~ 1.25 안이다

#### Scenario: 예시 제품에 묶이지 않는다

- **WHEN** 제품 10개·지역 2개·창고 1개인 다른 모양의 회사로 수요 예측과 발주·재배치·단종을 돌린다
- **THEN** 수요와 발주는 `ready` 이고, 창고가 1곳이라 재배치는 `insufficient` 에 「창고 2곳 필요」 다

### Requirement: what-if 는 기준 대비 변화를 말하고 구간이 0 을 포함하면 구분할 수 없다고 말한다

시스템은 what-if 를 같은 수요·같은 납기로 원안과 변경안을 나란히 돌려 기준 대비 변화의 P10·P50·P90 으로 답해야 한다(SHALL). 결과 구간이 0 을 포함하면 판정은 `indistinguishable` 이고 화면은 숫자보다 먼저 「효과를 구분할 수 없습니다」 라고 말하며 방향을 말하지 않는다. 그 밖에는 `up` 또는 `down` 이다.

#### Scenario: 기준 대비 변화를 P10·P50·P90 으로 보여 준다

- **WHEN** 김대표가 `whatif_policy` 에서 가습기와 전기히터를 고르고 돌린다
- **THEN** 제품을 고르기 전에는 실행 버튼이 꺼져 있다
- **AND** 매출·마진·품절일·재고 금액 줄과 「변화 P10」, 「변화 P90」 열, 판정, 근거가 보인다
- **AND** 「이 변경을 더하면」 으로 손익 전망에 환산할 수 있다

#### Scenario: 구간이 0 을 포함하면 숫자보다 먼저 구분할 수 없다고 말한다

- **WHEN** 김대표가 발주를 그대로 두는 변경(배수 1)으로 돌린다
- **THEN** 「효과를 구분할 수 없습니다」 가 표보다 위에 보이고 방향 판정은 없다
- **AND** 판정 코드는 P10 이 0 이하이고 P90 이 0 이상일 때 `indistinguishable`, 그 밖에는 P50 의 부호에 따라 `up` 또는 `down` 이다

#### Scenario: 창고 재배치는 대부분 구분할 수 없다고 말하고 같은 창고로는 못 옮긴다

- **WHEN** 김대표가 `whatif_realloc` 에서 제습기를 수도권에서 수도권으로 고른다
- **THEN** 실행 버튼이 꺼진다
- **AND** 호남 창고로 바꿔 돌리면 결과가 나오고, 가상 회사의 작은 이동은 `indistinguishable` 로 답한다

#### Scenario: 발주를 늘리면 방향과 크기를 말한다

- **WHEN** 입고 기록이 있는 품절 많은 가상 회사 8곳에서 여름 상품 발주를 늘린다
- **THEN** 모두 `ready`, 판정 `up`, `base_reliable` 은 참이고 실제 변화 대비 오차 중앙값이 30% 아래다

#### Scenario: 구매 기록이 없으면 기준 매출을 믿지 말라고 한다

- **WHEN** 재고까지만 켠 시점에 김대표가 `whatif_policy` 를 돌린다
- **THEN** 「기준 매출 자체는 믿지 마세요」 와 「변화량만 보세요」 가 보인다
- **AND** 결과의 `base_reliable` 은 거짓이고 경고에 「납기」 가 있다

#### Scenario: 품절 사례가 많으면 단종의 대체율을 잰다

- **WHEN** 김대표가 품절 사례가 많은 공기청정기 보급형의 단종을 돌린다
- **THEN** 제품 쌍별 대체율 표가 나오고 판정은 `down` 이다
- **AND** 가상 회사의 보급형→프로 대체율 중앙값은 실제 0.35 와 0.08 안이다

#### Scenario: 납기를 줄이면 품절일이 줄어든다고 말한다

- **WHEN** 최구매가 `whatif_lead` 에 평균 납기 5일을 넣어 돌린다
- **THEN** 지금 납기 → 바꾼 납기와 품절일 줄이 보인다
- **AND** 가상 회사에서 판정은 `down` 이고 재고 금액 변화는 양수다

#### Scenario: 결제 조건을 줄이면 입금이 늘어난다고 말한다

- **WHEN** 정회계가 `whatif_terms` 에서 조건을 15일로 돌린다
- **THEN** 결과나 근거 부족 안내가 나온다
- **AND** 조건이 바뀐 거래처가 있는 가상 회사에서 30일→15일의 판정은 `up` 이다

#### Scenario: 주문이 기다리는 회사에는 잃은 매출이 과대하다고 경고한다

- **WHEN** 재고가 없는 날에도 주문이 평소처럼 들어온 회사의 `whatif_policy` 를 돌린다
- **THEN** 경고에 「기다렸다」 가 들어가고, 그런 일이 없는 회사에는 나오지 않는다

#### Scenario: 음수 재고가 있으면 기초 재고를 의심하라고 경고한다

- **WHEN** 기초 재고가 빠져 재고가 음수인 제품이 있는 회사의 `whatif_policy` 를 돌린다
- **THEN** 경고에 「음수」 가 들어간다

#### Scenario: 최근을 재현하지 못하면 그렇다고 말한다

- **WHEN** 실제 발주와 동떨어진 재주문 규칙을 가진 회사의 `whatif_policy` 를 돌린다
- **THEN** 경고에 「다시 돌리면」 이 들어가고, 규칙이 맞는 회사에는 나오지 않는다

### Requirement: 분석은 원장을 바꾸지 않는다

시스템은 예측과 what-if 계산으로 원장에 아무것도 쓰지 않아야 한다(SHALL). 계산은 브라우저에서만 돌고 저장되지 않는다. what-if 화면은 이를 먼저 알린다.

#### Scenario: what-if 를 돌려도 원장은 그대로다

- **WHEN** 김대표가 what-if 화면을 열고 돌린다
- **THEN** 「원장을 바꾸지 않습니다」 안내가 보이고 원장의 이벤트 수가 그대로다

### Requirement: 분석은 원장만 읽어 모듈을 꺼도 이력을 쓸 수 있다

시스템은 분석에 모듈의 파생 표를 쓰지 않고 원장 이벤트와 공개 레코드만 읽어야 한다(SHALL). 모듈을 켠 기간도 원장에서 읽는다. 켰다가 끈 모듈의 이력만 읽는 모델은 계속 계산하고 `stale_modules` 에 그 모듈을 적으며, 지금 재고나 미결 청구서가 있어야 하는 모델은 잠긴다.

#### Scenario: 모듈을 꺼도 이력 모델은 계속 계산한다

- **WHEN** 김대표가 재고 모듈을 끄고 두 달 뒤의 모델 목록을 읽는다
- **THEN** `stockout_risk` 는 `locked`, `missing_modules` 는 재고다
- **AND** `demand_true` 는 `ready`, `stale_modules` 는 재고이고 안내에 「꺼져 있어」 가 있다

#### Scenario: 모듈이 켜진 기간은 원장에서 읽는다

- **WHEN** 재고를 끈 뒤 다시 켠다
- **THEN** 기간이 2개이고 첫 기간은 끈 날에 끝나며, 재고 이력 일수는 꺼진 기간을 뺀 값이다
- **AND** 그 전 시점의 모델 상태는 그때 모습 그대로다

#### Scenario: 원장에서 읽은 값은 회사가 한 일과 칸마다 같다

- **WHEN** 가상 회사의 이벤트를 넣고 원장에서 읽은 판매·재고·구매·청구 값을 생성기의 값과 비교한다
- **THEN** 제품·지역·날짜의 칸마다 같고 같은 시드의 what-if 결과도 같다

### Requirement: 고른 시점까지의 기록으로 계산한다

시스템은 회사 시점을 고르면 모델 상태와 결과를 그 시점에 시스템이 알던 것으로만 내야 한다(SHALL). 시점을 옮기면 다시 읽는다.

#### Scenario: 고른 시점까지의 기록으로 계산하고 옮기면 다시 읽는다

- **WHEN** 김대표가 재고까지만 켠 시점을 고르고 모델을 연다
- **THEN** 「… 까지의 기록으로」 가 보이고 근거의 끝 날짜가 그 시점이다
- **AND** 그때 구매가 없었던 `lead_time` 은 「구매 모듈을 켜면 열립니다」 로 잠긴다
- **AND** 날짜를 바꾸거나 시점 보기를 끝내면 근거가 다시 계산된다

### Requirement: 공개 시계열은 일어난 일을 그대로 돌려준다

시스템은 공개 시계열 함수로 그 시점의 사실을 돌려주어야 한다(SHALL). 판매는 취소·재확정·수량 변경·되돌리기를 반영하고 서비스 줄을 뺀다. 날짜는 회사 시간대의 업무일이고, 구간은 이벤트가 기록된 때로 나누므로 묶음을 더하면 한 번에 부른 값과 같다.

#### Scenario: 판매 시계열은 변경·취소·재확정·되돌리기를 반영한다

- **WHEN** 수량을 10 에서 7 로 줄이고 2개를 더한 주문, 취소한 주문, 취소 뒤 수량 4 로 재확정한 주문, 되돌린 주문, 되돌리기를 되돌린 주문이 있다
- **THEN** `erp_sales_daily` 의 첫 주문은 수량 9, 매출 900, 원가 540 이고 서비스 줄과 구역 줄은 세지 않는다
- **AND** 취소한 주문은 없고 재확정은 수량 4, 되돌린 주문은 없으며 되돌리기를 되돌린 주문은 다시 있다
- **AND** 그 이벤트들 전의 시점으로 읽으면 그때의 값이 나온다

#### Scenario: 소급 입력은 자기 업무일에 들어가고 묶음을 더하면 같다

- **WHEN** 3월 20일에 3월 2일자 주문을 입력하고, 3월 1일 23:30 과 3월 2일 00:30 에 주문을 확정한다
- **THEN** 회사 시간대로 3월 1일에 2개, 3월 2일에 5개가 나온다
- **AND** 구간을 셋으로 나눠 더해도 같다

#### Scenario: 수량은 제품 단위로 환산된다

- **WHEN** 기준 단위가 개인 제품을 2다스 판 주문을 읽는다
- **THEN** 수량 24, 매출은 그대로 나온다

#### Scenario: 재고 시계열은 창고로 올려 합치고 고객 위치를 뺀다

- **WHEN** 창고의 하위 위치와 고객 위치에 재고 효과가 있는 이벤트들을 읽는다
- **THEN** `erp_stock_daily` 의 하위 위치는 그 창고의 값으로 합쳐지고 고객 위치는 빠지며, 합계는 시점 합계와 같다
- **AND** `erp_stockout_days` 는 품절 구간을 `from`, `to`, `days` 로 주고 아직 품절이면 그 시점까지 센다

#### Scenario: 납기 시계열은 미입고 줄을 남기고 수량 변경과 반품을 읽는다

- **WHEN** 수량을 10 에서 8 로 줄이고 3개, 5개를 받고 1개를 반품한 줄과, 받지 않은 줄, 서비스 줄, 취소한 주문을 읽는다
- **THEN** `erp_lead_times` 에는 두 줄만 나오고 첫 줄은 수량 8, 받은 수량 7, 첫 입고일과 마지막 입고일이 있다
- **AND** 받지 않은 줄의 받은 수량은 0 이고 그 줄의 예정일이 나온다

#### Scenario: 입금 시계열은 부분 입금과 대변 메모와 취소를 읽는다

- **WHEN** 나눠 낸 청구서, 일부만 낸 청구서, 입금을 취소한 청구서, 대변 메모로 정리한 청구서를 읽는다
- **THEN** `erp_payment_delays` 는 고객 청구서 4건만 주고 차례로 잔액 0 과 입금일, 잔액 60, 잔액 100, `reversed` 다

#### Scenario: 전표 시계열은 손익 계정만 회계일로 묶는다

- **WHEN** 9월에 기록한 8월 31일자 전표와 9월 전표를 읽고 9월 전표를 되돌린다
- **THEN** `erp_journal_monthly` 의 8월에는 매출과 비용이 있고 예금 계정은 없다
- **AND** 되돌린 뒤 9월 합계는 0 이다

#### Scenario: 회계를 늦게 켜도 전표 달은 회계일로 센다

- **WHEN** 2026-07-01 에 회계를 켜 다시 만든 전표의 회계일이 2월부터 5월에 걸쳐 있다
- **THEN** `pnl_outlook` 의 근거는 4개월, 시작일은 2026-02-10 이다

#### Scenario: 통계·전환율·재주문 규칙을 시점별로 읽는다

- **WHEN** `erp_flow_stats` 를 분기로, `erp_quote_conversion`, `erp_reorder_rules` 를 읽는다
- **THEN** 분기별 수량·매출·마진·주문 수가 나오고, 견적 10건 중 성사 3, 실패 1, 진행 6 이면 전환율 0.3, 결정 건 기준 0.75 와 80% 구간이 나온다
- **AND** 규칙은 그 시점의 최소 수량을 주고, 모르는 단위 `decade` 는 `ERP_INVALID` 다

### Requirement: 통계와 전환율 화면

시스템은 지역·제품·기간 매출을 표와 그래프로 보여 주고 좁힐 수 있어야 한다(SHALL). 견적 전환율은 근거가 모자라면 비율 하나로 말하지 않고 범위로 말한다.

#### Scenario: 통계는 지역·제품·기간으로 좁혀지고 없으면 빈 상태로 말한다

- **WHEN** 김대표가 매출 통계 화면에서 지역을 고르고, 분기로 바꾸고, 판매가 없는 기간을 고른다
- **THEN** 지역 표가 한 줄로 줄고 매출 합계가 바뀌며 기간 표와 그래프가 나온다
- **AND** 판매가 없으면 「이 기간의 판매 기록이 없습니다」, 호출이 실패하면 오류가 보인다

#### Scenario: 견적 전환율은 근거가 모자라면 범위로만 말한다

- **WHEN** 박영업이 견적이 넉넉한 기간과 모자란 기간의 전환율을 본다
- **THEN** 넉넉한 기간은 비율과 「사용 가능」, 건수에 「아직 결정 전」 이 보인다
- **AND** 모자란 기간은 비율 없이 범위와 「범위로만」 안내가 보인다

### Requirement: 읽을 수 없는 문서의 숫자는 주지 않는다

시스템은 분석을 호출자 권한으로 읽어 읽을 수 없는 문서 유형에서 나온 숫자를 주지 않아야 한다(SHALL). 그 문서로 계산하는 모델은 `state: locked`, `forbidden: true` 이고 건수도 0 이다. 비구성원은 모두 잠기고 공개 키만으로는 호출할 수 없다.

#### Scenario: 권한이 없는 시계열은 비어 있고 모델은 잠긴다

- **WHEN** 박영업(`sales`)이 시계열과 모델 목록을 읽는다
- **THEN** 판매 시계열은 나오고 청구·구매·전표 시계열은 0건이다
- **AND** `cash_in` 은 `locked`, `forbidden: true`, 근거 0 이며 `demand_sales` 는 `ready` 다
- **AND** 정회계는 전표 시계열이 나오고, 비구성원은 모두 `locked`, 공개 키는 권한 오류다

#### Scenario: 권한이 없는 모델은 화면에서도 왜 잠겼는지 말한다

- **WHEN** 박영업이 예측 화면에서 `lead_time` 과 `cash_in` 을 연다
- **THEN** 「잠김」 과 「이 모델을 볼 권한이 없습니다」, 「필요한 역할이 없습니다」 가 보이고 모듈 화면 링크가 없다

### Requirement: 계산이 화면을 막지 않는다

시스템은 원장을 묶음으로 읽어 진행을 보여 주고 계산을 별도 스레드에서 돌려 화면을 막지 않아야 한다(SHALL). 읽기가 실패하면 오류와 다시 시도를 보여 준다. 공개 호출은 API 문장 제한 안에 끝나야 한다.

#### Scenario: 계산은 별도 스레드에서 돌고 읽는 동안 진행을 보여 준다

- **WHEN** 김대표가 `demand_true` 를 연다
- **THEN** 읽는 동안 「n / m」 진행이 보이고 메뉴는 바로 반응한다
- **AND** 계산은 워커 하나에서 돈다

#### Scenario: 읽지 못하면 오류와 다시 시도를 보여 준다

- **WHEN** 모델 목록 호출이나 판매 시계열 호출이 실패한다
- **THEN** 「요청을 처리하지 못했습니다」 와 다시 시도가 보이고, 다시 시도하면 결과가 나온다

#### Scenario: 큰 원장에서도 호출이 제한 안에 끝난다

- **WHEN** 이벤트 2만 건이 넘는 가상 회사의 원장을 묶음으로 읽는다
- **THEN** 가장 오래 걸린 호출이 4초 안에 끝난다

#### Scenario: 휴대폰 폭과 어두운 테마에서도 읽힌다

- **WHEN** 폭 375 의 어두운 테마에서 모델 카드, what-if 폼과 결과, 통계 그래프를 연다
- **THEN** 화면 폭 안에 들어오고 어두운 바탕에서 읽힌다

### Requirement: 품절을 기록으로 알면 수요를 되찾는다

시스템은 재고 이력으로 품절일을 가려 수요를 복원해야 한다(SHALL). 판매 기록만 읽으면 품절이 수요를 가린다. 다음은 정답을 아는 가상 회사의 시험이며 실제 회사의 성능이 아니다.

#### Scenario: 품절이 수요를 가리고 재고 이력이 되찾는다

- **WHEN** 품절이 많은 가상 회사 8곳의 여름 수요를 판매 기록만으로, 또 재고 이력으로 추정한다
- **THEN** 판매 기록만 읽으면 오차 중앙값이 20% 를 넘고 낮은 쪽으로 15% 넘게 치우친다
- **AND** 재고 이력을 쓰면 오차 중앙값이 16% 아래이고 치우침은 8% 안이며 구간 포함률 중앙값이 60% 이상이다

#### Scenario: 재고가 넉넉하면 재고 이력의 차이가 작다

- **WHEN** 재고가 넉넉한 가상 회사 8곳으로 같은 비교를 한다
- **THEN** 두 오차의 차이 중앙값이 5점 안이다

## 성능·비용 제약

**아래 숫자는 전부 생성기로 만든 가상 회사의 결과이고 실제 회사의 성능이 아니다.** 실제 회사에서는 이보다 나쁠 것으로 보아야 하며 다시 재야 한다.

|---|---|

| 보급형 단종(실제 -2.51억): + 재고 / + 구매 | -2.27억, 13.4%, 83% / -2.41억, 13.2%, 85% |
