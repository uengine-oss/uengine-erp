# 경비

## Purpose

직원이 영수증을 첨부해 경비를 신청하고, 상사가 승인하고, 경리가 지급을 기록한다. 인사 모듈이 있어야 켜고, 회계가 켜져 있으면 전표가 생기며, 회계를 나중에 켜도 같은 전표가 나온다. 파일과 파일 이름은 원장 밖 고객의 Supabase Storage 에 두어 지울 수 있고 원장에는 지문만 남는다. **경비의 금액, 적요, 직원 이름은 모든 구성원이 읽는다.** 커널의 읽기 권한이 유형 단위이기 때문이다. 판단과 안 하는 것은 `docs/modules/expense.md` 에 있다.

## Requirements

### Requirement: 경비는 꺼진 채 시작하고 인사가 있어야 켠다

시스템은 새 회사에서 경비 모듈을 꺼 두어야 한다(SHALL). 인사가 켜져 있지 않으면 켤 수 없고, 경비가 켜져 있는 동안 인사를 끌 수 없다. 켜면 메뉴에 경비, 경비 유형, 부서별 추이가 생긴다. 아무 이벤트도 구독하지 않는다.

#### Scenario: 인사 없이는 켤 수 없다

- **WHEN** 김대표가 인사를 켜기 전에 경비를 켠다
- **THEN** `ERP_MODULE_OFF` 로 거부되고 "인사 모듈을 먼저 켜세요" 라고 말한다
- **AND** 모듈 카드에 먼저 켤 모듈이 인사라고 적혀 있다

#### Scenario: 인사를 경비 아래에서 끌 수 없다

- **WHEN** 경비가 켜져 있는데 인사를 끈다
- **THEN** `ERP_IN_USE` 다
- **AND** 경비를 끈 뒤에는 인사를 끌 수 있고, 다시 인사와 경비 순서로 켜면 이어서 쓴다

#### Scenario: 어떤 조합에서도 서로 끼어들지 않는다

- **WHEN** 경비를 판매·재고·구매·청구·회계와 함께 또는 없이 켜고 경비 일과 업무 일을 차례로 한다
- **THEN** 멈춘 구독이 없고, 경비 일은 회계 전표 말고 다른 모듈의 스트림에 쓰지 않으며, 현재 상태는 원장을 재생한 값과 같다

### Requirement: 신청은 본인이나 담당자가 하고 승인은 상사나 관리자가 한다

시스템은 직원 항목을 비운 신청을 이 계정의 재직 직원 기록으로 받아야 한다(SHALL). 다른 직원 것은 `hr`, `accounting`, `admin` 만 대신 올린다. 승인과 반려는 신청 때 적은 상사의 계정이나 관리자만 한다. 지급은 `accounting` 과 관리자만 한다.

#### Scenario: 남의 일을 대신하지 못한다

- **WHEN** 오동료가 박영업의 경비를 고치거나 신청하거나 첨부하거나 지우거나 승인한다
- **THEN** 모두 `ERP_FORBIDDEN` 이다
- **AND** 승인 뒤 상사나 본인이 지급하거나 지급 뒤 상사가 취소해도 `ERP_FORBIDDEN` 이다

#### Scenario: 직원이 연결되지 않은 계정

- **WHEN** 직원 기록이 없는 구성원이 직원 항목을 비우고 경비를 만든다
- **THEN** `ERP_REQUIRED` 이고 "연결된 직원이 없습니다" 라고 말한다

#### Scenario: 본인 승인

- **WHEN** 상사가 있는 관리자가 자기 경비를 승인한다
- **THEN** `ERP_FORBIDDEN` 이고 상사가 승인한다고 말한다
- **WHEN** 상사가 없는 관리자가 자기 경비를 승인한다
- **THEN** 승인되고 `ExpenseApproved` 에 `self_approved: true` 가 남는다
- **WHEN** 상사에게 ERP 계정이 없다
- **THEN** 관리자가 승인한다

#### Scenario: 버튼은 승인할 사람에게만 보인다

- **WHEN** 박영업이 자기 경비의 승인 대기 화면을 연다
- **THEN** 승인과 반려 버튼이 없다. 김팀장에게는 있다

#### Scenario: 퇴사자

- **WHEN** 퇴사한 직원에게 새 경비를 올린다
- **THEN** `ERP_INVALID` 다
- **AND** 퇴사 전에 만든 경비는 담당자가 신청하고 상사가 승인하고 지급까지 끝낼 수 있으며 이름이 그대로 남는다

### Requirement: 금액과 날짜의 경계가 지켜진다

시스템은 금액을 회사 통화 자릿수로 반올림한 값이 0보다 커야 한다고 해야 한다(SHALL). 지출일은 오늘까지다. 회계일은 지출일 이상 오늘 이하, 지급일은 회계일 이상 오늘 이하다. 시스템만 쓰는 칸과 없는 칸은 버리지 않고 거부한다.

#### Scenario: 금액 경계

- **WHEN** 금액이 1, 0, -1, 0.4, 0.5, `abc` 다
- **THEN** 차례로 통과, `ERP_INVALID`, `ERP_INVALID`, `ERP_INVALID`, 1로 통과, `ERP_INVALID` 다

#### Scenario: 날짜 경계

- **WHEN** 지출일이 오늘, 내일, `today`, `infinity`, `2026-02-30` 이다
- **THEN** 오늘만 통과하고 나머지는 `ERP_INVALID` 다
- **AND** 비우면 오늘이다

#### Scenario: 회계일과 지급일 경계

- **WHEN** 지출일 6월 10일 경비의 회계일을 9일, 내일로 하거나 지급일을 회계일 하루 전, 내일로 한다
- **THEN** `ERP_INVALID` 다. 같은 날은 통과한다

#### Scenario: 단계는 순서대로만 간다

- **WHEN** 작성 중인 경비를 승인하거나, 승인 대기를 지급하거나, 지급을 다시 지급하거나, 신청한 경비를 고친다
- **THEN** `ERP_STATE` 다. 거부된 요청은 이벤트를 남기지 않는다

### Requirement: 신청에는 영수증이나 없는 사유가 있어야 한다

시스템은 영수증도 없는 사유도 없는 신청을 거부해야 한다(SHALL). 파일과 파일 이름은 원장에 넣지 않고 지문, 크기, 형식만 넣는다. 파일은 10 MB, JPG·PNG·WEBP·HEIC·PDF, 한 건에 10개까지다. 취소되지 않은 다른 경비의 영수증과 지문이 같으면 거부한다. 저장소가 있는 프로젝트에서는 파일이 실제로 있어야 등록된다.

#### Scenario: 영수증 없이 신청

- **WHEN** 박영업이 영수증 없이 신청한다
- **THEN** "영수증을 첨부하거나 영수증이 없는 사유를 적어 주세요" 로 막힌다
- **AND** 파일을 올리면 신청되고, 사유를 적어도 신청된다

#### Scenario: 파일 이름은 원장에 없다

- **WHEN** 파일을 올린다
- **THEN** 파일은 Storage 비공개 버킷에, 이름은 `erp.expense_receipts` 에 있고, 원장 전체 어디에도 이름과 경로가 없으며 지문은 있다

#### Scenario: 같은 파일은 한 번만

- **WHEN** 같은 파일을 같은 경비나 다른 사람의 경비에 다시 올린다
- **THEN** `ERP_DUPLICATE` 이고 어느 경비에 있는지 말한다
- **AND** 화면은 방금 올린 파일을 저장소에서 지운다

#### Scenario: 파일 경계

- **WHEN** 크기가 10,485,760, 10,485,761, 0 이거나 형식이 실행 파일이거나 지문이 짧거나 없는 칸이 있다
- **THEN** 첫째만 통과한다. 11개째도 `ERP_INVALID` 다

#### Scenario: 저장소에 없는 파일

- **WHEN** 저장소가 있는 프로젝트에서 올리지 않은 파일을 등록한다
- **THEN** `ERP_NOT_FOUND` 다

### Requirement: 영수증은 관계된 사람만 열고 지우는 데 규칙이 있다

시스템은 파일과 파일 이름을 본인, 승인을 요청받은 사람, `hr`, `accounting`, `admin` 에게만 열어야 한다(SHALL). 작성 중과 반려 상태에서는 본인이 지운다. 신청한 뒤에는 `hr`, `accounting`, `admin` 이 사유를 적어 지우고, 사유에 파일 이름이 있으면 거부한다.

#### Scenario: 다른 직원은 못 연다

- **WHEN** 오동료가 박영업의 경비를 연다
- **THEN** 내역은 보이고 "볼 권한이 없습니다" 가 보이며 파일 이름은 없다
- **AND** Storage 에 직접 요청해도 받지 못한다
- **AND** 공개 키로는 표를 읽지 못하고, 담당자도 표를 직접 고치거나 지우지 못한다

#### Scenario: 상사는 신청된 뒤에 연다

- **WHEN** 신청 전에 김팀장이 열면 아무것도 없고, 신청 뒤에 열면 파일이 열린다

#### Scenario: 지우기

- **WHEN** 신청한 경비의 영수증을 본인이 지우거나, 회계 담당자가 사유 없이 또는 파일 이름을 적은 사유로 지운다
- **THEN** 차례로 `ERP_FORBIDDEN`, `ERP_REQUIRED`, `ERP_INVALID` 다
- **AND** 사유를 제대로 적으면 행이 사라지고 사유가 원장에 남는다

### Requirement: 같은 날 같은 금액은 승인자에게 보인다

시스템은 같은 사람, 같은 지출일, 같은 금액으로 신청, 승인, 지급 상태인 경비가 있으면 막지 않고 번호를 적어 보여 주어야 한다(SHALL). 반려된 것은 세지 않는다.

#### Scenario: 쌍둥이 표시

- **WHEN** 같은 날 같은 금액을 두 번 신청한다
- **THEN** 둘째에 첫째 번호가 적히고, 첫째를 반려한 뒤의 신청에는 첫째가 적히지 않는다

### Requirement: 이벤트는 구독자에게 필요한 사실을 싣는다

시스템은 `ExpenseSubmitted`, `ExpenseApproved`, `ExpenseRefused`, `ExpensePaid`, `ExpenseCancelled` 에 번호, 직원, 부서, 유형, 계정, 지출일, 적요, 금액을 실어야 한다(SHALL). 구독자가 다시 묻지 않아도 되어야 한다. 계약은 `docs/modules/events.md` 에 있다.

#### Scenario: 승인과 지급의 사실

- **WHEN** 경비가 승인되고 지급된다
- **THEN** `ExpenseApproved` 에 `accounting_date, self_approved, approved_by_name, account_id` 가, `ExpensePaid` 에 `paid_on, paid_from, accounting_date` 가 있다

### Requirement: 회계가 켜져 있으면 전표가 생기고 나중에 켜도 같다

시스템은 승인 때 유형의 계정(없으면 잡비)을 차변, 미지급금을 대변으로, 지급 때 미지급금을 차변, 보통예금이나 현금을 대변으로 전표를 만들어야 한다(SHALL). 취소하면 그 경비의 전표가 원래 날짜에서 지워진다. 회계를 처음, 중간, 끝에 켠 회사의 장부는 같다. 회계가 멈춰도 경비는 멈추지 않는다.

#### Scenario: 승인과 지급의 전표

- **WHEN** 식대 20,000원을 승인하고 지급한다
- **THEN** 복리후생비 차변, 미지급금 대변, 그다음 미지급금 차변, 보통예금 대변이고 차변과 대변이 맞는다

#### Scenario: 나중에 켜도 같다

- **WHEN** 같은 일을 회계를 처음, 중간, 끝에 켠 세 회사에서 한다(승인, 지급, 현금 지급, 취소, 반려, 되돌리기를 섞어)
- **THEN** 세 회사의 날짜별 계정 잔액이 같다

#### Scenario: 회계가 고장 나도 경비는 간다

- **WHEN** 회계 처리기가 실패하는 동안 경비를 승인하고 지급한다
- **THEN** 경비는 지급 완료가 되고, 버스 화면에 원인이 보이며, 고치고 재시도하면 누락과 중복 없이 전표가 생긴다

#### Scenario: 취소

- **WHEN** 지급한 경비를 회계 담당자가 사유를 적어 취소한다
- **THEN** 계정 잔액이 0 이 되고 원장에는 승인, 지급, 취소가 모두 남는다

### Requirement: 잠긴 기간은 승인, 지급, 취소를 막는다

시스템은 잠금일 안의 회계일이나 지급일로 승인, 지급하는 것과 그 안의 전표를 지우는 취소를 거부해야 한다(SHALL). 더 늦은 날짜로는 지나간다.

#### Scenario: 마감한 달의 경비

- **WHEN** 5월을 잠근 뒤 5월 20일 경비를 그냥 승인한다
- **THEN** `ERP_LOCKED` 이고, 회계일을 6월 1일로 주면 승인된다
- **AND** 5월 전표가 있는 경비의 취소는 잠금이 풀릴 때까지 `ERP_LOCKED` 다

### Requirement: 지급한 경비는 되돌리지 않고 보상한다

시스템은 지급 전의 일은 전표와 함께 되돌리고, 지급한 경비의 되돌리기는 막아야 한다(SHALL). 사가에서는 지급한 경비를 `compensate` 로 취소하고 돈을 되찾는 일은 사람이 한다고 경고한다. 잠긴 기간이면 아무것도 하지 않고 이유를 말한다. 영수증이 남아 있으면 그 시점 이전으로 되돌리지 못한다.

#### Scenario: 말로 취소

- **WHEN** 에이전트가 MCP 로 경비를 만들고 신청하고 승인하고 지급한 뒤 같은 사가를 되돌린다
- **THEN** 방식은 `compensate` 이고 경고에 "돌려받았는지" 가 있으며, 뒤에 그 사가의 순효과가 모두 0 이고 지급 기록은 원장에 남는다
- **AND** 같은 사가에 새 호출은 `ERP_SAGA_CLOSED` 다

#### Scenario: 지급 전 되돌리기

- **WHEN** 승인을 되돌린다
- **THEN** 전표까지 범위에 보이고 승인 대기로 돌아가며 계정 잔액은 0 이다

#### Scenario: 잠긴 사가

- **WHEN** 잠긴 기간의 전표가 있는 사가를 되돌리려 한다
- **THEN** 방식은 `blocked` 이고 잠금일을 말한다

#### Scenario: 영수증이 남아 있다

- **WHEN** 첨부 이전으로 되돌리려 한다
- **THEN** 막히고 "영수증이 남아 있어" 라고 말한다. 지운 뒤에는 막히지 않는다

### Requirement: MCP 는 구성원의 권한만큼만 한다

시스템은 MCP 호출에 그 구성원의 규칙을 그대로 적용해야 한다(SHALL). 경비는 도구 4개로 다룬다.

#### Scenario: 에이전트의 권한

- **WHEN** 박영업의 키로 남의 경비를 올리거나 자기 경비를 승인하고, 김팀장의 키로 지급한다
- **THEN** 도구 결과가 `ERP_FORBIDDEN` 이다
- **AND** 파일 이름을 읽는 길이 없다

### Requirement: 부서별 경비 추이는 세 상태로 보이고 원장만 읽는다

시스템은 승인 경비를 지출한 달과 승인 때의 부서로 묶어 보여 주어야 한다(SHALL). 취소하거나 되돌린 건은 빠진다. 모듈을 켠 적 없으면 잠김, 승인 경비가 있던 달이 3개월이 안 되면 근거 부족, 그 뒤는 사용 가능이다. 꺼도 답한다.

#### Scenario: 세 상태

- **WHEN** 모듈을 켜기 전, 켠 뒤, 석 달째 승인 뒤에 모델을 본다
- **THEN** 잠김, 근거 부족(3개월 필요), 사용 가능이다
- **AND** 끄면 그대로 답하고 꺼져 있다고 말한다

#### Scenario: 부서는 그때의 부서다

- **WHEN** 직원이 부서를 옮긴 뒤 승인된 경비가 있다
- **THEN** 옮기기 전 달은 옛 부서, 옮긴 뒤 달은 새 부서로 묶인다
- **AND** 기간의 양 끝 날은 들어가고, 취소한 건은 빠지며, 시작이 끝보다 늦으면 `ERP_INVALID` 다

### Requirement: 경비 유형은 회계 담당자가 다룬다

시스템은 새 회사에 기본 유형을 넣어야 한다(SHALL). 이름은 유일하다. 유형을 비우면 기타 경비다. 계정 칸은 회계가 켜져 있을 때만 보인다.

#### Scenario: 유형

- **WHEN** 영업 사원이 유형을 만들거나 같은 이름을 다시 만들거나 없는 유형으로 신청한다
- **THEN** 차례로 `ERP_FORBIDDEN`, `ERP_DUPLICATE`, `ERP_INVALID_REF` 다

### Requirement: 가상 회사에 경비가 더해져도 판매와 재고 수치는 그대로다

시스템은 경비를 자기 난수열로 만들어 날짜별로 끼워 넣어야 한다(SHALL). 그 단계를 빼면 나머지 단계가 그대로이고 판매, 재고 수치가 같다. 시산표는 경비 계정과 지급한 돈만 다르다.

#### Scenario: 수치 비교

- **WHEN** 경비를 넣은 가상 회사와 뺀 회사를 만든다
- **THEN** 주문, 재고, 판매·재고·구매·청구 이벤트 수가 같고, 시산표는 경비 관련 계정 말고 같으며, 빠져나간 돈은 지급한 합계다
