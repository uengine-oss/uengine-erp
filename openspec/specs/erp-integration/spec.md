# 외부 연동: REST, MCP, 연동 키, 이벤트 피드

## Purpose

가온가전은 별도 서버 없이 Supabase 위에서 외부 시스템과 에이전트를 잇는다. 유형마다 REST 자원이 자동으로 생기고, MCP 는 켜져 있는 모듈의 레코드를 도구 4개로 다루며, 긴 작업에는 관리자가 만든 연동 키를 쓴다. 어느 입구로 들어와도 같은 명령이 되어 같은 규칙과 역할을 거쳐 원장에 남는다. 외부 시스템은 이벤트 피드로 원장을 차례로 읽는다.

## Requirements

### Requirement: 유형마다 REST 자원이 카탈로그에서 생긴다

시스템은 설정 유형과 숨김 유형을 뺀 카탈로그 유형마다 `/rest/v1/erp_api_<유형>` 자원을 만들어야 한다(SHALL). GET·POST·PATCH·DELETE 는 모두 명령으로 바뀌어 원장에 출처 `api` 로 남는다. 비밀번호 칸은 자원에 없다. API 는 표준 설명 문서로 자기 모양을 알려 준다.

#### Scenario: 표준 CRUD 가 명령이 되어 원장에 남는다

- **WHEN** 외부 시스템이 `erp_api_partner` 에 POST, GET, PATCH, DELETE 를 차례로 보낸다
- **THEN** 201, 200, 200, 200 이 오고 응답의 `version` 이 1, 2 로 늘며 지운 뒤에는 조회되지 않는다
- **AND** 그 문서의 이벤트 출처는 `api` 다

#### Scenario: 상태 변경은 업무 동작이 되어 한 번에 처리된다

- **WHEN** 초안 문서를 `state: done` 과 메모, 수량을 함께 PATCH 한다
- **THEN** 값 변경 이벤트 뒤에 그 상태의 업무 동작 이벤트가 이어지고 상태·메모·수량이 모두 들어간다
- **AND** 갈 수 없는 상태로 PATCH 하면 `ERP_INVALID` 다

#### Scenario: 넓은 필터로 여러 건을 바꿀 수 없다

- **WHEN** 외부 시스템이 필터 없이, 또는 `id=not.is.null` 처럼 여러 건에 걸리는 필터로 DELETE 한다
- **THEN** 둘 다 400 이고 넓은 필터의 `message` 에 `ERP_BULK` 가 있다
- **AND** 건수가 그대로다

#### Scenario: If-Match 로 옛 버전의 수정을 막는다

- **WHEN** 이미 버전 2 인 문서를 `If-Match: 1` 로 PATCH 한다
- **THEN** 409 이고 `message` 에 `ERP_CONFLICT` 가 있다

#### Scenario: Idempotency-Key 로 다시 보내도 한 건이다

- **WHEN** 같은 `Idempotency-Key` 로 같은 POST 를 두 번 보낸다
- **THEN** 두 응답의 `id` 가 같고 그 이름의 문서는 1건이다

#### Scenario: 역할과 모듈과 공개 키의 제한이 그대로다

- **WHEN** 조회 역할이 POST 하고, 공개 키만으로 GET 하고, 꺼진 모듈의 자원에 POST 한다
- **THEN** 조회 역할은 403(`ERP_FORBIDDEN`), 공개 키는 401 또는 403, 꺼진 모듈은 `ERP_MODULE_OFF` 다

#### Scenario: 제품과 함께 설치된 자원에도 쓸 수 있다

- **WHEN** 김대표가 설치된 유형의 자원 `erp_api_tag` 에 POST 한다
- **THEN** 버전 1 로 만들어지고 공개 키만으로는 권한 오류다

#### Scenario: API 가 자기 모양을 설명한다

- **WHEN** 로그인 토큰으로 `/rest/v1/` 을 `Accept: application/openapi+json` 으로 읽는다
- **THEN** `/erp_api_partner` 에 get, post, patch, delete 가 있고 `region` 칸이 있으며 `password` 칸은 없다

### Requirement: MCP 는 도구 4개로 켜진 모듈의 레코드를 다룬다

시스템은 `POST /rest/v1/rpc/erp_mcp` 에서 MCP 를 답해야 한다(SHALL). 도구는 `erp_read`, `erp_create`, `erp_update`, `erp_delete` 넷이고 모듈을 켜고 꺼도 도구는 그대로이며 다룰 수 있는 유형만 바뀐다. 쓰기는 출처 `mcp` 로 원장에 남는다. 규칙 오류는 도구 결과의 `isError` 로 돌려준다. 스트리밍은 제공하지 않는다.

#### Scenario: 공식 클라이언트가 접속해 도구 4개를 본다

- **WHEN** 에이전트가 로그인 토큰으로 공식 MCP 클라이언트로 접속한다
- **THEN** 서버 이름은 `uengine-erp` 이고 도구 4개가 나오며 목록은 4,000 바이트 아래다
- **AND** `initialize` 는 받은 `protocolVersion` 으로 답하고, 응답이 필요 없는 알림은 202 와 빈 본문이다

#### Scenario: 켜진 모듈의 유형만 도구와 리소스에 나온다

- **WHEN** 에이전트가 도구 목록과 리소스 목록을 읽고, 김대표가 그 모듈을 끈 뒤 다시 읽는다
- **THEN** 켜져 있을 때는 도구의 `type` 목록과 `erp://catalog`, `erp://<유형>/schema` 에 나온다
- **AND** 끄면 도구를 고치지 않아도 그 유형이 목록에서 사라진다

#### Scenario: 읽기·쓰기·상태 변경·이력·시점을 도구로 한다

- **WHEN** 에이전트가 문서를 만들고 고치고 `values.state` 로 상태를 바꾸고 지운다
- **THEN** 모두 이벤트로 남고 이력(`history: true`)에 차례로 보인다
- **AND** `erp_read` 는 인자 없이 유형 목록, `filter`·`search` 로 목록, `schema` 로 칸과 상태 변경, `as_of` 로 그 시점의 값을 준다

#### Scenario: 규칙 오류는 에이전트가 읽을 수 있는 도구 결과로 온다

- **WHEN** 에이전트가 옛 `expected_version` 으로 고치거나 필수값 없이 만든다
- **THEN** 호출은 성공하고 결과의 `isError` 가 참이며 글에 `ERP_CONFLICT`, `ERP_REQUIRED` 가 있다

#### Scenario: 에이전트가 주문을 확정하고 전표가 이어진다

- **WHEN** 박영업의 권한으로 에이전트가 `erp_create` 로 주문을 만들고 `values.state: sale` 로 확정하고 `action: lock` 으로 잠근다
- **THEN** 주문 상태가 `sale` 이고 마지막 이벤트의 출처가 `mcp` 다
- **AND** 재고가 켜져 있으면 전달 뒤 전표가 1건 생긴다

#### Scenario: 조회 역할은 읽기만 하고 읽기 제한 유형은 보이지 않는다

- **WHEN** 조회 역할의 에이전트가 읽고, 만들고, 회계 전용 유형의 목록·문서·이력을 읽는다
- **THEN** 읽기는 되고 쓰기는 `isError` 에 `ERP_FORBIDDEN` 이다
- **AND** 회계 전용 유형은 셋 다 `isError` 이고 유형 목록에도 없다

#### Scenario: 모르는 메서드는 표준 오류로 답한다

- **WHEN** 에이전트가 없는 메서드를 부른다
- **THEN** 응답의 `error.code` 가 -32601 이다

### Requirement: 에이전트의 실수를 같은 MCP 도구로 되돌린다

시스템은 도구를 늘리지 않고 되돌리기를 제공해야 한다(SHALL). `erp_read` 에 `rollback` 을 주면 범위를 미리 보고, `erp_create` 의 `type: rollback` 으로 실행한다. 이력에는 `correlation_id` 가 나온다. 비관리자는 자기가 MCP 로 한 일이고 범위 안의 모든 이벤트가 자기 것일 때만 되돌릴 수 있다. 그 밖에는 관리자만 한다. 원장의 앞선 기록은 지우지 않으며, 되돌린 이벤트에 행위자와 사유가 남는다.

#### Scenario: 에이전트가 자기 주문을 모듈을 넘어 되돌린다

- **WHEN** 박영업의 키로 에이전트가 주문을 만들어 확정하고, 재고 모듈이 출고 전표를 만든 뒤, 같은 키로 범위를 읽고 사유를 적어 실행한다
- **THEN** 미리보기의 `streams` 에 주문과 출고 전표가 함께 있고, 읽기만으로는 아무것도 바뀌지 않는다
- **AND** 실행 뒤 주문은 `draft`, 출고 전표는 없던 상태이고, 이력의 앞선 이벤트는 그대로이며 마지막 이벤트는 출처 `rollback`, 행위자 박영업, 그 사유의 `Reverted` 다

#### Scenario: 미리보기가 낡았거나 사유가 없으면 실행하지 않는다

- **WHEN** 에이전트가 틀린 `plan_hash` 로, 또는 `reason` 없이 실행한다
- **THEN** 결과의 `isError` 가 참이고 글에 `ERP_CONFLICT`, `ERP_REQUIRED` 가 있으며 데이터는 그대로다

#### Scenario: 온전히 자기 일이 아니면 스스로 되돌리지 못한다

- **WHEN** 에이전트가 다른 에이전트의 작업, 자기 계정으로 화면에서 한 작업, 다른 사람이 이어 간 작업, 회사 전체 시점 되돌리기를 시도한다
- **THEN** 모두 `isError` 에 `ERP_FORBIDDEN` 이고 데이터는 그대로다

#### Scenario: 관리자는 이어진 작업까지 동의하고 되돌린다

- **WHEN** 관리자가 에이전트의 작업 위에 다른 작업이 이어진 것을 되돌린다
- **THEN** 동의 없이는 `ERP_ROLLBACK_CASCADE` 이고, `allow_cascade` 를 주면 함께 돌아간다

#### Scenario: 도구는 4개 그대로다

- **WHEN** 에이전트가 도구 목록을 읽는다
- **THEN** 도구는 4개이고 `rollback` 은 `erp_create` 의 `type` 에만 있고 `erp_read` 의 `type` 에는 없다

### Requirement: 연동 키로 로그인 없이 구성원 권한으로 동작한다

시스템은 로그인 토큰이 1시간이면 끝나는 에이전트를 위해 구성원에 묶인 장기 키를 `x-erp-key` 헤더로 받아야 한다(SHALL). 키는 `erpk_` 로 시작하고 해시만 저장되며 원장에 남지 않는다. 키는 그 구성원의 권한을 넘지 못한다. 키를 만들고 폐기하고 목록을 보는 일은 관리자만 한다. 키가 잘못되거나 없거나 폐기됐으면 401(`ERP_AUTH`)이다. 현재 연동 키는 MCP 입구에서만 쓴다.

#### Scenario: 키로 로그인 없이 쓰고 행위자는 그 구성원이다

- **WHEN** 김대표가 박영업의 키를 만들고 에이전트가 공개 키와 그 키로 문서를 만든다
- **THEN** 키는 `erpk_` 뒤 16진수 48자이고, 문서의 이벤트 행위자는 박영업, 출처는 `mcp` 다

#### Scenario: 키는 저장되지 않고 원장에 남지 않는다

- **WHEN** 키를 만들고 쓴 뒤 저장소와 원장에서 찾는다
- **THEN** 표에 키 자체가 없고 원장에 키 글자가 없다
- **AND** 목록(`erp_api_keys`)에는 앞자리 `prefix` 만 있고 `key` 칸이 없다

#### Scenario: 키는 구성원 권한을 넘지 못하고 구성원이 사라지면 끊긴다

- **WHEN** 조회 역할의 키로 쓰고, 김대표가 그 구성원을 비활성화한 뒤 다시 부른다
- **THEN** 쓰기는 `isError` 에 `ERP_FORBIDDEN` 이고 비활성화 뒤에는 호출 자체가 `ERP_FORBIDDEN` 이다

#### Scenario: 잘못된 키와 없는 키와 폐기한 키는 거부된다

- **WHEN** 틀린 키로, 키 없이, 폐기한 키로 접속한다
- **THEN** 모두 401 또는 `ERP_AUTH` 다

#### Scenario: 관리자만 키를 만든다

- **WHEN** 박영업이 공개 함수로 키를 만든다
- **THEN** `ERP_FORBIDDEN` 이다

#### Scenario: 연동 화면이 주소와 헤더와 자원을 안내한다

- **WHEN** 김대표가 키가 하나도 없을 때 설정의 연동 화면을 연다
- **THEN** 「아직 만든 키가 없습니다」 와 MCP 주소, `x-erp-key`·`apikey` 헤더 예시, REST 예시가 보인다
- **AND** REST 자원 목록에 `erp_api_sales_order` 가 있고 꺼진 모듈의 `erp_api_picking` 은 없다

#### Scenario: 키는 만들 때 한 번만 보여 준다

- **WHEN** 김대표가 이름 「회계 에이전트」 와 정회계를 골라 키를 만든다
- **THEN** 이름이나 구성원이 비면 「이름과 구성원을 모두 고르세요」 가 나온다
- **AND** 「한 번만 보여 줍니다」 와 키, 복사 버튼이 나오고 MCP 예시에 키가 들어간다
- **AND** 표에는 앞 11자와 「사용 중」 만 보이고, 다른 화면에 갔다 오면 키가 화면에서 사라진다
- **AND** 그 키로 `tools/list` 를 부르면 도구 4개가 오고 새로 고치면 마지막 사용이 「아직 없음」 이 아니다

#### Scenario: 폐기하면 바로 끊긴다

- **WHEN** 김대표가 키의 폐기를 눌러 확인한다
- **THEN** 확인 창이 「바로 접속할 수 없게 됩니다」 를 알리고 표가 「폐기됨」 으로 바뀌며 폐기 버튼이 사라진다
- **AND** 그 키로는 더 부를 수 없다

#### Scenario: 관리자가 아니면 연동 메뉴가 없고 실패와 작은 화면에도 읽힌다

- **WHEN** 박영업이 연동 메뉴와 주소를 찾고, 김대표의 목록 호출이 실패하고, 폭 375 의 어두운 테마로 본다
- **THEN** 박영업에게는 메뉴와 키 만들기가 없고 「관리자만 볼 수 있습니다」 가 보인다
- **AND** 실패하면 「요청을 처리하지 못했습니다」 와 다시 시도가 보이고, 예시가 화면 폭 안에 들어오며 어두운 바탕에서 읽힌다

### Requirement: 외부 시스템은 이벤트 피드로 원장을 차례로 읽는다

시스템은 공개 함수 `erp_event_feed` 로 끝난 트랜잭션의 이벤트만 `(txid, seq)` 순서로 주고 다음 커서(`next`)를 함께 돌려주어야 한다(SHALL). 한 번에 최대 1,000건이고 이벤트 이름으로 거를 수 있다. 호출자의 읽기 권한을 따른다. 앱 화면에는 쓰이지 않는다.

#### Scenario: 커서로 이어 읽는다

- **WHEN** 외부 시스템이 `OrderCreated` 만 3건씩 읽고 돌아온 `next.txid`, `next.seq` 로 다시 읽는다
- **THEN** 첫 응답은 3건이고 둘째 응답의 첫 이벤트는 앞의 마지막보다 뒤다

#### Scenario: 끝나지 않은 트랜잭션의 이벤트는 나오지 않는다

- **WHEN** 트랜잭션이 열린 채 이벤트를 쓴 동안 피드를 읽고, 커밋한 뒤 다시 읽는다
- **THEN** 앞에서는 그 이벤트가 없고 뒤에서는 있다

#### Scenario: 피드는 호출자의 읽기 권한을 따른다

- **WHEN** 김대표와 박영업이 구매 주문이 있는 회사의 피드를 읽고, 공개 키만으로도 부른다
- **THEN** 김대표에게는 구매 주문 이벤트가 있고 박영업에게는 없다
- **AND** 공개 키만으로는 권한 오류다
